# 会話検索と仮想化の設計案

この文書は、仮想化導入前の検索処理をもとにした設計案です。実装後の設計条件と制限は、[チャット履歴のメモリ](working_memory/チャット履歴のメモリ.md)に記録しています。

Nerita では、検索対象をチャットデータに変更すれば、検索中も仮想化を維持できると考えられます。既存の検索機能を変更し、`@tanstack/react-virtual` と Ctrl+F を両立する方針を提案します。

仮想化導入前の実装には、次の特徴がありました。

- `useChatSearch.ts`：Ctrl+F を独自に捕捉している
- `searchRanges.ts`：描画済み DOM を走査して一致箇所を検索している
- `Messages.tsx`：メッセージ・ツール・サブエージェントを時系列に統合している
- `MessageText.tsx`：Markdown を描画し、既に `memo` で再描画を抑制している

独自の検索機能を使っているため、ブラウザーの標準検索の制約を受けずに、検索対象を DOM からチャットデータへ変更できます。

## 検索結果と描画の分離

検索結果の情報と、実際に DOM へ描画する内容を分離します。

この構成なら、検索対象が数千メッセージあっても、検索結果へ移動する際に全メッセージの DOM を生成せずに済みます。

## 具体的な実装方針

既存の `searchPattern()` と `findMatches()` は再利用できます。変更する中心は `useChatSearch.ts` です。

検索結果を次のような情報で管理します。

```ts
type SearchHit = {
  entryKey: string;
  start: number;
  end: number;
};
```

`entryKey` はメッセージだけでなく、ツールやサブエージェントのカードも識別できる安定したキーです。

検索は `message.text` や `tool.title` などの元データに対して行い、結果には一致位置のみを保存します。全文のコピーや全件分の `DOM Range` を保持する必要はありません。

検索結果への移動は、例えば次の形です。

```ts
function revealHit(hit: SearchHit) {
  const index = indexByKey.get(hit.entryKey);
  if (index === undefined) return;

  virtualizer.scrollToIndex(index, {
    align: "center",
  });

  setActiveHit(hit);
}
```

`scrollToIndex()` でメッセージを描画範囲へ移し、マウント完了後に該当行の DOM から一致箇所を探します。既存の `CSS.highlights` と `revealMatch()` で、一致箇所を強調して表示位置を調整します。

ただし、Markdown 原文と表示テキストは一致しないことがあります。まず表示上の一致箇所を探し、後から Markdown を解析して検索用テキストと表示位置を対応付ける方式へ拡張する案です。

## Nerita 特有の注意点

検索以外の処理でも、次の対応が必要になります。

| 対象                         | 必要な対応                                                     |
| -------------------------- | --------------------------------------------------------- |
| `useFollowConversation.ts` | TanStack Virtual 側のスクロール追従との二重制御を避ける                               |
| `ToolCard.tsx`             | 仮想化でアンマウントすると開閉状態が失われるため、状態を親側に保持する                       |
| `Messages.tsx`             | `indexOf()`、`slice().reverse().find()` を各メッセージで実行する構造を見直す |
| `useChatView.ts`           | 生の `scrollTop` による復元は、行の推定高さによるずれに注意する                    |
| `searchRanges.ts`          | 全 DOM の走査から、現在マウントされている行だけのハイライト生成に変更する                      |

TanStack Virtual には、チャットのスクロール追従に使える機能があります。設定例は次のとおりです。

```ts
const virtualizer = useVirtualizer({
  count: entries.length,
  getScrollElement: () => conversation.current,
  getItemKey: (index) => entries[index].key,
  estimateSize: () => 180,
  overscan: 5,
  anchorTo: "end",
  followOnAppend: true,
  scrollEndThreshold: 80,
});
```

`anchorTo: "end"` と `followOnAppend` は、ストリーミング中の末尾追従と、過去ログを読んでいる際の位置保持を支援します。可変高さのメッセージには `measureElement` も必要です。

`ChatConversation.tsx` は、メッセージの下に承認・進行状態なども配置しています。TanStack Virtual の追従機能を使う場合も、スクロール位置を管理する責務は一か所に集約するのが安全です。

## ほかの選択肢との比較

| 方式                         | メモリ           | 検索改修 | 評価        |
| -------------------------- | ------------- | ---- | --------- |
| 検索中は仮想化を無効化                 | 検索開始時に急増する可能性 | 小    | 短い履歴なら可   |
| `content-visibility: auto` | DOM を全件保持      | 小    | 描画負荷の削減向け |
| データ検索＋仮想化                  | 描画する DOM を限定できる   | 中    | 最も推奨    |

`content-visibility: auto` は画面外のレイアウトや描画を省略でき、標準のページ内検索も利用できます。ただし DOM や React コンポーネントの保持自体は減らないので、今回のメモリ対策としては不十分です。

## 実装の順序

最初に `messageTimeline()` を共通のデータモデルへ切り出し、描画と検索が同じ `entries` を参照できるようにすると整理しやすいです。

続いて TanStack Virtual を導入し、既存の検索バーは維持したまま、DOM を走査する検索から元データを直接検索する処理へ移行します。検索時のハイライト生成だけ、DOM を使う形で残します。

最後に、ツールカードの開閉状態・スクロール追従・履歴復元を調整します。

仮想化しても、`ChatState` が保持するメッセージ本文や巨大なツール出力そのもののメモリは減りません。それでも、多数の Markdown 要素やツールカードを React のコンポーネントや DOM として保持せずに済む効果は期待できます。

この構成なら、検索中も仮想化を維持し、画面外の検索結果へも移動できると考えられます。Nerita では、全件の DOM を描画する方式に戻すより、この分離設計を推奨します。
