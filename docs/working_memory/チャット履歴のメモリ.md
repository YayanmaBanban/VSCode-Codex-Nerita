## 描画・検索を変更する際の設計条件

- 描画と検索は同じ時系列と行 ID を参照する。検索中も仮想化を継続し、検索結果には一致位置だけを保存する。DOM Range はマウント中の行に限定し、行が外れると `CSS.highlights` からも解放する。
- 末尾への追従は、承認・進行状態も含めて既存の会話スクロール制御に集約する。TanStack Virtual 側の行追加時の追従を同時に有効化しない。
- ツールの開閉状態は行 ID に対応付けて保持する。画面外の本文や取得済みの詳細出力は保持せず、戻ったときに再マウントする。
- 表示先の変更では、会話 ID・行 ID・画面内の上端位置・末尾かどうかを Host 経由で保存する。幅変更後は古い高さキャッシュを破棄し、表示中の行も再計測する。
- 検索は、Markdown 原文、受信済みのツール名・正規化した本文・出力プレビュー、エージェント名などを対象にする。未取得の詳細出力は検索しない。Markdown 記号を含む原文の位置と表示文字の位置は、厳密には対応付けていない。移動後のハイライトは描画済み文字への一致から作る。装飾をまたぐ検索や原文の位置との厳密な対応が必要になった場合は、Markdown の解析結果から検索文字と描画位置の対応を作る。
- 仮想化は行単位である。単一メッセージの本文が極端に大きい場合や、本文を開いたカードが画面内にある場合は、その行全体を描画する。次の性能調査では全履歴の行数と、表示中の単一行の大きさを分けて扱う。

## 仮想化前の比較結果

閉じたツール本文を遅延描画・解放する修正を含む本番 VSIX を、VS Code 1.141.0 の専用プロファイルで計測した。対象は約25.6 MB の履歴で、復元後は発言73件・ツール670件。Webview の表示幅は290px、暗色テーマ。本文・ツール出力を保持したコピーを使い、保存済みの環境と設定の作業場所だけを専用ワークスペースに合わせた。

GC を途中に挟まない3回の表示・クリアでは、Webview のワーキングセットは表示前150 MiB、表示中374〜422 MiB だった。3回目のクリア直後は422 MiB だったが、約18秒後には自然な GC で204 MiB、JS ヒープ17 MiB、DOM 214個まで下がった。

別の3回の計測では、各段階で GC 後の値も採取した。Webview のワーキングセットは表示前144 MiB、表示中277〜285 MiB、クリア後193〜205 MiB だった。表示中の JS ヒープは50.2〜50.9 MiB、ブラウザー管理側のヒープは約38 MiB、DOM は12,226個。クリア後の JS ヒープは16.3〜16.9 MiB、DOM は毎回214個だった。閉じたツール本文は通常操作の計測で0件だった。

同じ履歴を3回開いた範囲では、クリア後に履歴全体が積み上がる傾向は確認していない。ただし、初回表示前とクリア後のワーキングセットの差（約50〜60 MiB）の内訳は未特定。DOM 以外のキャッシュや確保済みメモリの影響を含む可能性があるため、差だけをリークと断定しない。

Extension Host は計測用 Playwright ドライバーを含む。通常操作でのワーキングセットは表示前268 MiB、表示中320〜324 MiB、クリア後の待機で224 MiB だった。通常環境との絶対値の比較には使わない。Codex プロセスは62 MiB から約99 MiB に増え、ビューのクリア後も残った。この増加は Webview の描画最適化とは別に扱う。

## 継続して確認する点

- 表示中の単一行の描画と、`ChatState` が保持する元データは仮想化の対象外。追加の削減が必要になった場合は、それぞれを別に計測する。
- ツールチップ共有の単独効果はまだ計測していない。上記の数字だけでは、ツールチップが保持するメモリ量を切り分けられない。
- GC 後の計測と通常操作の計測を分ける。途中の強制 GC は次の操作の状態にも影響する。製品への強制 GC の導入を解決策にはしない。
