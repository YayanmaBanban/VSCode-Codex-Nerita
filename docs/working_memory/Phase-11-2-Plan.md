# Phase 11-2 実装計画：Workspace Trust / External Code Trust

2026-09-26 作成。フェーズ仕様と現行ソースを照合した、着手時点の実装計画。

追記：着手後の実装範囲・検証・残る制限は [実装記録](Phase-11-2-Implementation.md) を参照する。

## 目的と基本方針

Host が root 単位の信頼状態を保持し、未信頼のコード実行を Approval Guard より前で拒否する。実行経路は Trust → Approval Guard → Sandbox とする。Trust による承認や隔離の省略は認めない。

- 未登録・外部取得・状態不整合・解決失敗は `untrusted` とする。
- 昇格と取消しはユーザーの明示操作だけで行う。モデル向けの昇格ツールを提供しない。
- 未信頼の対象には、Host が実装を把握する read / ls / grep / find を許可する。既存の秘密情報保護と読取り範囲の制限は維持する。
- 初期実装の未信頼対象への write / edit は deny を選ぶ。取得専用アダプターによる外部キャッシュの作成とは区別する。
- Shell / test / lint / build / install / script / 未分類の実行ツールは deny とし、Jev や人の承認へ送らない。
- Workspace Trust と Pi Extension Trust は別々に必要とする。Trust は認証情報の利用許可を与えない。

## 現行実装との差分

パスはリポジトリルートを基準とする。

| 現状                                                                                     | 計画への反映                                                    |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `package.json` の `untrustedWorkspaces.supported` は false                               | ガード完成後に制限付き対応へ変更する。先に起動制限を解除しない  |
| `src/extension/workspace.ts` は未信頼と複数 root を拒否する                              | ローカルパス検証、root 選択、信頼判定を分ける                   |
| `src/extension/backends/createBackend.ts` は両バックエンドで同じ入口を使う               | Pi の読取り接続を追加し、Codex の未対応経路を誤って開放しない   |
| `ApprovalGuard.ts` は Guardrails と Jev を呼び出す                                       | 共通入口の先頭に Trust Gate を追加する                          |
| `ApprovedToolCall.ts` は要求固定・一回限りの許可・取消しを実装済み                       | Trust の世代と取消しシグナルを結び付け、実行直前にも再検査する  |
| `PiExtensionTrust.ts` はユーザー設定の単一ファイルと Workspace 全体の boolean を検査する | 拡張の実体が属する root ごとの Trust に変更する                 |
| `PiResources.ts` は拡張の自動発見を無効化している                                        | この既定を維持し、ロード前に root の Trust を評価する           |
| `WorkspacePathPolicy.ts` は実体パスを解決するが、Windows の UNC を拒否する               | 正規化処理を共用する。UNC 対応は既存ポリシーとの共同変更が必要  |
| 外部取得元の登録処理は Pi の製品コードに見当たらない                                     | `pi-web-access` の取得処理を調査し、Host 管理の登録境界を設ける |

## 実装単位と順序

### 1. 信頼の正本とパス判定

`src/extension/security/trust/` に型、Store、Policy、Resolver、ExternalOriginRegistry を追加する。構成の詳細はディレクトリ構成ガイドに従う。

- Store は Extension Host の永続領域を使用し、形式の版、canonical root、状態、変更元、更新時刻を保持する。
- 初回登録は untrusted。既存の VS Code Trust を無条件に全 root へコピーしない。初回の明示操作で対象 root を登録する方針を初期案とする。
- VS Code が制限モードなら、保存済みの Nerita Trust があっても実行を許可しない。
- 明示登録した外部 root を親 root の信頼より優先する。複数対象では1つでも未信頼なら実行を拒否する。
- Windows の大文字小文字、区切り、境界、`..`、symlink、junction を既存のパス規則と一致させる。root の実体変更も再検査する。
- UNC は独立した検証対象とする。対応完了までは拒否し、未対応を信頼済みへ読み替えない。仕様の UNC 条件は未完了として残す。
- Store の破損・読込み失敗時は未信頼とする。昇格は永続化の成功後に反映する。取消しの保存に失敗した場合も実行を止め、再起動時の再信頼を防ぐ処理を設計する。

完了条件：再起動、破損、ネストした外部 root、複数 root、パス別名について単体検証が通る。

### 2. 共通 Trust Gate と承認の失効

- `ApprovalGuard.ts` の先頭で、Host が確定した capability、cwd、対象パス、origin を評価する。ツール名やモデルから渡された trust 値を信頼しない。
- `PiPowerShellTool.ts`、ファイルツール、拡張ツール、Host Shell の各入口を接続する。
- `ApprovedToolCall.ts` に信頼判定時の世代を結び付ける。取消しで待機中の承認と発行済みの未使用許可を失効させる。
- Executor の実行直前に、世代・実体パス・対象 root を確認する。取消しと実行が競合する場合も古い許可を消費させない。
- 既に実行中の処理は既存の取消し経路で停止を要求する。実行済みの副作用の巻戻しは保証しない。

完了条件：未信頼での拒否時に Jev 呼出し、人の承認、プロセス起動、書込みがすべて0件になる。

### 3. 制限モードとユーザー操作

- Pi は未信頼でも読取り用セッションを作成可能とする。接続には Shell の準備や workspace-local コードのロードを要求しない。
- multi-root では会話の cwd を明示選択し、先頭 root を暗黙に採用しない。
- まず Command Palette の Trust / Revoke と状態表示を実装し、Chat header の badge と説明を同じ Host 状態へ接続する。
- 共有プロトコルには状態表示とユーザー操作の要求だけを定義する。Host が現在の root を再解決し、昇格時はネイティブダイアログで確認する。Webview のメッセージだけで昇格させない。
- 確認では対象 root と出所、実行可能になる操作、Approval と Sandbox が引き続き必要であることを表示する。
- Codex は内部の全実行をこの共通ガードが覆うとは限らない。初期計画では未信頼接続を拒否し、root ごとの制約を保証できない構成も拒否する。両バックエンドの完全対応とは扱わない。

完了条件：未信頼で読取りができ、モデル経由で昇格できず、取消しが画面と実行可否に即時反映される。

### 4. 外部取得物と実行対象の追跡

- 導入済み `pi-web-access` の取得・clone・キャッシュ・子プロセス起動を調査し、取得先を Host が確定できるアダプターを設計する。
- 外部取得先を専用 root として事前に未信頼登録し、取得成功後に origin を確定する。通知欠落時も登録前の内容を実行可能にしない。
- clone / download の出所はツールの自由文出力から判断しない。コピー・移動を Host が扱う場合は由来を引き継ぐ。
- Trusted な cwd から外部スクリプトを呼ぶケースも対象とする。`cd`、絶対パス、`-File`、package の作業先指定を検証する。
- 任意 Shell の変数展開やプログラム内部の参照は、文字列解析だけでは追跡を保証できない。対象を確定できない経路は拒否し、必要な OS 境界を先に検証する。
- 特に Trusted root 内の clone で通知が欠落すると、親 Trust を誤継承する恐れがある。専用取得先への制限または実行時の独立 root 検出が必要であり、未登録 root の既定値だけで解決済みとしない。
- 任意の信頼済み拡張が直接実行する JavaScript は完全隔離の対象外。取得アダプターが安全な分離を保証できない経路は利用不可とし、読み取りツールと自己申告させて許可しない。

完了条件：実際の取得先は読めるが実行できず、ユーザーによる信頼後だけ Approval へ進む。通知欠落、ネスト、外部コード参照の拒否を確認する。

### 5. 拡張・subagent・監査

- workspace-local の拡張はロード前に root の信頼を確認する。取消し時は対象セッションを破棄し、未信頼コードが動き続ける経路を閉じる。
- Host 管理の子と孫、ジョブ、workflow は親の制限と同じ Trust Store を利用する。新規 root は信頼を継承せず、親の取消しも子の未実行要求へ反映する。
- 再接続・履歴再開時は保存された会話状態で信頼を復元せず、Host の最新状態を参照する。
- 初回登録、昇格、取消し、外部 origin、実行拒否、子の root 遷移、拡張ロード拒否を記録する。
- 監査ログには理由コード、root の識別子、時刻、状態の世代を保持する。secret、URL の認証情報、コマンド出力全文は保存しない。

完了条件：親子間の権限非拡大と、未信頼のローカル拡張の未ロードを実 SDK で確認する。

### 6. 結合検証と完了判定

1. 単体：Store、パス、capability、origin、世代変更、永続化失敗、プロトコル不正値。
2. 実 SDK：read / grep 許可、Shell / build / install 拒否、信頼後の毎回承認、取消し、子・孫・ジョブ。
3. Extension Host：制限モード、multi-root、Trust 操作、再起動、バックエンド切替、拡張ロード。
4. Webview：UI レビューガイドに従い、badge、確認、取消し、切断時の表示を確認する。Storybook と実 Host 検証を分ける。
5. Windows：承認後の製品 Sandbox 経由実行、外部書込み、外部コード参照、リンク差替えを確認する。
6. `pnpm check`、関連単体テスト、`pnpm test`、関連する Pi / Sandbox smoke、`pnpm textlint:changed` を変更範囲に応じて実行する。

## 依存関係と未確定事項

- 1 → 2 → 3 の順に実装する。4 の取得処理調査は早期に実施し、外部コードの境界を確定してから外部取得を開放する。5 を接続して6で受け入れる。
- 既存の Sandbox には通信隔離などの制約がある。詳細は [既存検証記録](Sandbox-Approval.md) を参照する。Trust の実装を理由にネットワーク遮断や秘密情報隔離を達成済みとしない。
- UNC の正式対応、Codex 内部の実行ゲート、取得アダプターで捕捉できない経路は、対応可否と拒否条件を実装開始時に確定する。
- 初期案は「未信頼 write / edit は拒否」「既存 Trust の一括移行なし」「Pi を先行対応」。これらは仕様の選択肢・現行制約を踏まえた提案である。
- Quarantine、LLM による信頼昇格、任意拡張 JavaScript の完全隔離は対象外。

## 受入基準

- [ ] root ごとの状態を Host に永続化でき、未知の対象は未信頼となる。
- [ ] 人の明示操作だけで昇格し、取消しが待機中・未実行の許可を失効させる。
- [ ] 未信頼の実行要求が Jev / Approval / Executor に到達しない。
- [ ] 信頼済みでも Approval と Sandbox を通る。
- [ ] 外部取得物、複数 root、子の root に親 Trust を誤継承しない。
- [ ] 読取り、ローカル拡張ロード制限、監査、再起動、障害時の拒否を確認する。
- [ ] UNC、Codex、OS 隔離について未完了の条件を明示し、仕様全体の完了と混同しない。
