# Pi の HTTP 通信と個人情報保護

## 現在の設計範囲

`pi-web-access` による直接のページ取得では、ユーザー設定 `web-search.json` に明示された `fetchContent.userAgent` を優先する。未指定・null・空白だけの場合は、他の項目を保持して `Nerita/1.0` を補う。明示された値にはメールアドレスが含まれていても、ユーザーの指定として扱う。Nerita は `PiWebTrust.ts` で実行前と承認後に設定内容が接続時と一致することを検査する。設定を修正した後は再接続が必要になる。

グローバル設定がない場合は UA 入りの設定を自動生成する。既存ファイルへの追記は、読み取り時から内容が変わっていないことを確認してから一時ファイルで置換する。明示済みの UA があるファイルは書き換えない。導入済み `pi-web-access` はワークスペース設定を読み込まないため、ユーザーは Fork を伴うワークスペース対応を見送り、グローバルへの自動生成を選択した。今後ワークスペース設定に対応する場合は、Nerita の検査対象と Web 拡張が実際に読み込む設定先を一致させる必要がある。

これは、信頼済み外部拡張の設定に対する検査であり、すべての HTTP 通信のヘッダーを書き換える仕組みではない。検索プロバイダーがサーバー側で取得するページ、別の MCP、Git やブラウザーなどの取得経路には同じ UA の強制を保証しない。任意コードを実行できる拡張は、設定ファイルの検査だけではネットワークから隔離できない。

## Pi のシェルで適用する範囲

ネットワークを使える Pi の `powershell`・`pwsh` では、子シェルの通常のコマンド解決に UA 上書きを追加する。`Invoke-WebRequest`・`Invoke-RestMethod` と既存のエイリアスは、実行時の引数をバインドした後に `UserAgent` と `Headers` 内の UA を置き換える。`curl.exe` と curl エイリアスのないシェルの `curl` は、実行時の引数から UA 指定を取り除き、転送ごとに設定値を適用する。設定値は承認前に固定し、承認後にも照合する。通信禁止のシェルは既存の MXC ポリシーを使い、これらのラッパーを追加しない。

PowerShell の標準 cmdlet のパラメーター定義は、解決済みシェルの組み込みモジュールから取得する。Host ではモデルのコマンドを実行しない。Curl の引数を本文やファイル名と取り違えないよう、対象の Curl のヘルプから値を取るオプションを識別する。Curl の既定設定ファイルは無効化し、明示的な設定ファイル・外部ヘッダーファイル・複数行ヘッダー・未対応のオプションは送信前に拒否する。

これは通常コマンドの誤送信対策であり、シェル全体のネットワーク境界ではない。絶対パスの Curl、モジュール修飾した cmdlet、別の実行ファイルや `rtk` などの子プロセスからの通信、ラッパーの再定義には適用できない。Codex のシェルと非 Windows の Host シェルには適用しない。

## 残る検討事項

- PowerShell 7 の製品経路の検証はユーザーの指示で保留する。導入済みの Store 版 7.6.9 は Host で起動できるが、`PowerShellExecutable.ts` は MXC で利用できない MSIX 配置を明示的に除外している。通常版の追加導入、除外の緩和、Host 実行への切替は行わない。再開時は MXC で起動可能な配置を確認する。
- 任意コードによる迂回の防止は、ユーザーの判断で実装対象外とする。絶対パス、モジュール修飾、別プロセス、ラッパーの再定義に対する限界は引き続き明示する。
- 個人情報対策は Web 拡張のツール引数と HTTP MCP の送信要求に接続した。Curl・PowerShell の実行時検査、外部 Web 拡張内で追加される要求、モデルによる氏名・住所の検出は未対応。次節に現在の契約と残る設計をまとめる。
- HTTPS プロキシは将来の対応候補として記録に留める。CONNECT 中継だけでは HTTPS のヘッダー・本文を検査できない。対応を再開する場合は、TLS 終端の要否、CA と秘密鍵の管理、信頼する証明書の範囲、認証や証明書固定との互換性、通信内容の保存禁止を先に設計する。現時点で CA の登録や通信経路の変更は行わない。

## 個人情報の送信対策と拡張方針

### 設定と検出の境界

個別の保護対象の登録はユーザーの判断で廃止した。個人情報を入力するダイアログ、登録一覧、SecretStorage への保存・読み取りは設けない。登録方式は未使用のため、旧データの削除や移行処理も設けない。認証用の資格情報ストレージは別の責務であり、この変更の対象にしない。

設定はワークスペースの `.pi/guardrails.json` の `privacy` に置く。`enabled` は既定で true、`usePiiModel` は false 固定とする。他のガードレールと同様に文書を編集し、「保存して適用」で有効にする。保存しただけの内容や外部からの書換えは自動適用しない。適用済みの設定は既存の `workspaceState` から復元し、復元失敗時は送信を止める。ユーザー共通の別設定とのマージは行わない。

検出は Host 内の `PiPrivacyPatterns.ts` で行う。NFKC で正規化し、代表的な URL・JSON の符号化を展開してから検査する。メールアドレス、日本国内の固定・携帯電話番号、国番号を明示した電話番号、Luhn アルゴリズムによる検査に通るカード番号を候補にする。マイナンバー・免許証・旅券・保険・口座・社員・学籍などの番号は、日時や単なる数字列との誤検出を抑えるため項目名を手掛かりにする。JSON のキーと数値型の値も対象とする。任意の変換や一般的な番号のすべてを網羅する仕組みではない。

PII 検出モデルはユーザーが別途作成する予定のため接続しない。UI ではオフの状態で表示し、変更できないようにする。JSON に true を直接書いた場合もスキーマで拒否する。モデルのダウンロード・推論ライブラリ・Worker は導入しない。氏名・住所などの文脈に依存する検出は未対応である。

### 現在の送信経路

対象は Pi Web ツールの実引数と HTTP MCP の実際の送信要求である。モデルプロバイダーへのプロンプト、Git、ブラウザー操作、任意コードの通信全体を監視する仕組みは含めない。

Web は拡張の所属を確認して検査し、ツール名だけで対象を決定しない。UA は明示した設定値を維持するが、検索語や本文への個人情報送信の許可には流用しない。外部 Web 拡張の内部で追加される要求や変換後の内容は、実引数の検査だけでは保証できない。

HTTP MCP は URL・メソッド・ヘッダーと本文を検査する。64 KiB 以内の UTF-8 テキスト・JSON・フォームを扱い、バイナリー、Content-Encoding 付き本文、上限超過は検査不能として送信前に拒否する。保護を明示的に無効にした場合は追加検査を省く。リダイレクトは既存どおり拒否する。

検出時は通常のツール承認や自動レビューとは別に「今回だけ送信」を求める。承認画面には値や入力のキーを複製せず、送信経路・分類・件数を示す。許可は固定した要求の1回の送信に限り、ガードレールの再適用、入力の変更、Stop、期限切れで失効する。検索サービスの宛先を確定できない要求で個人情報を検出した場合は、1回限りの例外も発行しない。

### 今後の検討

- 独自 PII モデルを接続する際は、検出カテゴリ、学習時と同じ前処理、精度、長文の分割、CPU・メモリー・起動時間を先に確認する。オンの場合だけ遅延読み込みし、推論失敗や取消しで未検査のまま送信するフォールバックを設けない。検査対象や結果を永続保存しない。
- Curl・PowerShell の個人情報検査は未対応。実行時の変数・スプラッティング・ファイル入力を扱う必要があり、コマンド文字列の検査だけで保護済みとしない。登録辞書を廃止したため、正規表現のみならラッパー内での検査も候補になる。Host の共通検出器や将来のモデルを使う場合は、MXC から最小権限で照会できる IPC が必要かを改めて検討する。
- ファイル本文を扱う場合、検査後に元ファイルを読み直さず、検査したスナップショットを送信する。未対応の添付やリダイレクトを保護済みと報告しない。
- HTTPS プロキシと任意コードからの迂回の扱いは、前節の保留・対象外の判断を維持する。

## 検証時の注意

Host の表示情報を分離した際、実機 Webview 全体の受け入れ検証で接続終了が発生した。`tests/vscode/account.cjs` でバックエンドを Codex へ切り替えたところ、期待した認証待ちにならなかった。信頼管理・チャット・Pi 認証・資格情報管理の起動通信と操作には到達している。同じ Codex 版を UI から切り離し、隔離した設定で起動した場合の `initialize` と `account/read` は成功した。実機で接続終了になる原因は未特定であり、全体の受け入れ検証を完了条件にする場合はこの差を調査する。認証待ちの期待を接続エラーへ緩めて成功扱いにしない。

`mxc-pi-shell-web.test.ts` と `mxc-pi.test.ts` を同時に配布検証した際、既存の Host pnpm のタイムアウト検証が失敗した。開始出力を受け取る前に1秒の実行期限に達した。`mxc-pi.test.ts` の単独再実行は成功した。負荷や並列実行との関係は未特定であり、再発する場合は既存の起動・タイムアウト検証の条件を調査する。
