## 基盤の依存関係と入口

- `test:host` は共有パッケージをビルドし、対象を新規の Vitest プロセスへ渡す。全件または結合検証では、本番の `bundlePi` で新しい一時領域へ SDK・ワーカー・WASM を生成する。過去の開発ビルドへ戻らない。
- 配布用 SDK を使う結合検証は `tests/fixtures/piSdk.ts` から読み込む。準備されていなければ失敗する。ビルドの成功は実 Extension Host や VSIX 単体の成功を意味しない。
- `tests/unit/hostSetup.ts` は Node 上での VS Code API の読込み境界。`codexHarness` と `piHarness` は本番の状態管理へ外部応答を注入する既存基盤。SDK 自体を模擬する検証を実 SDK の証拠には使わない。
- `sandboxFixtures`、`trustedPolicy` は一時領域と明示的な信頼の準備。`piHttpMcp` はローカル HTTP、`piScriptedTools` はモデル応答の模擬。新しい担当でも必要な外部境界だけを再利用する。
- 実 Extension Host は `tests/.vscode-test.mjs` と `config/build-vscode-tests.cjs` を使う。Storybook の描画とは分ける。
- `run-vscode-tests.cjs` は毎回新しいプロファイルと拡張領域を用意する。`test:vsix` は再生成した VSIX を一時領域へ展開し、その配布物から起動する。ユーザーの VS Code へインストールしない。必須パッケージの不在やスキップを成功に数えない。
- 明暗の UI シナリオでは、`storyPage.ts` がブラウザーの設定を Storybook のテーマへ接続し、属性と CSS の反映を待つ。明示的なテーマやシステム色の専用検査は、それぞれの指定を使う。
- `test-process.cjs` は新規プロセスの起動と一時領域の回収だけを担当する。準備失敗、起動失敗、時間切れ、ゼロ件を正常な検証として数えない。

## 検出能力と撤去判断

`config/regression-cases.json` に対象実装・注入内容・担当を対応付ける。
`test:regressions` は製品ファイルを編集せず読込み時に注入し、実際の適用を記録する。
通常実行の成功、対象テストの実行、注入後のアサーション失敗をすべて要求する。
変換対象の不一致や構文エラーでは成功しない。通常の `test:host` へ変異設定を引き継がない。

- `modelEffort.test.ts` は `codexSelection` へ統合して削除。再設定で結果を隠さず、切替直後の要求と再起動を観測する。
- `piStorage` の衝突検査を削除。`piStorageLifecycle` が本番の保存切替から拒否通知・非送信・元ファイル保持・修復後の再送・別インスタンスでの復元まで担当する。別保存先へ退避する変異を検出してから撤去した。
- 模擬ツールの名前だけを変える4条件、同じ利用枠不一致の3条件、同じ非 Windows 分岐の3条件、既定値を無視する1条件を削除。実 SDK の配線と Windows の実行境界は別の担当とする。
- サイズ超過時の不正 JSON、同期通知で完了待ちを省ける条件、空配列への `every()` を置き換えた。
- 大きな結果の失敗はテスト基盤と別の製品不具合。秘密除去のために JSON 全体を切り詰めていた処理を修正した。画面やコード実行の出力上限は、それぞれの境界で引き続き適用する。
- MCP の直接戻り値だけを調べる検査を、通知・本番カード変換・JSONL・別の読込みへ置き換えた。表示属性は値を検証し、生の遠隔応答からは引き継がない。表示属性から MCP の展開可否を判断しない。
- `pi-persistence-smoke` の Fork・移動・空履歴の重複検査を削除。元ファイルとモデル文脈の分離は `piStorageLifecycle` が担当する。実プロバイダー形式、保存設定切替、未完了ツールは既存スモークに残す。
- 子起動の未知キー拒否を統合し、`workflowScript` に正常な必須入力を加えた。Fork は未対応入力ではなく親文脈のない接続の拒否へ分離した。ワークフローは実在する別ルートを使い、パス不在との混同を除いた。
- 承認 UI は操作4種と表示4種を代表条件で組み合わせ、明暗で確認する。閉じた推論本文をそのまま検査していた既存シナリオには、開閉操作と状態確認を追加した。

### Windows サンドボックスの受入範囲

2026-10-01 のユーザー指示により、通信禁止でも通信できる挙動は Codex Windows サンドボックスの仕様として扱う。
通信の閉じ込めは、上流追跡にある Docker 対応へ委ねる。Docker による遮断を今回検証したという意味ではない。
Windows の必須条件は、許可範囲外への書込みが拒否されることとする。
外部ファイルの作成・上書き・削除、相対パス、ジャンクション、子孫プロセスの書込み拒否を維持する。
ネットワークの4条件は `observation` として記録し、到達・非到達や観測失敗を受入の合否へ含めない。
通信遮断はフェーズ18の未解決事項から外す。

`test:sandbox` のネットワーク検査は、URL がコマンドのパス検査に拒否され、通信まで進んでいなかった。
信頼済みの一時領域に通信専用の Node スクリプトを置き、通常実行・App Server 直結・本番の実行経路で同じコマンドと環境を比較する形へ変更した。
前段の拒否やタイムアウトだけでは、通信遮断の成功に数えない。

2026-10-01 に Windows 10.0.26200、Codex 0.159.1、`elevated` で実行した。
`networkAccess: false` でも IPv4・IPv6 のループバックと外部 HTTP・HTTPS の4条件すべてで通信できた。
App Server 直結と本番の実行経路がともに終了コード0・`REACHABLE` を返した。これは通信到達の観測結果として残す。
本番の実行処理・通信クライアント・要求型を確認し、通信禁止の値は `command/exec` まで渡されている。
[公式仕様](https://learn.chatgpt.com/docs/app-server)も、この操作をサンドボックス内の実行としている。

読み取り専用の OS 調査では、ファイアウォールの3プロファイルは有効で、サービスも稼働していた。
一方、`codex_sandbox_offline_block_*` の4ルールは `Enabled=True` だった。
実効状態は `PrimaryStatus=Inactive`、`EnforcementStatus=CategoryDisabled` だった。
通信遮断が働かない原因候補だが、この状態を生んだ設定や製品は未確定。OS 設定の変更やサンドボックスの再設定は行っていない。
この OS 状態の原因調査は、今回の受入条件には含めない。
詳細は `apps/vscode-nerita/dist/sandbox-smoke/results.json` に保存した。
通常配置の PowerShell 7 がない条件も未検証として残り、Windows PowerShell の成功で代用しない。
