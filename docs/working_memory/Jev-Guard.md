# 自動レビューと Jev 接続準備

## Pi の自動レビュー実装（2026-10-26）

`ApprovalGuard.ts` の Jev 固定呼び出しを、Host 登録のレビューコンテキストと管理画面の設定を使う処理へ置き換えた。Pi の Agent Manager に「自動レビュー」タブを追加し、承認方法、固定モデル、推論レベル、待ち時間、追加方針を表示する。初期値は手動承認。自動レビューを選んで「保存して適用」した場合にだけ、通常操作の承認省略とモデルへの送信を開始する。

### 設定の保存と有効化

設定はワークスペースごとに VS Code の `workspaceState` へ保存し、プロジェクトのファイルや下書きから自動適用しない。`AutoReviewStore` が設定を保持し、保存成功時に以前の世代の承認・許可を失効させる。下書きの復元、世代の競合、未保存の移動確認は Agent Manager の既存経路を使う。

### 履歴の保存と復元

審査の開始・結果は Pi セッションの `nerita.auto-review.v1` カスタム項目として保存し、既存の `GuardianReview` で表示する。設定タブの「直近の判断」とプロセス内の履歴は削除した。保存対象は秘密値を除いたツール名・作業ディレクトリ・コマンド・パスと、判定、理由、モデル、所要時間に限定し、モデルの会話入力へ追加しない。

同じ審査 ID のカードを更新するため、復元時にもカードが重複しない。審査中の記録だけが残った場合は中断として復元し、審査や実行許可を再開しない。子 Runtime の審査も親セッションへ記録する。承認を省略した通常操作のカードは増やさない。

### 実行前の判定と送信内容

共通ガードは Trust とガードレールの拒否を先に適用する。自動モードでは通常の `write` / `edit` を直接実行するが、起動設定や依存スクリプトなどは審査対象に残す。MXC 内の表示専用コマンドと、構文を限定した表示専用バッチも審査の省略対象とする。バッチは内容のハッシュと祖先ディレクトリの同一性を記録し、MXC の各実行前に再検査する。任意のシェルやプロジェクトのスクリプトを包括的に自動許可する処理は設けていない。

審査対象の操作は、Pi の `ModelRuntime.completeSimple` で作業ツールを付けずに判定する。親 Runtime のユーザー依頼と、出所を区別した証拠、正確な操作を送信する。推論本文、構造化されたツール引数内の環境変数の値、登録済みの秘密値は除外する。長い証拠には省略を明示する。操作全体を含む入力が上限を超える場合は、手動承認へ戻す。

| 判定・状態 | 実行の扱い |
| --- | --- |
| `allow` | 一度限りの許可を発行する |
| `deny` | 実行を拒否する |
| `ask` | 手動承認へ戻す |
| 重大リスク、またはユーザーの承認が不足している高リスク | Host 側でも実行を拒否する |
| 時間切れ・不正応答・通信失敗 | 手動承認へ戻す |
| Stop・設定変更 | 中断する |

子 Runtime は親の信頼 ID に結び付いた設定・レビューモデル・ユーザー依頼を継承し、子のタスクをユーザー承認に昇格させない。MXC の権限やネットワーク許可は自動レビューから変更しない。

### 実装の参照先

- `apps/vscode-nerita/src/extension/security/AutoReviewGuard.ts`：決定論的な検査後に、設定した Pi のレビューモデルへ審査を依頼する。
- `tests/product/auto-review.test.ts` と `tests/product/pi-auto-review.test.ts`：許可・拒否・承認省略・障害・取消しを検証する。Pi SDK への接続も確認する。

### 未検証事項と対象外

未実施なのは、実サービスのモデルごとの判定品質・料金・遅延の評価と、自動レビューを有効にした状態での MXC 実機受け入れ検証。製品経路の検証ではモデル HTTP 境界だけを代替し、設定保存、Pi SDK の推論、ファイルへの副作用、子 Runtime、取消しを確認する。非同期の先読み、低リスク判定のキャッシュ、Codex の内部レビュー専用モデルの利用は実装していない。

## Jev アダプターの状態

以下は独立した Jev アダプターの接続準備の記録。現在の Pi の承認処理からは呼び出さない。将来 Jev を選択肢として追加する場合は、Pi モデルによる自動レビューと同じ入力・取消し・判定契約へ接続し直す必要がある。

### 接続状況

**Jev が準備でき次第、認証を設定し、実サービスで検証する。**

現在はアカウントがないため、仕組みとモックによる検証までを実装した。既定では未接続で、外部への通信は発生しない。API キーの取得・保存・設定画面は未実装。実サービスの応答や判定品質は未確認。

### 接続点

- `apps/vscode-nerita/src/extension/security/JevGuard.ts`：任意の判定器、接続世代、時間切れと取消し、送信する要約。
- `apps/vscode-nerita/src/extension/security/JevClient.ts`：公式の `tool-guard` REST API アダプター。キーを閉包に保持し、固定した HTTPS 接続先だけを使用する。

将来、Host の認証処理から `jevGuard.configure(createJevReviewer(apiKey))` を呼ぶ。解除は `jevGuard.configure()` とする。接続変更は古い世代の判定待ち・承認・実行許可を取り消す。ワークスペースの JSON やエージェント入力から接続を有効化する経路は設けていない。

### Jev 接続時の判定方針

決定論的な拒否では Jev を呼ばない。ワークスペース内の通常の `read` など、承認不要の操作も対象外。承認対象のツール呼び出しだけを判定し、`deny` は許可を発行しない。`allow / confirm / review` は既存の毎回承認を維持する。判定と理由を承認画面に表示し、承認対象の `fingerprint` にも含める。

通信失敗・不正応答・8 秒の時間切れでは `confirm` として人の確認へ戻す。Stop やガードレール変更による取消しでは承認を出さない。生のエラー本文は表示しない。応答サイズは 32KiB に制限する。Jev は実行先ではなく、Sandbox の制限を変更しない。

エディターの「検査」は従来どおりローカルの決定論的な検査のみ。ボタン操作で外部へ情報を送らない。

### アダプターの送信範囲と制約

現段階ではツールの分類、引数の個数、コマンドの有無、固定した制約だけを送る。生のコマンド、ファイル内容、パス、環境変数、任意の拡張ツール名、会話は送らない。ユーザー意図や実際の操作内容を渡していないため、意味的な危険度判定の品質は評価できない。この構造要約は接続準備用であり、十分な意味解析ができる状態とは扱わない。

### Jev の接続時に行う作業

1. 公式 API の契約・利用条件・応答形式を再確認する。
2. VS Code SecretStorage へのキー保存と削除、利用者による明示的な有効化を実装する。認証情報をワークスペースのファイルに置かない。
3. 外部へ送る情報を利用者に提示する。秘密値を除去した操作要約とユーザー意図の扱いを決め、送信への同意を得る。
4. 必要な文脈を含む要約を整備し、無害な専用の検証データで実サービスの判定を検証する。
5. 認証失敗、利用制限、障害、遅延、Stop、切断、子 Runtime からの呼出しを実接続で確認する。
6. 実際の承認画面と Sandbox への受け渡しを確認し、検証結果をこの記録へ追記する。

参考： [Jev 公式 API ドキュメント](https://www.jevai.org/docs)。実装時点では `/api/v1/decisions/tool-guard` と `code / data.decision / data.guidance` の契約を使用した。

## Codex 自動レビューの調査と Pi への適用案（2026-10-26）

以下は実装前の調査と設計判断の根拠。現在の実装範囲と未検証事項は冒頭を参照する。

### 調査した版と役割分担

調査時の `openai/codex` の `main` は `970111f6cb62cc02fe36a82ea7d71b37a2889c97`（コミット日時は 2026-10-23 UTC）。指定された `codex-rs/ext/guardian-reviewer/src` は現行の同期レビューの共通処理であり、旧実装として削除されてはいない。ただし、承認を必要とする条件や、非同期判定を使う条件は別領域にある。

- `core/src/exec_policy.rs`：実行ポリシー、危険コマンド、Sandbox の有無、権限拡張要求から、実行・承認・拒否を振り分ける。通常の `on-request` では、危険と判定されず権限拡張も要求していないコマンドを Sandbox 内で実行できる。HelloWorld という出力文字列を特別扱いしているわけではない。
- `core/src/apply_patch.rs`：パッチの権限検査で自動許可・承認・拒否を分ける。
- `core/src/tools/orchestrator.rs`：承認不要なら実行し、承認が必要なら `core/src/tools/approvals.rs` へ渡す。ただし `strict_auto_review` では省略対象も承認経路へ渡す。
- `ext/guardian-reviewer/src`：審査先の選択、同期審査、再試行、期限、構造化出力、結果通知、拒否の反復停止を担当する。Host が実際の操作と証拠を結び付け、実行を制御する。
- `ext/guardian-v2/src/async_scorer/approval.rs`：設定とモデルのポリシーに応じて非同期の低リスク判定を再利用する。権限・文脈の一致、有効な判定、遅れの上限などを確認し、不足・高リスク・権限変更・再試行では同期審査へ送る。画面に同期レビューが出ないことだけでは、モデル判定が一度も動いていないとは断定できない。
- `ext/guardian-v3/src/lib.rs`：この版では永続的な証拠保存の接続口。ソースのコメント上、バックグラウンド処理やモデルツールの公開はまだ担当していない。

レビュー入力は、実行予定の正確な操作と、発言者を区別した会話・ツール証拠。ユーザーの依頼・承認と、ツール出力やファイル内の指示を混同しない。レビュー結果は `outcome`（allow / deny）、危険度、ユーザー承認の強さ、理由。レビュー実行環境は読み取り専用で、再帰的な承認を起こさない。

専用レビュー用モデルはプロバイダーのカタログやモデルメタデータから選ぶ。利用できなければ親モデルへ戻る経路がある。Pi から同一の内部モデルを利用できることや、別モデルで同等の判定品質が得られることは確認できていない。Rust クレートは Codex 内部の複数のクレートに依存するため、そのまま Pi の npm ライブラリとして取り込む構成には向かない。

### 調査時点の Nerita との差

調査時点では、`ApprovalGuard.ts` の `assessToolCall` に毎回承認があった。`GuardrailEvaluator.ts` の `write` / `edit` と拡張ツール、`GuardrailCommands.ts` の Shell も毎回承認を要求していた。いずれか1か所だけを変えても、他の箇所の承認は残る構成だった。

`ToolCall` には正確な引数・実行コマンド・対象ファイルのスナップショット・cwd・権限があるが、ユーザーの依頼や会話の証拠はない。既存の `summarizeJevCall` は値を伏せた構造情報しか渡さないため、自動許可の根拠にはできない。`reviewJevIfNeeded` の `allow` も人の承認を省略しない。

次の仕組みは再利用できる。

- `ApprovedToolCall.ts` の入力固定、fingerprint、一度限りの許可。
- `FileSnapshot.ts` と `PiFileTools.ts` のファイル内容・リンク先・既存祖先の再検査。
- `ApprovalGuard.ts` の Trust、ガードレール世代、Stop に結び付いた取消し。
- `MxcExecutor.ts` の実行境界と、MXC の権限・ネットワーク設定。
- `PiHandoffGeneration.ts` の `ModelRuntime.completeSimple` による、既存認証とモデルを使ったツールなし推論。初期のレビュー実装では、新たな作業エージェントを起動する必要はない。

### 推奨する実行順序

1. Trust・親から継承した権限上限・固定保護・組み込みと追加ルールを検査する。明示的な拒否はモデルへ渡さない。
2. 保護対象に該当せず、確認済みの実行境界内に収まる通常操作は、モデルによるレビューや人の承認を経ずに実行する。初期候補は通常ファイルの `read` / `ls` と、許可範囲内の限定的な `write` / `edit`。
3. 組み込み／追加ルールの承認対象、危険操作、未知の実行内容、Host 実行、権限や接続先の変更を自動レビューへ渡す。通常操作を理由とする `ask` と、明示ルールによる `ask` を区別する。
4. レビューが承認した場合は Host が同じ操作に一度限りの許可を発行する。拒否なら理由を返す。情報不足・通信障害・時間切れなら実行を保留し、人の承認へ戻す。Stop は実行を中断する。これは Pi 向けの案であり、Codex の障害時動作の完全な複製ではない。
5. 実行直前に操作・対象ファイル・設定世代を再確認する。拡大した Sandbox 権限やネットワーク許可で再実行する場合は新たな審査対象にする。

バッチの「作成」と「実行」は分ける。ワークスペース内で新しい通常ファイルを作る処理と、既存ファイルを上書きする処理も分ける。`.bat` という拡張子、短い入力、`echo` という部分文字列だけを理由に任意の実行を許可しない。作成したスクリプトの実行を省略対象にするなら、内容とハッシュを確認し、対応する構文を限定した静的解析が必要。未知のスクリプトやシェル展開はレビューへ送る。MXC は範囲内のファイルの削除・破壊まで防ぐ仕組みではないため、Sandbox 内という条件だけで組み込みの危険操作検査を省略しない。

最初は同期レビューと直接実行の振り分けを実装する。非同期分類の先読みや、スレッド全体の低リスク判定の再利用は後段とする。将来キャッシュする場合も、同じコマンド文字列だけでは再利用せず、ユーザー承認の更新、対象スクリプト・ファイルのハッシュ、実行権限、設定世代を照合する。

### 「自動レビュー」タブの内容案

Pi 選択時だけ表示し、既存の `TabBar` と未保存変更の保護へ接続する。通常エージェントの一覧へレビュー役を追加すると、モデルによる呼び出しや編集と混同するため、Host 専用の設定として扱う。

| 項目 | 初期案 |
| --- | --- |
| 動作 | 手動承認 / 自動レビュー |
| レビューモデル | 利用可能な Pi のモデルから固定選択。現在のモデル追従は補助選択肢 |
| 推論レベル | 選択モデルが対応する値だけ表示 |
| 審査対象 | 機密アクセス、危険コマンド、未知の操作、権限変更など。通常操作は省略することを説明 |
| 判断方針 | 組み込みの標準方針を表示。追加指示は標準方針と固定保護を弱められない形で扱う |
| 送信内容 | ユーザー依頼・操作・差分・関連証拠の送信範囲と除外対象を表示 |
| 障害時 | 実行を保留して手動承認へ戻す。自動許可は設けない |
| 履歴 | 操作、直接実行／自動承認／拒否／確認待ち／時間切れ、理由、モデル、所要時間 |

表示場所と設定の信頼境界は別。セキュリティを緩めるモード・モデル・追加方針の変更を、Git から取得したプロジェクト設定だけで自動適用しない。利用者側の信頼済み設定を初期案とし、プロジェクトごとの設定を設ける場合は専用 UI での明示的な適用を必要とする。子 Runtime は親の方針を継承し、子の入力から緩和できないようにする。

### 実装前に検証する条件

HelloWorld の新規作成と MXC 内での実行、通常の編集、破壊的削除、機密情報の外部送信、未知の拡張ツールを分けて評価する。許可後のスクリプト差し替え、設定変更、子 Runtime、Stop、障害、悪意のあるツール出力を含め、呼び出し省略の精度と誤許可を検証する。Jev の実サービスは未評価のため、Pi のモデルによるレビューと比較する場合も同じ評価データを使う。
