# Testing policy

テストの目的は、実装詳細を固定することではなく、ユーザーから見える仕様・安全性・重要な回帰を検出することです。

## 基本方針

- 新しい実装を追加したからという理由だけで、新しいテストを追加しない。
- まず既存テストで対象仕様が十分に保護されているか確認する。
- 既存テストを拡張できる場合は、新しいテストファイルや類似テストを増やさない。
- 同じ仕様を unit / integration / smoke の複数層で重複して検証しない。
- 1つの仕様について、原則として「その仕様を所有するテスト」を1か所にする。
- テスト件数・coverage の増加自体を成果としない。

## テストを追加する条件

新しいテストは、原則として次のいずれかに該当する場合だけ追加する。

1. 過去に実際に発生した不具合の再発防止
2. 外部公開された仕様・プロトコル・schema・設定値の契約
3. データ損失、権限、安全性、Sandbox、Approval、Trust に関わる境界
4. 複雑な状態遷移や分岐で、回帰がコードレビューだけでは検出しにくい箇所
5. 既存テストでは保護されていない重要なユーザー動作

上記に該当しない場合は、テスト追加をデフォルトとしない。

## 実装詳細を固定するテストを避ける

以下は、それ自体が公開契約でない限りテストしない。

- private/internal な関数の呼び出し順序
- 内部クラス構成
- ファイル分割方法
- import 元
- 中間オブジェクトの完全一致
- DOM の不要な内部構造
- exact mock call count
- 内部処理の細かな呼び出し回数
- ディレクトリ名やファイルパスの重複した固定値
- リファクタしても外部挙動が変わらない実装詳細

たとえば保存先が仕様として重要な場合、正確な保存パスは保存先を所有する contract test 1か所だけで検証する。
Persistence や Smoke test では、保存 → 再起動 → 復元できることを検証し、保存先の文字列を再度固定しない。

## 振る舞いを優先する

可能な限り、内部実装ではなく入力と観測可能な結果を検証する。

悪い例:

```ts
expect(directory).toBe(join(root, ".pi", "sessions"));
```

このパスそのものを検証する必要がないテストでは避ける。

良い例:

```ts
await saveSession();
await reconnect();

expect(await restoredSession()).toEqual(expectedSession);
```

正確な保存パスが契約である場合のみ、専用の contract test で検証する。

### 重複テストを作らない

変更前に、対象仕様について以下を検索する。

- `tests/unit`
- smoke tests
- integration tests
- VS Code extension tests
- Storybook / Playwright tests

既に同じ失敗を検出できるテストが存在する場合、新しいテストを追加しない。

複数テストが同じ定数・パス・内部構造を直接 assert している場合は、新しい重複を追加せず、必要なら既存テストを整理する。

## テスト変更時の判断

実装変更によって既存テストが失敗した場合、すぐに実装を元へ戻さない。

まず以下を判断する。

- 本当にユーザー仕様が壊れたのか
- 意図した仕様変更によってテストが古くなっただけか
- テストが内部実装へ過剰に結合していないか
- 同じ仕様を複数テストが重複して固定していないか

意図したリファクタで外部挙動が変わっていない場合は、実装ではなくテスト側の修正・削除を検討する。

## 最小テスト原則

変更に必要なテストは最小限にする。

目安:

- pure function / mapper:
  代表ケース + 重要な境界だけ
- bug fix:
  原則1つの regression test
- contract:
  契約を所有する1つの test suite
- persistence:
  round-trip を優先
- UI:
  ユーザー操作・表示結果を優先
- safety:
  許可されるケースと拒否されるケースを明示的に検証

単純な実装について入力値の組み合わせを網羅的に列挙しない。

## 実装完了前の確認

新しいテストを追加する前に、次を自問する。

1. このテストはどの具体的な回帰を防ぐか？
2. 既存テストで同じ回帰を検出できないか？
3. リファクタだけで壊れるテストになっていないか？
4. 外部仕様ではなく内部実装を固定していないか？
5. 同じ仕様を別レイヤーでも assert していないか？

明確に答えられない場合、新しいテストは追加しない。
