# テスト方針

テストの追加・変更・整理に適用する。目的は、少ない変更コストで製品の振る舞い・契約・安全性の回帰を検出すること。件数やカバレッジの増減を成果としない。

## 追加・維持の判断

「このテストがなければ、どの具体的な不具合を見逃すか」で判断する。
対象仕様の既存テストを確認し、同じ回帰を検出できるなら既存の担当テストを使う。
担当テストは、その仕様を直接検証するテストまたはテスト群を指す。

- 追加する: 未保護の重要なユーザー動作、外部契約、安全境界、複雑な状態遷移、実際に起きた不具合の再発防止。
- 既存の担当テストを拡張する: 同じ仕様の境界値や固有の失敗経路。代表値・境界値・過去の回帰を選ぶ。
- 削除・統合する: 固有の回帰を説明できない重複、外部挙動を変えないリファクタだけで壊れるアサーション。

新しい実装やファイルに対応するという理由だけでは、テストを追加しない。
局所修正では関連するテストを調べればよく、全スイートの監査を毎回行う必要はない。

## 仕様の担当テストとレイヤー

1仕様につき原則1つの担当テストを置く。上位層には、接続や実環境でしか検出できない失敗を担当させる。

| 種別 | 主な責任 |
| --- | --- |
| 単体テスト | ロジック、変換、状態遷移の入力と結果 |
| 契約テスト | スキーマ、プロトコル、公開 API、設定・保存形式の境界 |
| 結合テスト | コンポーネント間の接続、実 SDK、保存と独立した再起動後の復元 |
| スモークテスト | 起動・主要機能・配布物が実環境で動くこと |
| e2e / UI | 重要なユーザー操作と表示結果 |

正確な保存パスは保存先の契約テストで検証する。永続化やスモークテストでは保存・再起動・復元を検証し、パス文字列を重ねて固定しない。
Storybook の描画成功は、Extension Host や実バックエンドとの接続成功を意味しない。
UI の検証方法は、表示・操作を変更するときに [UI レビュー](UI-Review-Guide.md) を参照する。

## アサーションと検証データ

入力と観測可能な結果を優先する。内部クラス・インポート・ファイル分割・中間構造・DOM の入れ子・細かな呼出順や回数は、それ自体が契約の場合だけ固定する。
二重実行や承認迂回を検出する呼出回数は、安全性を守るアサーションとして扱う。

検証データやヘルパーは、準備・後片付け・外部境界のモック・ユーザー操作に使う。
期待値を求めるために本番の判定アルゴリズムを複製しない。
テスト専用の不要なエクスポートや抽象化を本番コードに追加しない。

## 安全性・データ保持

サンドボックス・承認・信頼・ワークスペース外アクセス・シェル・シンボリックリンク・外部コード読込みは、許可と拒否の両方を検証する。
破損したセッションの読込み、復元失敗、会話の分岐では、既存データや現在の会話を失わないことを守る。
これらのテストを削除・統合するときは、保護していた失敗経路を引き継ぐ担当テストを確認する。
SDK の配線、OS の境界、人の承認操作など、異なる境界を検証する複数レイヤーは維持する。
初期化失敗や前段の拒否を、目的の安全境界が機能した証拠にしない。

## 検証と完了

変更の影響に合うテストから実行し、今回の変更による失敗を修正して関連テストを再実行する。
ユーザーが依頼した範囲で、一時検証データだけを使うローカル検証は、その都度の確認を挟まず進める。
実認証・外部サービス・インストールを伴う試験は、必要な環境と依頼の範囲を確認して選ぶ。
実行入口は [package.json](../../package.json) を参照する。

失敗は、製品の回帰、意図した仕様変更、実装への過剰な結合、環境不足に分けて判断する。
成功させるためだけにアサーションを弱めたり、スキップへ変更したりしない。
必要な検証が通ったら完了とし、新たな変更・失敗・未解決の懸念がなければ実行範囲を広げない。
全件実行は、全体整理や共通基盤の変更などで必要な場合、または明示的に依頼された場合に行う。
報告には変更理由、実行結果、残る失敗・未検証範囲を含める。
