# README・Markdown 文書の校正

README、設計文書、利用手順など、段落や見出しを持つ文書を校正する場合に適用する。
コードコメントでは、文書全体の構成に関する基準を適用しない。

## 文体と語尾

README や利用手順などの説明文は「です・ます」調を基本とする。
スキルの指示書とその参照文書は常体に統一する。
コードコメントや既存文書では、周囲の文体との統一を優先する。

同じ文末が3文以上続く場合は、文の統合や段落・箇条書きへの整理を検討する。
これは見直しの目安であり、語尾だけを変えるために断定の強さや文の役割を変えない。
並列の手順や規則では、文末を揃えた方が読みやすい場合もある。

## 読者が必要な情報へ進める構成

- 冒頭では対象、用途、解決する問題を示す。一般論や宣伝的な形容だけの導入は短くする。
- README では既存の目的に合わせ、利用条件、導入、最初の操作、詳しい説明への案内が見つかるか確認する。
- 手順は実行する順序で並べ、説明と読者への操作指示を区別する。
- 前提条件や制限は、それが関係する操作の近くに置く。
- 見出しは内容が分かる名前にする。短い本文を言い直すだけの節や結論は統合する。

全ての文書に同じ章立てを要求しない。情報が不足している場合も、校正だけを理由に新しい仕様や手順を作らない。
コマンド、設定値、対応環境は実ファイルを確認して記述する。確認できない内容は報告する。

## Markdown の構造を保つ

説明のつながりは段落で示し、操作の順序は番号付きリスト、並列の条件は箇条書き、比較は表で示す。
箇条書きの割合や太字の個数には一律の上限を設けない。必要な一覧を文章へ押し込まず、装飾だけの強調を整理する。

コードブロック、インラインコード、リンク先、画像、バッジ、HTML、表の対応関係を保つ。
文章を直す際に、実行例や設定の意味を変えない。記号・空白・コロンは構文や名称の一部か確認する。
見出しを変更した場合は、目次や文書内リンクの参照先も確認する。

## 仕上げの確認

本文を通して読み、同じ情報の繰り返し、唐突な話題の切替、説明されていない用語を確認する。
長文や表を変更した場合は、利用可能なら Markdown のプレビューで改行・リスト・表・コードブロックの表示を確認する。
表示を確認できなかった場合は、構文の確認と区別して報告する。

README の校正が対象に含まれるかは、ユーザーの依頼とリポジトリの指示で判断する。
校正スキルの利用だけを理由に、更新が制限されているファイルを変更しない。
