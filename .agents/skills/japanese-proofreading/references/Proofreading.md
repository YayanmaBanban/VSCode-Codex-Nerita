# 日本語の校正

## 意味を保つ

校正の前後で、次の点が変わっていないか確認する。

- 結論と、その結論を支える条件・因果関係。
- 重要な情報と補足情報の区別、否定や比較の対象。
- 確定した事実、推測、可能性の区別。
- 説明、評価、依頼、予定など、その文が伝える内容の種類。

読みやすくするために、原文や実装から確認できない主体・原因・数値・仕様を補わない。

指示語は指す対象が分かる場合だけ具体化する。情報が不足する場合は、推測で本文を埋めず未確認事項として報告する。

原文と実装が矛盾する場合は、根拠を確認して内容を訂正し、文体の調整とは区別して報告する。

## 曖昧な表現と過剰な装飾を整理する

AI が書いたかどうかを判定するのではなく、読者が操作・状態・理由を理解できるかで判断する。

- `静かに壊れる` などの比喩は、確認できる不具合や状態に置き換える。通知やエラーが出ないと確認できなければ、その仕様を追加しない。
- `地味に効く`・`時間を溶かす` などは、効果や所要時間が分かる表現にする。原文にある評価や困りごとまで消さない。
- 「重要なのは」などの前置きや、同じ内容を繰り返す補足は、削っても意味が通る場合に整理する。
- 否定や対比が誤解を防いでいる場合は残す。否定した選択肢を、追加の選択肢や優先順位の低い候補へ変えない。
- 抽象的な名詞や造語を重ねず、誰が何をするのか、何がどう変わるのかを書く。

技術用語、定着した慣用句、必要な強調を一律に消さない。

文長・文末・記号の数を揃えるためだけの言い換えは避ける。

識別子のバッククォートや和欧文間の空白は、既存の技術文書の表記に合わせる。

## AI に特有の不自然な表現の検出

`config/textlint-slop.json` で、日本語の表現を英単語辞書と分けて管理する。

- `ai-slop-pattern` は高確度の不自然な構文を表し、通常の静的検査も失敗させる。`suggestion` は自動置換用ではなく、何を具体化すべきかを示す。
- `ai-slop` は文脈確認が必要な語や表現を表し、単独では失敗させない。正当な技術用語や必要な説明なら維持できる。

いずれも候補ファイルの元テキスト・行番号から元ファイルと周辺コードを読む。警告の除去を目的にせず、主張・重要度・確実さ・説明や依頼などの文の役割を保つ。実装にない主体・原因・条件・仕様は補わない。

`した瞬間` は厳密な時点を説明する場合もあるため、レビュー候補とする。`まで踏み込む` は実装・処理・仕様・コード・設計を対象とする構文に限定する。解像度・実測・照合・装置などは単語だけで検出しない。

文法・箇条書き・強調・誇張表現など、既存の textlint のプリセットが扱う指摘はそちらに任せる。AI が書いた確率の判定や、一括置換は行わない。

## 読点と文の区切り

- 読点を使って文の構造や意味の区切りを明確にする。単なる強調や間を作る目的では挿入しない。
- 「前提を、確認する」のように、密接につながる語句を不必要に分断しない。「ここでは、設定する」のような短い文でも、区切る必要がなければ読点を省く。
- 読点が多くなる場合は、対象・条件・処理・結果の関係を整理し、意味を保って文を分けられないか検討する。
- 誤読を防ぐ読点や、条件・補足の範囲を明確にする読点は残す。読点の数だけを基準に削除しない。

## textlint の修正方針

textlint が英語・識別子と日本語の不自然な接続を報告した場合、単純な文字置換ではなく、周囲のコードと文章を確認して修正する。

コード上の識別子、型名、関数名、API 名、コマンド名、製品名、ライブラリ名、プロトコル名などは、実際の名称である場合は翻訳しない。

文章中の技術用語で、一般的な日本語訳が定着しているものは、自然な日本語へ置き換える。

<!-- texlint-ignore-start -->

例を示す。

    canonical化
    → 正規化

    retryする
    → 再試行する

    disposeする
    → 破棄する

    Tool名
    → ツール名

識別子の場合は次のように表記する。

    Controllerが
    → `Controller` が

    signalは
    → `signal` は

    pwshが
    → `pwsh` が

<!-- texlint-ignore-end-->

textlint の警告を機械的に修正せず、コード上の意味を確認してから修正する。

## 静的な英単語チェック

日本語の文章でバッククォートに囲まれていない英単語も、通常の textlint 実行時に確認する。
設定はスキル内の `config/textlint-terms.json` に置く。

- `preferredJapanese`: 一般的な日本語表現へ置き換えたい語と推奨表記。最優先で判定する。
- `technicalDictionary`: SHA を固定した CSpell の技術辞書ソース。一般英語辞書は使わない。
- `allowedEnglish`: 辞書やプロジェクト情報でも判断できない固有名詞などの例外。

CSpell の技術辞書は保存済みの辞書が利用できない場合に取得し、抽出した語彙を `.textlint-cache/technical-terms.json` に保存する。

取得元のリビジョンを固定するため、上流更新だけで lint 結果は変わらない。

ネットワークから取得できない場合は警告を表示し、外部辞書なしでレビュー候補を出す。

- `package.json` の依存パッケージ、実行コマンド、スクリプト中のパスもプロジェクト語彙として自動許可する。
- CSpell の software-terms 本体と Node 辞書も使用し、一般英語辞書は使用しない。
- `CPU`、`ESM`、`CJS`、`WASM`、`SHA-256` のような大文字の技術略語も自動許可する。
- `320px`、`32KiB`、`2 MiB` などの数値と単位、キーボードショートカット、I/O 表記、バージョン番号は英単語レビューの対象外とする。
- `config.toml`、`guardrails.json`、`models-manager/models.json` のようなファイル名・パスも対象外とする。
- `npm:`、`node_modules`、`manifest.name`・`metadata.name`、スコープ付きパッケージ名、バージョン番号と併記された名前からパッケージ名を自動抽出する。抽出した名前は同じ検査の実行中に技術語として扱う。ハイフンを含むという理由だけで、その語をパッケージ名とは推測しない。
- `ls`、`gh`、`chcp` などの既知コマンド名、`Backspace`、`Tab`、`Undo` などのキー名、`/plan` のようなスラッシュコマンドはレビュー対象外とする。
- 対応言語の抽出処理で収集した識別子がバッククォートに囲まれていない場合は、エラーとして扱う。TypeScript / JavaScript は構文木、Rust はコメントと文字列を除く字句から収集する。
- 識別子として判定する対象は `camelCase`、複合 `PascalCase`、`snake_case` 形式に限る。
- `Plan` や `Tool` のように単語1個で構成される PascalCase は、識別子として自動判定しない。
- `preferredJapanese` は自動許可する語彙や識別子の判定より優先する。`owner` などが辞書やコードに含まれていても、日本語への言い換えを求めるエラーとして報告する。
- 未登録の英単語はレビュー候補として表示するが、それだけではコマンドを失敗させない。
- バッククォート内の識別子、URL、Markdown のリンク先、HTML コメントは英単語チェックから除外する。
- 文書の検査対象から外す範囲は、単独行の `<!-- texlint-ignore-start -->` と `<!-- texlint-ignore-end-->` で囲む。

## 実装と説明の照合

意味のレビューでは、静的検査で警告されなかった文章も含めて、日本語コメント・文字列・JSX 本文を周囲のコードと照合する。

文字列が UI 文言・ログ・エラーメッセージなど人が読む文章かどうかを、周辺コードと利用箇所から判断する。永続化キー・イベント名・プロトコル値・コマンド・パスなど、機械が読む値は文章として機械的に書き換えない。日本語を含むキーもレビュー候補に残るため、修正前に用途を確認する。校正によって製品の動作・保存形式・通信で使う値を変えない。

テンプレートでは、式を挟んだ固定部分を別々に抽出する。式を評価したり、欠けた内容を補って文章を作ったりしない。エスケープシーケンスや JSX の文字参照は展開されないため、表示内容は元コードと照合して確認する。

次の点を確認し、問題があれば修正する。

- 文法的には成立していても意味が不明瞭ではないか
- 実装に存在しない概念をコメント内で作っていないか
- 複数の処理を不自然な造語で圧縮していないか
- 対象・条件・処理・結果の関係が分かるか
- コードを読んだとき、コメントの説明と実装が一致しているか
- 英語を不自然に日本語化していないか
- 一般的な日本語表現へ置き換えられる技術語を、必要性を検討せず英語のまま使っていないか

コード上の実際の操作を具体的な日本語で記述する。

例を示す。

<!-- texlint-ignore-start -->

NG:

    roleを正規化して親上限と交差する。

OK:

    `role` を正規化し、親の `role` で許可された権限との共通部分だけを残す。

<!-- texlint-ignore-end -->
