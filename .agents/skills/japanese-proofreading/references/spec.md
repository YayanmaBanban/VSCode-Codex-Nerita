# 仕様書の校正

実装者が必要な情報を見つけ、意味を理解して実装・検証に使える仕様書へ整える。
[校正ルール](Proofreading.md)と[Markdown 文書のルール](Markdown.md)を併用する。
通常のコードコメントや UI 文言の校正では、この手順を適用しない。

## 判断の基準

[ISO 24495-1:2023](https://www.iso.org/standard/78907.html)のプレインランゲージの考え方を、仕様書へ次のように適用する。

| 原則           | 仕様書で確認すること                                       |
| -------------- | ---------------------------------------------------------- |
| Relevant       | 実装者に必要な情報を優先しているか                         |
| Findable       | 目的・手順・条件・完了基準を探しやすいか                   |
| Understandable | 複雑な説明を分け、条件・処理・結果の関係を明確にしているか |
| Usable         | 実装と検証に使える形で情報を示しているか                   |

短文化そのものを目的にしない。必要な例外や前提を削って短くするより、関係が分かる配置を選ぶ。

[ISO 24495-3:2026](https://www.iso.org/standard/86938.html)は、科学について幅広い読者に伝える文章を対象とする。専門家同士の科学論文を直接の対象とする規格ではない。
ここでは科学的な内容を正確に伝えるための考え方を技術仕様書へ応用し、次の観点を補助指針とする。各項目を規格の条項や認証基準とは扱わない。

| 観点       | 校正時の扱い                                               |
| ---------- | ---------------------------------------------------------- |
| 根拠と主張 | 事実・推測・設計判断を区別する                             |
| 不確実性   | 未検証・未実装・仮説であることを維持する                   |
| 専門用語   | 必要な名称を維持し、理解に必要な説明を確認できる範囲で補う |
| 前提条件   | 比較や結論に必要な条件を、関係する説明の近くに置く         |
| 図表       | 関係を整理し、単位・条件・出典を保持する                   |
| 正確さ     | 因果関係や確実性を原文より強めない                         |

ISO への完全準拠や認証を判定する機能ではない。静的検査の閾値も ISO の規定値ではなく、このスキルの暫定的な見直し基準である。

## 静的検査

対象リポジトリのルートで、校正を依頼された Markdown ファイルまたはフォルダを明示する。

```sh
pnpm --dir .agents/skills/japanese-proofreading spec:lint --root ../../.. docs/example.md
```

このコマンドは文章を書き換えない。仕様書専用の指摘を警告として表示し、`.textlint-cache/spec-lint.json` へファイル名・行・列・ルール ID を保存する。
毎回同じレポートを置き換えるため、別の校正と同時に実行しない。警告だけなら終了コードは0、引数・設定・読込みなどの実行エラーは2になる。
対象を省略したリポジトリ全体の検査は行わない。

| ルール ID              | 検出する候補                                                                         | 初期値    |
| ---------------------- | ------------------------------------------------------------------------------------ | --------- |
| `spec/long-sentence`   | 長い一文。既存の `sentence-length` を再利用する                                      | 100文字超 |
| `spec/long-paragraph`  | 長い段落。箇条書き内の段落は項目側で扱う                                             | 200文字超 |
| `spec/long-list-item`  | 長い箇条書きの項目。子リストの文字数は親へ加算しない                                 | 160文字超 |
| `spec/table-candidate` | 「場合は」など、条件に続く結果の反復。同じ段落内、連続する段落、同じリスト内で数える | 3件以上   |

文字数は空白や Markdown の装飾を除いた本文をコードポイント単位で数える。
コードブロック内の Schema・コマンド、インラインコード、URL、リンク先、複合形式の識別子などは数えない。リンクの表示名や強調した本文は検査する。
技術記述はコードブロックやインラインコードで示す。検出されなかった説明も構成レビューの対象とする。

閾値は `config/.textlintrc.json` の `spec` 設定で変更できる。この設定は `spec:lint` だけが読み、通常の textlint のルールは変更しない。
一度の検査だけ変更する場合は次の引数を使う。

```sh
pnpm --dir .agents/skills/japanese-proofreading spec:lint --root ../../.. --sentence-max 120 --paragraph-max 240 --list-item-max 180 --table-min 4 docs/example.md
```

文字数の閾値は1以上、反復件数は2以上の整数を指定する。
既存の `.textlintignore` と textlint の無効化コメントを再利用する。
範囲の除外には、`<!-- texlint-ignore-start -->` と `<!-- texlint-ignore-end -->` を使う。
例えば `<!-- textlint-disable spec/long-paragraph -->` は指定ルールだけを無効にする。警告を消すためだけに除外を追加しない。

## 校正ワークフロー

### 1. 仕様書 Lint と文章校正

1. 依頼された対象、文書の目的、読者、更新できる元ファイルを確認する。修正前の差分または複製を比較用に確保する。
2. 同じ対象へ `spec:lint` と既存の `textlint:review` を実行する。通常の検査は[全体・指定範囲のコマンド](Cmd-All.md)に従い、引数へ同じ対象を渡す。
3. 仕様書のレポート、既存 textlint の指摘、`review-all.jsonl` と `issues-all.json` を読む。検査処理の失敗と文章への指摘を区別する。
4. 元の文章と周辺の仕様を読み、文法・表記・冗長表現・長文を校正する。検出候補を自動置換の指示とは扱わない。
5. 修正を元ファイルへ直接反映する。

### 2. 構成レビューと構成校正

文書全体の情報の配置、見出し、重複、説明順を確認する。Lint が指摘しなかった箇所も読む。
意味を保てることを確認し、実装者の理解を助ける整理を選ぶ。その結果を元ファイルへ直接反映し、提案だけで終えない。

条件と結果が対応する場合は表にする。各行で条件と処理を対応させ、保存内容や例外を省略しない。
手順と確認項目は分ける。処理の順序は番号付き手順で示し、照合する値や判断基準は別の表や箇条書きにまとめる。

| 元の説明             | 選択できる整理方法         |
| -------------------- | -------------------------- |
| 複数の処理を含む文章 | 文や段落を分割する         |
| 条件と処理の対応     | 条件・処理・例外の表にする |
| 複数の選択肢         | 比較軸を揃えた表にする     |
| 実装・操作の順序     | 番号付き手順にする         |
| 独立した制約         | 箇条書きにする             |
| 複雑な技術説明       | 概要と詳細に分ける         |
| 重複する共通仕様     | 共通契約の参照へ整理する   |

必要なら段落や章を再配置する。表へ整理する際も条件を省略しない。並列の制約には、原文で示されていない実行順序を付けない。
共通契約への参照は実在する参照先と適用範囲を確認し、出典や例外を残す。見出しを変えた場合は目次と文書内リンクも照合する。

### 表・リストへの変換後の整合性確認

文章を表やリストに再構成した場合、元の仕様との対応を確認する。

- 情報の網羅性：元文の条件、処理、結果、例外、禁止事項が欠落していないか。
- 列の一貫性：表の各行が同じ観点を説明しているか。ある行だけ保存内容や結果が省略されていないか。
- 記述間の整合性：手順、表、補足説明で処理や適用条件が矛盾していないか。
- 条件付き処理：一部の条件でしか実行しない処理を、すべての条件で実行するように書き換えていないか。

欠落や矛盾があれば、根拠となる元文や関連仕様を確認して修正する。

根拠がない情報は推測で補わず、未解決事項として報告する。

**構成校正の完了前に、元文との意味の一致を再確認する。**

### 3. 再検査と最終確認

1. 校正した同じ対象へ `spec:lint` と既存の `textlint` を再実行する。
2. 修正前後の差分を確認し、文章と構成の両方が改善されたか読む。
3. 要件・例外・禁止事項、Status・ID・API・Schema・コマンド、処理順序・依存関係・リンクを照合する。
4. 権限・承認条件、参照と更新の基準となるデータ、実装済み・未実装・検証待ちの区別、根拠と確実性が保たれているか確認する。
   校正後も保存内容・例外・承認条件を原文と照合する。表への変換や手順の分割で、保存対象・保存単位・確認時点が変わっていないか確認する。
5. Markdown の表・見出し・リスト・コードブロックを確認する。問題があれば修正と再検査を繰り返す。
6. 対象、文章と構成の修正内容、検査結果、意図して残した警告、未確認事項を簡潔に報告する。

校正作業の経緯、Lint の実行結果、変更件数などは、仕様書本文に追加せず、校正完了時の報告に記載する。

矛盾や根拠の不足は推測で埋めず、該当箇所と確認できない内容を報告する。
Lint の警告を解消しただけでは完了としない。仕様の意味や設計判断は変更しない。

この手順は仕様書の校正依頼時だけ実行する。通常の開発、`pnpm check`、`pnpm lint`、CI に必須検査として追加しない。
