# 仕様書の校正

実装者が仕様を理解し、条件・処理・結果・完了基準を実装と検証に使えるように校正する。
文章・表・構成を変更する一般手順と ISO 24495-1/3 の参考指針は `Prose.md` にまとめる。
この文書では、仕様書固有の Lint と意味保持の確認事項を示す。
通常のコードコメントや UI 文言の校正には、この手順を適用しない。

## 仕様書 Lint

対象リポジトリのルートで、校正を依頼された Markdown ファイルまたはフォルダを明示する。

```powershell
.\.agents\skills\japanese-proofreading\run.cmd spec:lint docs/example.md
```

このコマンドは文章を書き換えない。仕様書専用の指摘を警告として表示し、`.textlint-cache/spec-lint.json` へファイル名・行・列・ルール ID を保存する。
毎回同じレポートを置き換えるため、別の校正と同時に実行しない。
対象を省略したリポジトリ全体の検査は行わない。

|検査結果|終了コード|
|------------------------------------|----------|
|警告だけの場合|0|
|引数・設定・読み込みなどの実行エラー|2|

### ルールと文字数の数え方

|ルール ID|検出する候補|初期値|
|----------------------|------------------------------------------------------------------------------------|---------|
|`spec/long-sentence`|長い一文。既存の `sentence-length` を再利用する|100文字超|
|`spec/long-paragraph`|長い段落。箇条書き内の段落は項目側で扱う|200文字超|
|`spec/long-list-item`|長い箇条書きの項目。子リストの文字数は親へ加算しない|160文字超|
|`spec/table-candidate`|「場合は」など、条件に続く結果の反復。同じ段落内、連続する段落、同じリスト内で数える|3件以上|

文字数は空白や Markdown の装飾を除いた本文をコードポイント単位で数える。
コードブロック内の Schema・コマンド、インラインコード、URL、リンク先、複合形式の識別子などは数えない。リンクの表示名や強調した本文は検査する。
技術記述はコードブロックやインラインコードで示す。検出されなかった説明も構成レビューの対象とする。

### 閾値の変更

閾値は `config/.textlintrc.json` の `spec` 設定で変更できる。この設定は `spec:lint` だけが読み、通常の textlint のルールは変更しない。
一度の検査だけ変更する場合は次の引数を使う。

```powershell
.\.agents\skills\japanese-proofreading\run.cmd spec:lint --sentence-max 120 --paragraph-max 240 --list-item-max 180 --table-min 4 docs/example.md
```

文字数の閾値は1以上、反復件数は2以上の整数を指定する。

### 除外設定

既存の `.textlintignore` と textlint の無効化コメントを再利用する。
範囲の除外には、`<!-- texlint-ignore-start -->` と `<!-- texlint-ignore-end -->` を使う。
例えば `<!-- textlint-disable spec/long-paragraph -->` は指定ルールだけを無効にする。警告を消すためだけに除外を追加しない。

## 仕様書固有の整合性確認

一般的な文章・構成校正は `Prose.md` に従い、次の情報を追加で厳密に照合する。

|対象|校正前後に照合する内容|
|------------------|--------------------------------------------------------------------------------------|
|要件・条件|必須・任意、適用条件、除外条件、例外、禁止事項|
|状態・実装状況|正式な Status・Enum、完了・未実装・未検証、変更できる主体|
|識別子・形式|ID、API、Schema、コマンド、リビジョン、ダイジェスト|
|保存と承認|保存内容・対象・単位、更新範囲、トランザクション境界、確認時点、承認者・承認条件・権限|
|データの参照と更新|参照と更新の基準となるデータ、その優先関係|
|依存と手順|先行条件、順序、停止条件、再実行・復旧の扱い|
|根拠|Source・参照先、根拠の有効性、不確実性|

条件と結果を表へ整理する場合は、各判断の保存内容と利用可否など、必要な比較軸を揃える。
各行で条件・処理・結果・例外を対応させ、判断ごとに更新対象や処理の違いを明確にする。
校正後も保存内容・例外・承認条件を原文と照合する。

元の仕様から決定できないセルは推測で埋めず、未解決事項として報告する。判断の変更を校正扱いしない。

## 仕様書校正の実行順

[Prose.md の校正ワークフロー](Prose.md#校正ワークフロー)を実行し、仕様書では次を追加する。

1. 文章校正の前：通常のレビュー用コマンドに加えて、`spec:lint` を同じ対象へ実行する。`.textlint-cache/spec-lint.json` と通常のレビュー結果を確認する。
2. 構成校正の際：一般的な表・リストへの変換と意味の検証に加えて、[仕様書固有の整合性確認](#仕様書固有の整合性確認)を行う。元ファイルへ直接反映する。
3. 最後の再検査：通常の静的検査に加えて、`spec:lint` を同じ対象へ再実行する。原文から条件や権限の意味が変わっていないか差分で確認する。

Lint の警告をなくしただけでは完了しない。仕様書の意味や設計判断は変更しない。
矛盾や根拠の不足は推測で解消せず、該当箇所と確認できない内容を未解決事項として報告する。
