# 章の役割とつながり

## Arena で役割を引き継ぐ

候補ごとに、読者が抱く疑問（`readerQuestion`）、章が担当する説明（`sectionRole`）、読み終えて分かること（`takeaway`）、次章へ進む理由（`nextBridge`）を短く示す。仕組み、利用できる範囲、使い方など、読者の判断に必要な説明のまとまりを確認する。

部分統合では、採用した要素をユーザーの原文と推薦から確かめる。必要な役割を独立章で維持したか（`kept`）、他章へ統合したか（`merged`）、見送ったか（`omitted`）と、その理由を記録する。必要なら `approvedOutline.sectionRoleDecisions` の各項目に `candidateId`、候補の `sourceHeading`、`sectionRole`、`disposition`、採用先の `sectionId`、`basis` を保存する。見送った役割の `sectionId` は `null` とする。確定構成の各章に上の4項目を保存でき、最後の章は `nextBridge: null` とする。

承認した要素の役割が失われたら `section-role-loss` とする。承認対象に含まれない要素が原因で、完成構成の前後がつながらない場合は `transition-gap` として提案する。たとえば A 案の Markdown 例だけを取り入れた場合に、A 案の仕組み章が承認済みだったとは扱わない。独立章を置く案と、既存章の中で説明を補う案を、読者が探しやすいか、説明が重複するかで比べる。章の追加や章順の大きな変更で承認範囲が変わるときは、構成承認へ戻す。

## 初稿と改稿でつながりを読む

隣接する章を続けて読み、前の章で分かったことから、次の章で知りたいことへ進めるかを確かめる。たとえばコメントと Markdown の校正例から、静的検査が候補を出す範囲、指摘のない文もエージェントがコードや設定と照合する判断、意味を保った修正、同じ範囲の再検査へつなぐ。続く使い方は、依頼する対象と確かめる条件、修正の根拠や変更点、再検査結果、未確認事項を知らせる。提示しただけの依頼文から、実行結果を推測しない。

「スキルの使い方」のような短い見出しは、記事や目次から対象と目的が分かれば使える。手順の全体が見出しに詰め込まれていれば `heading-overload` を検討し、操作は本文と依頼例に残す。章の数や見出しの長さは、説明が自然につながり、必要な箇所を探せるかで選ぶ。

指摘には、どの役割や疑問が残ったか、読者の判断に及ぼす影響、変更案、再確認の結果を既存のレビュー形式で記録する。
