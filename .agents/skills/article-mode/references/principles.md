# Principles

指摘に対応する ID を添える。適用によって読者が必要な条件を見失うときは、例外の理由を説明する。章数、文字数、強調数、図の枚数に固定の合格値を設けない。

| ID | 判断基準 |
| --- | --- |
| Reader Goal First | 冒頭で、読者が直面する場面と記事から得られる答え・判断・完成状態を示す。作例から始める場合も、何を確かめる例なのかが最初に伝わるようにする。適用する環境や必要な知識は判断・操作の前に置く。リンクは読者が次に調べたいことや試したいことに対応させ、リンク先で得られる情報をラベルや前後の文で示す。 |
| Evidence First | 技術仕様や数量を断定するなら、実装・公式資料・確認結果を主張ごとに対応させる。 |
| Separate Fact and Opinion | 確認事実、推測、評価、推奨、未確認事項、対象バージョンが読み分けられる。 |
| Front-load Information | 冒頭、見出し、段落の最初で主要な情報を伝える。操作順序を変えると再現できない場合は、完成状態だけ先に示して手順の順序を守る。 |
| Meaningful Headings | 記事タイトルだけで主題の見当がつき、見出しを順に読むと話題と結論がわかる。作例の一文や引用を題に使うときは、記事が扱う主題も伝える。短い導入はタイトルから本文へ続けられる。結びに節を設ける場合は、その節で読者が知ることや次に取れる行動を見出しにする。 |
| Coherence | 前の疑問・例・判断と、次の説明との関係を読者が追えるようにする。つながりが伝わりにくい箇所では、読者が次に見る対象や調べる理由を示す。補足はその情報が必要になる場面に置く。 |
| Natural Editorial Voice | 開発ブログの読者が使う言葉で、筆者が何をして何が分かったかを書く。技術的な意味、確実性、試した範囲を保つ。 |
| Genuine Curiosity | 読者が自分の作業で知りたい疑問や、確かめた発見を入口にする。続きを読みたくなる理由が、伏せた前提や位置情報の謎に依存しない。 |
| Self-contained Introduction | 題名と導入だけで、筆者が何に困り、何を試し、この記事で何が分かるかを説明できる。 |
| Detail Placement | 読者が主張や結果を理解してから、ファイル名・行番号・出力形式などの詳細を使う場面で示す。操作に欠かせない前提や注意は、実行前に読めるように置く。 |
| Semantic Emphasis | 太字は主張と、それを限定する条件を一緒に読める単位にする。 |
| Progressive Detail | 結論、必須手順、前提、安全上の注意は常時表示する。長文の対比や補足は要約を残して初期状態を閉じる。開閉が理解を妨げる場合は重要な実例を本文に出す。 |
| Cognitive Pacing | 抽象説明や仕様の列挙が続く区間を見つけ、例・図・比較・再構成のうち、読者の疑問を解く方法を選ぶ。 |
| Visualize Relationships | 工程、分岐、責務、依存など、配置や線で関係が伝わるときに図を使う。 |
| Explain with Examples | 例がどんな用途と条件を表すか示す。再現可能な例には操作と確認結果を添える。出力や形式の使い方が伝わりにくいときは、必要な項目を実例で示し、その値を使って次に何を確認・操作するかを書く。 |
| Artifact Focus | 自作したものを紹介する記事では、制作物とその価値を題名と導入から読み取れるか確かめる。具体例は価値を伝えるために使う。 |
| Example-anchored Explanation | 具体例の直後は、何を変えて、なぜそうしたかを先に書く。一般化する場合は、その例から導ける判断を示す。 |
| Subtract Before You Add | 新しい説明を足す前に、重複した説明や結論を遅らせる前置きを整理する。 |
| Preserve Meaning | 校正前後で条件、否定、確実性、対象、技術的意味を照合する。 |

見出しや先出しを使って情報を探しやすくする。F字型は観察されたパターンの一つであり、右側の情報の価値や一律の離脱率は導けない。[NN/g の閲覧パターン調査](https://www.nngroup.com/articles/how-people-read-online/)
