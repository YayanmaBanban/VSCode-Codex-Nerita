# 記事 Skill の評価

## 実記事の評価

[日本語校正 Skill の紹介記事](../tests/fixtures/japanese-proofreading/evaluation.md) の依頼と出典を使う。初稿と改善稿を並べ、スキャン、意味、出典、コードの再現性、画面表示、読書体験の確認を記録する。掲載に使う Zenn/Qiita のコピーは各アダプターを適用し、同じ SVG から作る。

人による評価では、最初のスクロールで Lint と意味の照合の違いがわかるか、UI 節で表示文と機械が読む値の違いが見出し・図・短い本文から追えるかを見てもらう。どの位置で読むのをやめたくなったか、改善稿で理解に必要な作業が変わったかを記録する。人の評価を得られなければ未実施とする。

## フィードバックからスキルを見直す

原稿を直す前に、読者がどこで何を理解できなかったかを特定し、題材や媒体が変わっても起きる問題かを考える。[Principles](principles.md) に該当する判断基準があれば、その適用で解決できるかを確認する。再利用できる観点が不足していれば既存原則を補い、独立した判断基準として使える場合は原則を追加する。見落としを防ぐ方法が既存の判断基準で説明できる場合は、必要に応じてレビュー手順や評価例に反映する。記事固有の好みや、その題材だけで必要な補足は原稿の編集で扱う。

検証記録には、指摘から導いた判断、原稿での対応、スキルへ反映した内容を残す。固有の見出しや章の追加を求められた場合は、その変更で満たした読者の目的を記録する。

## 入口・構成承認・レビューのケース

新しいコンテキストで依頼または事前状態を与え、SKILL.md を入口として結果を比較する。構成承認のケースは構成・次の行動で判定できるので、初稿を生成する必要はない。結果には入力、観察した出力、判定と未確認事項を付ける。

| 依頼または状態 | 期待結果 |
| --- | --- |
| 「ブラウザの HTTP キャッシュが再検証される仕組みを記事にして」 | 技術解説。冒頭の答え、成立条件、実例、出典を設計する |
| 「小規模サイトの配信先を、キャッシュ無効化と復旧の手間で比較する記事にして」 | 技術比較。同一条件の表と条件別結論になる。未計測を埋めない |
| 「Node.js の標準テストランナーで初めてのテストを実行する記事にして」 | チュートリアル。前提、手順、期待結果、復旧を設計する。必要な操作順を守る |
| 「このモジュールをリファクタリングして」 | 通常のコード実装として扱い、記事工程を始めない |
| 並列実行不可、独立セッションは利用可能 | 同じ Brief を使って順次独立生成し、いずれも隔離できない場合は未検証点を報告する |
| 構成案が2つしか成立していない、または3案の順序と主張がほぼ同じ | 該当案の切り口や不足を修正し、比較と執筆を保留する |
| レビュアー間で評価が割れた | 判断理由と適用条件を併記し、ユーザーが選ぶ |
| 明示的承認なし、推薦のみ、または差し戻し | 初稿を生成しない。差し戻しでは指示に応じて Brief や候補を更新する |
| 「A を軸に B の例を使って進めて」 | 採用理由と取り込む要素を記録し、その構成で1本だけ書く |

## 制作動機・語り口・検証範囲・Skill の使い方

下の入力を同じ Brief と承認構成で照合する。自然な文章かどうかは、語単体に加えて、その前後と本文全体を読んで判断する。初稿で見つかった指摘と、改稿で残った指摘にそれぞれ根拠を書く。

| 入力 | 期待する判定 |
| --- | --- |
| 「再試行の作例」「作例コード」「作例の全文」が導入、補足題名、補足冒頭で続く技術ブログ | `editorial-voice`。実行記録があれば「検証に使ったコード」「コメントだけを3通りに替えた」など、操作と結果が伝わる表現を提案する。 |
| 条件分岐を学ぶ教材で「この作例を動かしてみる」と一度書く | 読者と教える目的に合うので維持できる。 |
| 説明用の状態表示を「実際に試した画面」と書き換える | `evidence-scope`。実機確認の根拠がないため、「たとえば」「説明用」に戻す。 |
| 回数を受け取る関数だけ掲載して、「呼び出し側を読んだ」と書く | `evidence-scope`。初期化、加算、次に渡すコードの引用または記録を求める。 |
| 4入力への応答だけを確認して「製品全体で再試行は最大2回と実証」と書く | `evidence-scope`。入力ごとの分岐を示し、上限は数え方を前提として明記する。 |
| 同じ処理で `let retries = 0` から始め、再試行するたびに `retries += 1` として次の判定に渡す呼び出し元があり、連続した実行履歴も示す | 実行した環境・コード・ログに一致する範囲で上限を述べられる。実行履歴がなければ仕組みの説明として扱う。どちらも初回は再試行回数に含めない。 |
| Skill 紹介なのに `run.cmd textlint:review` と `run.cmd textlint` だけを案内する | `skill-value-missing`。エージェントに渡すファイルと確認依頼、コード照合、修正、再検査の説明を加える。 |
| 「どのコメントが textlint を通ったか」を調べる検証記事に、Skill の依頼例がない | 題名と読者の目的に合うなら維持できる。 |
| 過去のユーザー発言に「曖昧な言い回しで差分を追いづらく、Skill を作った」とある | 参照できる発言を制作動機に使う。期間、回数、感情、効果などは個別の根拠が必要。 |
| 制作動機は前回の記事に書かれており、本人の発言原文はない | 文書に記録された説明として使える範囲を明示する。一人称の新しい出来事や感情を加えない。 |
| 検査結果しかない本文に「Skill を作った」と題名だけ付ける | `title-promise`。制作を記事の中心にする場合は動機と工夫の根拠を添え、構成と題名の承認へ戻す。 |

媒体を変換した場合は、本文の条件、補足の初期閉、リンクと Front Matter を対象版で見る。Zenn CLI で確認した表示と、本番サイトの対象稿プレビュー、読者テストの有無を個別に記録する。

## 自作した成果物と章のつながり

| 入力 | 期待する判定 |
| --- | --- |
| 自作が確認できる紹介で、題名に一般名詞の「Skill」だけを使う | `title-authorship` を検討し、何を作ったか、固有名、特徴を示した案を並べる。 |
| 検査結果だけの本文に「スキルを作った」と題名だけ付ける | 制作物の紹介を届けられるか Title Promise に戻る。 |
| 他者の Skill を使う記事 | 自作したという表現を足さない。 |
| Markdown の例から仕組みに触れず使い方へ移る | `transition-gap`。静的検査とコード照合がどうつながるか、独立章と既存章に収める案を比べる。 |
| 仕組みの章を採用した記録があるのに、確定構成の章にも本文にもその説明がない | `section-role-loss`。統合先を明記するか、採用範囲へ戻す。 |
| A 案から Markdown 例だけを取り入れ、仕組みの章の採用は明記していない | 仕組みは承認済みに含めず、読者が迷う場合に `transition-gap` を検討する。 |
| 3章で必要な仕組みが説明されている場合と、4章で同じ内容を繰り返す場合 | 3章でも役割を満たせる。重複は移設か短縮で解消する。 |
| 見出しを「スキルの使い方」に短くする | 対象が前後から分かり、本文に依頼、修正内容の見方、再検査が残れば成立する。 |
| 依頼・条件の照合・再検査をすべて見出しに詰め込む | `heading-overload` を検討する。詳細を本文で読めるようにする。 |

## 具体例の根拠と参考元の配置

| 入力 | 期待する判定 |
| --- | --- |
| コメントは分岐を根拠に直し、Markdown は「重要なのは」を削っただけなのに、両方で技術的な意味を確かめたと述べる | `example-evidence-gap`。Markdown の条件を裏付ける資料を示すか、文章整理と明示する。 |
| 再起動を必要とする根拠をすでに確認したと仮定し、文章だけを短くする | 文章整理を説明する章なら成立する。実製品で再起動が必要だと断定するなら根拠を求める。 |
| `previous !== current` だけを条件とする関数を、設定保存時に自動でキャッシュが消えると説明する | 関数が呼ばれた場合の条件と、呼び出し元が決める時点を分ける。 |
| 説明用の関数を Markdown の利用ガイドでも使い、比較処理が呼ばれ、値が異なる場合だけ消えると書く | 同じコードから条件をたどり、未確認の時点を説明できる。実測したという説明や、章ごとの同量のコードは不要。 |
| ユーザーが記事にある見直し方法を設計に使ったと明示する | 制作動機と記事の価値のあとに、出典と取り入れた考え方を短く置く。1件のために章を立てる必要はない。 |
| URL だけ提供された。著者名・記事名が確認できない | 用途は未分類。未取得の項目は空欄で記録し、着想元として紹介しない。 |
| 技術的条件のリンクをすべて参考資料の一覧に移した | `reference-placement`。読者が判断を確かめるリンクを該当箇所へ戻す。 |
| 各主張に必要なリンクをそばに残し、補足資料だけ末尾に移す | 本文の根拠を追いながら、参考リンクも探せる。 |
| 参考記事の文章を長く転載し、どこからが自作の説明か分からない | `attribution-misattribution`。引用と自作の境界、使用範囲と出典を確認する。 |

配置を比べるため、Zenn 公式のガイドを見て記事の補足表示を決めた、とユーザーが明示した場合を想定する。導入の動機と記事の価値に続けて「長いログは、Zenn 公式の『ZennのMarkdown記法一覧』を参考に、必要なときだけ開ける形にしました」と紹介できる。URL だけを提供されたケースでは、この文を載せず用途を未分類にする。これは配置の評価用であり、対象記事の制作経緯を記録したものではない。

## 制作物中心の題名と具体例の直後

| 入力 | 期待する判定 |
| --- | --- |
| 自作の日本語校正スキルを紹介する Brief に対し、題名の先頭が「検索キャッシュはいつ消える？」 | `artifact-focus-drift`。題名から期待される主題と実際の本文を照合し、制作物中心の案と比較する。 |
| 保存処理と呼び出し元まで追って、キャッシュが消える時点を説明する検証記事 | 疑問を主題にした題名が成立する。 |
| 他者のスキルを紹介する記事に「作った」を加える | 制作したと書く根拠がない。筆者の立場が伝わる題名へ戻す。 |
| 自作したスキル名、用途、制作の背景が伝わり、本文で作例や使い方を説明する | 語尾にかかわらず題名の約束を満たせる。 |
| キャッシュの削除条件を書き直した例の直後に、太字の数、コロン、番号付きリストの一般則が続く | `detached-guideline`。この例で何を変え、どう読みやすくしたかを説明する。 |
| 関数名と比較条件を一文にまとめ、外した太字と箇条書き、残したバッククォートの理由を示す | 変更前後から判断の根拠を追える。スキルの自動処理を裏付ける例として扱わない。 |
| 静的検査、コードとの照合、再検査をこの順に行う手順 | 順序を伝える番号付きリストを使える。Markdown の書き方そのものを解説する記事では、読者の目的に合う一般則も維持できる。 |

## レビューの失敗例

下記の入力例は評価用に作ったもの。記事中で事実として使わない。

| 入力例 | 期待する指摘 |
| --- | --- |
| 「この Skill で校正時間が半減する」 | `Evidence First`。測定の出典がない断定は削るか未計測とする |
| `## について` → `## 仕組み` → `## その他` | `Meaningful Headings`。見出しだけで内容と答えがわからない |
| タイトルが文中の作例の言い回しだけで、対象の技術や課題がわからない | `Meaningful Headings`。タイトルに記事の主題を入れ、作例の意味が伝わる位置で引用する |
| 読者が利用場面を知らないまま、再試行するコメントの修正例から始まる | `Reader Goal First`。導入に誰がどんな場面で使うのか、作例から何を確かめられるかを示す |
| `**全ファイルを検査する**。対象は指定したファイルに限る。` | `Semantic Emphasis`。強調だけで範囲を誤読する |
| 段落末に初めて「修正後は同じ範囲を再検査する」と書く | `Front-load Information`。段落冒頭だけで必要な操作がわからない |
| 再試行のコードから、適用場面を示さず対応言語の補足へ移る | `Coherence`。いま読む理由がある補足をその場に置く。対応範囲は対象ファイルを選ぶ説明につなげる |
| 「結果にファイル名と行番号が出る」で説明を終える | `Explain with Examples`。結果の具体的な値と、その行を開いて何を確認するかを示す |
| 「パッケージ定義」へのリンクだけを貼る | `Reader Goal First`。対応バージョンを確認したい場面など、リンク先を開く目的をラベルや前後の文で伝える |
| すぐ隣の一文「静的検査を実行する」を、そのまま単独の箱にした図 | `Visualize Relationships`。関係が増えないので図を省く |
| チュートリアルの必須バージョンまたは最初のコマンドを折り畳みに入れる | `Progressive Detail`。実行の前提と必須操作を本文へ戻す |
| 長いコードを開くと記事のルートが横にスクロールする | `Cognitive Pacing`。PC・スマホで再現し、コードの横スクロールを必要な範囲にとどめる |
| 「エラーの場合に実行しない」を「場合によって実行する」に変更 | `Preserve Meaning`。否定と適用条件が変わる |
