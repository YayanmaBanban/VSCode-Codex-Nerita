# Reading Experience Review

事実確認とは別のパスで、読者が熟読せず縦にスクロールする状況を想定する。記事の目的、初稿、可能なら媒体のデスクトップとスマホのプレビューを用意する。

1. 最初に本文を熟読せず、見出し・図・強調だけをたどる。主要な答えと、続けて読みたい箇所に到達できるか確認する。
2. 離脱しそうな節や行と、その直前から続く負荷を記録する。抽象説明の連続、仕様・Lint の列挙、密集した段落・表・コード、重要情報までの距離を確認する。
3. 重複を削る、実例を先に出す、表を目的別に割る、関係を図解するなど、その負荷の原因に合う変更を提案する。導入、修正前後の要約、重要な注意は開閉や横スクロールに依存させない。
4. プレビューを幅ごとに撮影し、記事全体と折り畳み付近のスクロール、幅の狭い表とコード、図中の文字・線、開閉とコードコピーのしやすさを確認する。プレビューがなければ Markdown 構造による暫定レビューとし、画面の目視を未実施と記録する。
5. [語り口と情報の順序](editorial-voice.md#初稿と改稿を通して読む)を初稿と改稿で照合する。改善箇所の前後を含めて全文を再読し、何を追いやすくなったかを記録する。

報告には位置、つまずく原因、読者の作業への影響、変更案、改善後の観察、確認幅・プレビュー種別を含める。模擬レビューと、人による読書体験の評価は区別する。

## 具体例の直後を読む

変更前後の例と、続く段落を一緒に読む。直後の説明には、元の書き方で分からなかったこと、今回変えた箇所、変更が妥当な理由を示す。一般化する場合は、「条件を一文で伝えられるなら、関数名だけの箇条書きは文に組み込める」のように、その例で使った判断を伝える。

例に関係しない太字の数、記号、リストの規則が続いて読者の関心がそれる場合は、`detached-guideline` として位置、具体例との関係、読者への影響、修正案を記録する。関連資料を置くときは、その判断をした本文の近くで何が分かるか示す。規則そのものを解説する記事では、目的に沿った体系的な説明も成立する。

具体例で行った編集を、スキルの自動検出・削除の仕様として説明しない。必要な順序、適用条件、注意、識別子、根拠から言える範囲は残す。改稿後は例から説明への流れを再読し、変更の効果を確認する。元の説明を維持した場合も、読者に必要な理由を記録する。
