# 語り口と情報の順序を読む

## 構成を選ぶ前に

匿名の独立審査では、[題名だけの審査](title-promise.md)の回答を受け取ってから、題名と最初の段落を渡す。他の段落、構成、根拠はまだ見せない。読者が何を知りたくなったか、その疑問を段落だけで理解できるか、どの文がそう感じさせたかを記録する。

次に残りの導入を渡し、題名から最初の2〜3段落だけで「何に困ったか」「何を作ったか、何を試したか」「何が分かる記事か」を言い直してもらう。答えられない点は不足として残す。その後で構成と根拠を渡し、題名と冒頭が作った期待を本文が満たすか、筆者の目的が保たれているかを照合する。

例えば「回数が間違っていても静的検査を通った。コードのどこを見て判断するか」は、開発者が自分のレビューに持ち帰れる疑問。同じファイルの同じ行を変えた実験で「なぜ同じ12行目なのか」を強調しても、位置が一致するだけでは発見にならない。疑問形と結論先出しは、どちらも導入だけで話が通り、本文に読む価値があれば使える。制作記録の題名には制作動機、工夫、具体例を届ける構成が必要。

## 初稿と改稿を通して読む

1. 題名と導入だけを読み、困りごと・試したこと・読者が得る答えを言い直す。見出しと段落の冒頭をたどり、結果を理解する前に専門用語や内部情報の説明を読む箇所を探す。チュートリアルは実行順を保ち、必要な前提や注意を操作のそばに置く。
2. 読者の疑問への答えを、その疑問が出た場所の近くに置く。再試行の例では検査結果から条件式と回数を渡す前提へ進み、JSONL の `file` と `startLine`、ファイル名や行番号は元の行を開く段階で使う。長い差分やログは、判断に必要な要点を本文に置いてから補足にする。
3. 導入から結びまで、折り畳みの題名と補足、章末、コマンド前後も続けて読む。受け身の名詞句や「〜を示します」が重なり、何をして何が分かったか見えにくい箇所を示す。例えば実行記録があれば「同じ処理を使って、コメントだけを3通りに変えて試した」と書ける。教材の「作例」など、その場で意味が通る語は使える。場所、違和感の原因、自然な言い換え、言い換えても根拠が支える範囲を記録する。
4. 改稿を全文で読み、`brief.authorMotivation`、`brief.coreThesis`、`approvedOutline.titleContract`、実行記録に戻る。説明用の画面を「検証した画面」と呼んだり、確認した分岐から製品全体の挙動を断定したりしない。題名の約束、記事種別、主張、適用範囲を変える案は再承認に戻す。読みやすくなった理由、残した表現や条件、人による読者テストの実施有無を記録する。

| 指摘の種別 | 記録する観察 |
| --- | --- |
| `editorial-voice` | 資料や報告書に寄った言い回しが続き、何をして何が分かったかを追いにくい。 |
| `artificial-curiosity` | 読者の疑問に答える代わりに、後から説明するだけの情報を謎として先に出している。 |
| `intro-dependency` | 記事の価値を説明するには、導入の外にある前提が必要になる。 |
| `premature-detail` | 実装の詳細や操作用の位置情報が、それを知りたい理由より早く出ている。 |
| `evidence-scope` | 調べたコードや入力を越えて、動作、体験、効果を断定している。 |
| `skill-value-missing` | Skill紹介で、エージェントへの依頼や、静的検査後にどんな判断を返すかが見えない。 |

各指摘に `type`、`location`（段落・見出し・短い引用など）、`observed`、`whyReaderCares`、`suggestedAction`、`evidenceIds`（既存の `evidenceRefs` も使用可）、`severity` を記録する。原稿では既存の構成一致レビューにも載せ、指摘ごとの解消・未解消と根拠を残す。編集上の判断に語の出現回数や独自の点数を使わない。
