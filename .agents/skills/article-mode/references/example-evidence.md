# 具体例の根拠を比べる

Arena と初稿・改稿で、読者の理解を支える例を見比べる。各例について、その章で伝えたい主張、修正前の問題、読者がたどれる根拠、修正後に伝わる条件・操作・結果、確認した範囲と応用先を言葉にする。根拠を探すときは、コード・呼び出し元・設定・実行結果・公式資料・既存手順から、確かめたい内容に合うものを開く。

静的検査後の意味の確認を伝える章で、例が前置きを短くするだけなら `example-evidence-gap` とする。条件や操作を確かめる根拠を示すか、文章整理の例として扱う範囲を明示する。読みやすい手順文を示す章なら、前置きの削減だけでも役割を果たせる。動機や利用案内など、例を中心にしていない章へコードや実測をそろえる必要はない。

例えばコメント節の関数が、呼ばれたときに前回値と今回値を比較してキャッシュを消すなら、Markdown でもそのコードを根拠に条件と結果を書ける。「設定を変えた瞬間に自動的に消す」かどうかは呼び出し元を確認する。再起動の要件を扱うなら、対象製品の設定や公式文書で、何を変更したら何を再起動するかを確かめる。文書で確認した動作と実行結果を区別する。

必要なら候補または確定構成の `sections[].exampleEvidencePlan` に、例ごとに `claim`、`beforeProblem`、`afterMeaning`、`evidenceIds`、`status`、`scope` を記録する。`status` は `verified`、`illustrative`、`unverified` のいずれか。説明用コードの分岐を読んだ場合は、その範囲を `scope` に記し、製品挙動や実測へ広げない。技術的主張や承認済みの例の役割を変えるときは、根拠を示して承認へ戻す。
