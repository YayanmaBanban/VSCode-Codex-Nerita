# Correct

依頼者がこのリポジトリのエージェントへ同じ誤りを繰り返し指摘している。次のエージェントがそれを犯せないよう、リポジトリを変更する。

すべての貢献者はエージェントだと仮定する。エージェントは開いたファイルしか見ず、最も近い例をコピーし、コンパイルできる最短の道を選ぶ。一つのファイルから見て正しい変更がリポジトリ全体でも正しいものになるよう設計する。

## 誤りの種類を見つける

最初に最近のコミット、revert、レビューコメント、エージェント向け指示ファイル、回避策の理由を書いたコメントを読む。誤りを種類ごとに分類する。同じ種類の誤りが2回起きたら、一つの種類として扱う。

## 各種類を最も上位の有効な方法で防ぐ

1. **アーキテクチャで発生を不可能にする。** 状態ごとの所有者を一つにし、タスクごとに正式な実行方法を一つにする。内部を隠して誤ったimportを失敗させる。手作業で同期する一覧を単一の正本へ置き換える。エージェントがコピーしそうな旧方式や不要コードを削除する。
2. **型で強制し、不正な状態を記述できなくする。** 悪いコードがまだコンパイルできるなら、代わりに使うファイル・型・関数をエラーメッセージに示すLintやCIチェックを追加する。すでに広まっているパターンなら、変更が問題を増やした場合だけ失敗させる。
3. **振る舞いをテストする。** 検証対象の振る舞いを壊しても通るテスト、または内部実装だけ変えると失敗するテストは修正・削除する。
4. **文書やエージェント規則は最後に、判断が必要なものだけ書く。** エージェントが読まなくても何も失敗しないからである。

## 修正と証明

その後、最も頻繁な種類から実際に修正し、種類ごとに1コミットを作る。新しい検査が実際の過去の誤りに対して失敗することを証明する。同じコマンドをローカルとCIで実行する。例外は問題のある行に記載し、理由・期限・人間の承認を含める。

## 規則表を維持する

最後に、各規則と、それを強制する仕組みを対応付けた表をエージェント向け指示ファイルに保持する。依頼者から訂正されたら誤りを修正し、規則を追加する。規則がすでに書かれているのに強制手段がないなら、それは再発なので同じ変更で最も上位の方法から修正する。誤りが起こり得なくなったら、その規則を削除する。

**回答：** 誤りの種類と根拠、選んだ強制レベル、より上位の方法で対処できなかった理由を示す。
