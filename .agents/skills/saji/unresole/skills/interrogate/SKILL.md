# Interrogate

批判的な担当者が変更や設計の不具合を見つけようとする。実行によって証明された指摘だけを残す。結果を報告し、修正は適用しない。

## 対象の定義（Frame）

対象範囲はユーザーが指定したものとする。指定がなければ、ベースブランチとのmerge baseから作業ツリーまでのブランチ差分を対象とする。ユーザーのメッセージ、コミット、PRの説明から、**in-your-own-words** Skillで意図を言い直す。意図が不明ならユーザーに質問する。

## 並列実行（Fan out）

**arena** SkillのフェーズAの手順3・4、およびフェーズBを実行する。ただし、次の4点を変更する。`arena runners`ではなく`interrogate reviewers`行を読む。各worktreeへ対象範囲の未コミット変更をコピーする。各批判的担当は`generalPurpose`として起動する。arenaのタスクと根拠説明の代わりに、対象範囲、意図、次の依頼文を各担当へ渡す。

> この変更を壊してください。各指摘は実際のコードに対する実行結果で証明してください。例えば失敗するテスト、再現スクリプト、誤った振る舞いを示すコマンド出力を使ってください。設計や計画の場合はプロトタイプを実行するか現在の作業ツリーを調査してください。再現用のファイルは自分専用のworktreeに置いてください。各指摘はタイトル、実際に実行した正確なコマンド、出力された内容、意図から必要な出力を記載してください。実行していないことは報告しないでください。これには文体・命名・構造、および将来の変更がなければ実害が生じないリスクも含まれます。指摘がないという結果も有効です。

## 検証（Verify）

arenaのフェーズFに従って、各指摘のコマンドを再実行する。出力が失敗を示し、その失敗が意図に反するときだけ指摘を残す。それ以外は除外する。根本原因を共有する指摘はまとめる。

arenaのフェーズC・D・Eは実行しない。批判的担当者は異なる不具合を探すため、結論は1人の一覧ではなく、検証済みのすべての指摘を残す。

## 出力（Output）

- **意図（Intent）**：言い直した内容。
- **指摘（Findings）**：検証済みの指摘ごとに、コマンド、その出力、どのように意図を破るか、指摘した担当者を示す。1件も残らなければ「検証済みの指摘なし」と記載する。
- **除外（Dropped）**：批判的担当者ごとに、除外した指摘の件数とその理由を記載する。
