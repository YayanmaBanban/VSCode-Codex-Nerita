# 影響範囲（Blast radius）

出荷前に、変更がほかの場所で何を壊すかを調べる。「Xの影響範囲」「何が壊れるか」「まだ信用できない小さな差分をレビューする」といった依頼で使用する。

`how`と`why`を補完する。`how`はコードが何をするか、`why`はその構造になった理由、Blast radiusは別の場所で何を壊すかを説明する。

呼び出し元を列挙するのが仕事ではない。エージェントは数秒でgrepできる。重要なのはgrepでは見つからない故障である。

## 自分の説明文を信用しない

もっともらしい影響範囲の説明は価値がない。真偽にかかわらず説得力があるように読めるからである。そのため、説明だけを返さない。全体の安全性が依存する1～2個の事実を見つけ、実際にコードを動かして証明する。

### どの程度確信できるか

安全性を左右する事実ごとに、低コストで到達できる限り次の段階まで確認し、どこで止まったかを示す。

1. 自分でそう述べた。単独では価値がない。
2. 該当する行を示した。実在する`file:line`か、ライブラリ自身のソースを示す。
3. 悪いケースが起きないことを示した。故障経路を段階ごとに追い、到達しないことを確認する。
4. 実行した。実際のコードを呼び出し、誤っていれば明確に失敗するスクリプトまたはテスト。
5. 動いているアプリで再現した。

通常、工程4はアプリが出荷するものと同じライブラリをimportし、懸念する正確な関数を呼び出す小さなスクリプト1つで済む。

## 工程

1. 変更を読む。差分、追加・変更・削除したシンボル、差分に明示されない振る舞いの変化も含めて調べる。PRとコミットを取得する。
2. 安全性を裏付ける一つの事実を探す。危険に見える変更も「この呼び出しはすでに無効なキャッシュ項目だけを削除し、それ以外はしない」という事実で安全な場合が多い。その事実が成り立てば、多くのリスクを一度に否定できる。多数の可能性を列挙するより、この調査へ時間を使う。
3. grepの限界を超えて調べる。使用するライブラリのソースを読み、固定されたバージョンとローカルパッチを確認する。microtask、unmount、teardown、SolidとReactの差など、処理のタイミングを調べる。シンボル検索では見つからないAPIのJSON応答、DBの列、通信形式、同じバイト列を読むほかの言語、feature flag、3段階下流のコードなどを追う。
4. 各リスクを正直に評価する。現実に起きる可能性と、起きたときの実際のコストを示す。確認できたリスクを残し、調べて問題がないと分かったものは別に列挙する。実在する`file:line`を引用する。検索で何も見つからないことも結果である。存在しない呼び出し元やAPIを作り上げない。
5. 安全性の根拠となる事実を証明する。実コードを実行するスクリプトまたはテストを書いて実行し、何が起きたかをそのまま貼る。
6. 大規模または横断的な変更では`arena`として実行する。同じ質問を複数のモデルへ渡して答えを統合する。モデルが異なると、異なる実在の不具合が見つかることがある。

## 返すもの

- **変更の振る舞い。** 明白でない部分を含め、何が変わったか。
- **安全性を裏付ける一つの事実。** 事実と、上記のどの段階まで検証したか、証拠を示す。証明できなければ「未実証」と記す。
- **リスク。** どう壊れるか、`file:line`、可能性と重大度、調べ方を記す。重要なものには証拠を貼る。
- **安全と確認できたこと。** 何を調べ、なぜ問題ないか。
- **マージ前に行うこと。** 実際の不具合を捕捉する最も安価なテストまたは再現。作成したスクリプトも含む。

`unslop`を適用して記述し、実在するコードを根拠にし、公開する前に非公開情報を除去する。

**回答：** 上記の説明を返し、安全性を裏付ける事実を実証済みまたは未実証と明記する。
