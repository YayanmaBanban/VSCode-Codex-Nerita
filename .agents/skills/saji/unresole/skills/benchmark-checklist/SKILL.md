# ベンチマークの確認項目

性能の数値を出すときに使用する。PRの変更前後、性能劣化の主張、Hillclimb用ハーネス、ライブラリや設定の選択が対象となる。各質問にはコードからの推測ではなく、実際の実行で得た証拠を示して回答する。

ユーザーが求めた大まかな目安だけなら1回の実行でよい。ただし質問4と7は確認し、1回だけの実行だと明示する。その結果に異常がなければ残りは省略する。選択肢を比較して決定する場合は、決して「大まかな目安」には該当しない。

## 何かを実行する前に

- 出す予定の主張を、そのまま報告に使える言葉で書き出す（例：「6万行のデータセットでexportのp50が30%高速化した」）。以下の質問でこの一文を検証する。
- 計測スクリプトを読む。何を計時・計数し、何を無視しているか確認する。
- `uptime`でロードアベレージ、`nproc`でCPUコア数を確認する。マシンが忙しければ何が動いているか調べる。停止できなければ、比較対象が同じノイズを受けるよう交互に実行し、その旨を報告する。

## 質問

1. **なぜ2倍にならないのか。** 制約要因を挙げる。プロファイラやトレーサー自体が処理を遅くするため、報告には使用しない別の実行でプロファイルを取る。プロセスごとのCPU（`top`、`pidstat`）、実行時プロファイラ（`node --cpu-prof`、`py-spy`、`perf`）、I/O待ち、システムコール数（Linuxの`strace -c`）を調べ、高負荷箇所をソースへ対応付ける。負荷生成側も監視する。そちらが先に飽和したなら測っていたのは負荷生成側である。変更しても数値が動かなかった場合、その理由は制約要因に現れる。変更が無意味だったと判断する前に制約要因を見つける。
2. **調整されていたか。** 比較するすべての側を本番と同じように実行する。Releaseビルド、本番フラグ・環境変数、バッチ処理・トランザクション設定、接続プール、本番と同じ温度のキャッシュ、同じバージョンとデータを使う。一方を既定設定で実行したなら、実装ではなく設定を比較したことになる。制約要因が設定（行ごとのコミット、Debugビルド、索引の欠落など）なら、その側は未調整である。勝者を選ぶ前に調整して測り直す。調整できない場合はその結果から勝者を選ばない。何を採用するかユーザーが決める場合、「現時点で出荷されているコード」の比較へ主張を狭めても問題は解消しない。ユーザーが採用するのは今日の設定ではなく、その選択肢そのものだからである。
3. **限界を破っていないか。** 計算する。毎秒バイト数をディスク・ネットワーク帯域幅と、毎秒操作数×操作1件のコストをコア数と、削減時間を変更した部分の元の実行時間と比較する。実行時間の10%を占める部分を完全になくしても、全体の高速化は最大で約11%。物理的な限界を超える結果は、キャッシュ、実際には何もしていない処理、バグなど、意図した処理とは別のものを測っている。
4. **エラーがあったか。** 失敗と成功以外の応答を数え、出力が存在するだけでなく正しいことを確認する。拒否は速い場合が多く、タイムアウトと再試行は遅い。スクリプトがエラー数を数えていなければ追加する。
5. **再現するか。** 比較する各側を最低5回実行し、A、B、A、B…と交互に測る。ウォームアップ、遅延初期化、キャッシュ、経時変化が一方だけに有利にならないようにする。中央値と範囲を報告する。差が実行ごとのばらつきより小さい場合は、測定可能な差はない。判断が微妙なら順位和検定または計測ハーネス固有の統計手法を使う。
6. **実用上意味があるか。** ミクロな結果に加え、ユーザーが待つエンドツーエンド経路を現実的なデータ量と並行性で測り、ミクロな処理が全体の何割かを報告する。リクエスト時間の1%しか使わない補助関数は、どれほど速くなってもリクエスト全体を最大1%しか高速化できない。
7. **処理は本当に行われたか。** 計時区間内に仕事が実行されたことを確認する。リクエストがサーバーへ到達し、行が書き込まれ、バイトが読み込まれ、結果が使われたか確認する。反復されなかったジェネレーター、待機されなかったPromise、JITが捨てられる結果などの遅延処理やタイムアウトは、実行されなかった仕事の数値を生み得る。

## 報告

- 最初に判定を書く。高速化、低速化、測定可能な差なし、結論不能のいずれか。
- 単位付きの数値、実行回数、範囲、制約要因を示す。例えば「p50 41ms → 33ms、各側7回の中央値、修正後の範囲32～35ms、1コアのJSON解析が制約要因」。
- 差を主張しながら制約要因を挙げられない、一方が未調整、または質問4と7を確認できなかった場合は、結論不能と判定し、欠けているものを示す。
- PR本文では主な数値を1つに絞る。実行結果、範囲、制約要因の証拠はリンクした成果物またはメモファイルに置く。

## 性能に関するほかの資料

- **Perf issue** Playbookがベースラインから計画を作る前、および以降のすべての数値について精査する。
- **Hillclimb** Playbookのハーネスを固定する前に精査する。固定されたハーネスはエラーと仕事量を出力するため、採用または取り消しの判断ごとに質問4と7を追加作業なしで確認できる。
