# Automate me

ユーザーの仕事の進め方を、エージェントが従うSkillへ変換する案内付きの手順。成果物は、本人向けに調整した1つの`-mode` Skill（例：`jay-mode`、`priya-mode`）。

このSkillは3つの仕組みを統括する。手順1にある会話記録の調査、Cursor組み込みの`create-skill`（Skillの作成）、**unslop** Skill（文章の規律）である。処理順を管理し、それらを置き換えない。

## 流れ（Flow）

### 0. 既存Skillを確認する

`.cursor/skills/**/*-mode/SKILL.md`と`~/.cursor/skills/*-mode/SKILL.md`を再帰的に探し、ユーザーのハンドルに一致するものを調べる。Mode Skillは最上位だけでなく、個人別ディレクトリ（`.cursor/skills/<handle>/`）にも置かれる。存在する場合、すでに「自分のSkillを更新して」などと明言していなければ、`AskQuestion`で意図を確認する。

- 既存のSkillを更新（再実行時の既定）
- 新しく作り直す（まれな選択。先に理由を尋ねる）

更新の場合、その後の処理を変える。

- 手順1は、Skillの最終編集時点（`git log -1 --format=%cI <path>`）以降の履歴だけを調べる。
- 手順2ではゼロから何を記録するかではなく、何が変わり何が不足しているかを尋ねる。
- 手順4は既存ファイルをその場で編集する。ユーザーが否定していない節は残し、新しい証拠がある節を修正する。本当に新しい規則があるときだけ節を追加する。

### 1. 履歴を調べる

並列に分担する前に、現在のワークスペースのトランスクリプトを探す。システムプロンプトに`agent-transcripts/`の場所が記載されている。その場所だけを使用する。`~/.cursor/projects/*/`を横断して探さない。ワークスペースの境界を越えて、無関係なプロジェクトの私的なチャットを読んでしまうためである。

その範囲で最近のエージェントとの会話を調べ、繰り返されるパターンを探す。履歴を分割し、複数のサブエージェントで並列に調査する（例えば直近2～4週間を3区分にして、それぞれが十分な資料を扱う）。推論レベルは**poteto-mode** SkillのSubagentsセクションに従う。各担当は親が渡したワークスペース限定のパスからトランスクリプトを読み、以下の兆候を探し、根拠への参照を付けた短い構造化リストを返す。既定の調査対象は次のとおり。

- 回答の好み（長さ、語調、形式、「もっと簡単に」のような訂正）
- 委譲の習慣（サブエージェント、モデル、専門ワークフロー、並列化）
- 検証への姿勢（「完了」の意味、単体テストと実動作の再現、レビュー担当）
- コードと文章の規律（スタイル、引用するPrinciple、Lint・整形ツール）
- 作業工程の慣習（worktree、コミット、PR、レビュー・マージのツール）
- メタ的な好み（作業途中でSkillを修正する、新しいSkillを提案する）

各情報を規則として採用する前に、複数の区分と照合する。2つ以上の区分で見つかったパターンは高い確信度を持つ。単独の兆候は弱く、通常は除外する。

### 2. ユーザーへ直接尋ねる

履歴調査では、まだ表面化していない意図を拾えない。ゼロから文章を入力させるのではなく、構造化された複数選択の`AskQuestion`を使用する。

質問は1～2件、各4～6選択肢。カテゴリの質問では`allow_multiple: true`を使う。最初は「どの領域を最も重視するか」のように幅広く尋ね、その後、選ばれた領域の具体的な選択肢を提示する。構造化された質問の最後に、選択肢で拾えなかった内容を一つの自由入力の質問で確認する。

20個もの質問を一度に提示しない。

### 3. 発見事項を分類する

まとめた情報を節に分ける。よくある分類は次のとおり。ただし該当するものだけを使う。

- **回答スタイル（Response style）**：長さ、語調、形式。
- **自律性（Autonomy）**：質問なしでどこまで進めるか、MCPの使用。
- **最初に理解する（Understand first）**：作業範囲の決定・調査時に使うSkill。
- **サブエージェント（Subagents）**：既定値、並列化、作業とモデルの対応、専門ワークフロー。
- **文章・コードの規律（Prose / code discipline）**：Principle、Lint、スタイルガイド。
- **レビューと検証（Review and verify）**：再現の方針、検証Skill、実動作のテストツール。
- **工程（Process）**：Git worktree、コミット、PR、レビュー・マージのツール。
- **Skill（Skills）**：作成方針、Skillを先に修正すること、新しいSkillの提案。

形式は**poteto-mode** Skillを参考にする。粒度を把握するために読み、内容はコピーしない。ユーザーの規則はpoteto-modeの規則と同じではない。

### 4. Skillの草案を作る

Cursor組み込みの`create-skill` Skillを使って作成する。配置は次のとおり。

- **パス：** 既存Mode Skillの分類を維持する。新規作成時、ハンドル用の個人カテゴリがリポジトリ内に存在する場合は`.cursor/skills/<handle>/<handle>-mode/SKILL.md`へ置く。それ以外はプロジェクト内の`.cursor/skills/<handle>-mode/SKILL.md`を既定とする。ユーザーが個人用を好む場合は`~/.cursor/skills/<handle>-mode/`に置く。
- **ハンドル：** ユーザーの名前または選んだ識別子。
- **frontmatterの`description`：** 本人の名前、`/<handle>-mode`、その人のスタイルで作業することを発動条件にし、「コードを書く」「PRをレビュー」のような一般的な語を条件にしない。
- **frontmatterの形式：** `create-skill`のYAML規則に従う。`description`は1つのYAMLスカラーとして保持する。句読点や折り返しのために必要なら引用符を付けるか、字下げした継続行を伴う`description: >-`を使う。
- **frontmatterの`disable-model-invocation: true`：** 既定で付ける。毎回のターンにModeを適用したいとユーザーが明示した場合だけ無効にする。

### 5. 文章を改善する

すべての行に**unslop** Skillと`create-skill`の執筆ガイドラインを適用する。

草案をユーザーへ提示し、意見を得る。複数回の反復を前提にする。不要な部分は徹底的に削る。Mode Skillはマニュアルではない。

### 6. 反映する

mainから分岐したworktreeで作業する。コミットしてPRを作る。mainへ直接Pushしない。

## 守る条件（Guardrails）

- **一つの会話へ過剰適合しない。** 一度だけ述べられ、別のときに否定された好みはノイズである。規則化する前に複数の実例を要求する。
- **技巧を凝らさない。** ほかのSkillの内容を繰り返し書く、比喩を発明する、エージェントが読む文章を詩的にすることはコストに見合わない。作業に直結する文章を残す。
- **引用し、本文を複製しない。** ユーザーが使うほかのSkillや、別に維持しているPrinciple文書は、内容を貼り付けずパスで参照する。
- **節を最小限にする。** ユーザー固有で、既定と異なる規則がある場合だけ節を追加する。「明確に伝える」は節にならない。「短い段落。案の比較には表を使う。箇条書きは項目が本当に並列の場合だけ」は節になる。
- **指示文では名前を一般化する。** 著者の名前ではなく「ユーザー」または「人間」を使う。
- **対称性を強制しない。** ユーザーに書く価値のある工程規則がないなら、Process節を丸ごと省く。

## 評価（Evaluation）

`-mode` Skillは主観的な成果物である。`create-skill`型のテスト・反復ベンチマークのループはここでは有用でない。ユーザーに感覚を確かめてもらう。本人らしい文章か、見落としがないかを判断し、その後反映する。

Skillの発動条件の正確さが実務で問題になった場合だけ、descriptionの最適化ループを実行する。

## 使用しない場合

- ユーザーが作業固有のSkillを求めている場合（作業習慣ではない）：`create-skill`だけを使う。履歴調査は不要。
- ユーザーが一つの狭いワークフロー（例：「コミットメッセージの書き方」）を保存したい場合：通常のSkillでありMode Skillではない。
