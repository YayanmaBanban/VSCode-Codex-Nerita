# Notesの検証対象一覧

このディレクトリは、Notesの利用者向けの動作を検証するための正本である。アプリを操作する前に一覧を読み、該当する機能ファイルを手順として使う。

## ベースラインの前提条件

- 破棄可能なデータディレクトリを使って`http://127.0.0.1:4173`でNotesを起動する。
- 同時実行で状態を共有しないよう`NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`を設定する。
- `Quarterly plan`と`Grocery list`という題名のノートを初期登録する。
- `control-notes`と`notes` CLIを`PATH`に含める。
- `control-notes doctor`を実行し、期待するURL・データディレクトリ・ビルドリビジョンを検証する。
- この検証で起動していないインスタンスは操作しない。

## 操作上の約束

- 別の前提条件が書かれていない限り、各手順はベースラインの状態から開始する。
- CSSセレクターやDOMの位置より、ARIAロールとアクセシブルな名称を優先する。
- 各コマンドは文字どおり実行する。引用符付きの名前とフラグを変えない。
- ブラウザー操作には`control-notes browser`を使用する。
- 端末操作には`control-notes cli -- <command>`を使用する。
- 状態を変更した後は初期データを復元する。後片付けで証拠となる成果物を消さない。

## 証拠と省略の報告

- 最後の画面だけでなく、利用者の操作と、その結果の状態を取得する。
- UIの証拠には、ARIAスナップショットとアプリ名が見えるスクリーンショットを含める。
- CLIの証拠には、コマンド、stdout、stderr、終了コードを含める。
- データ変更の証拠には、保存値を別の読み取り専用経路から再確認した結果を含める。
- すべての成果物に機能IDと使用した入口を記録する。
- 到達できない経路は、試したコマンドと満たされなかった前提条件を報告する。
- ある入口を省略した場合、別の経路で検証したことを理由に検証済みと報告しない。

## 機能ファイルの契約

各機能ファイルはH1見出しと、利用者が観測できる振る舞いを説明する1段落で始める。その後、以下の**4つのH2節を順番どおり**に記載する。

1. `Sub-features`：各振る舞いに短いIDを付け、1行ずつ列挙する。
2. `How to get to it (user POV)`：利用者が到達できるすべての入口を列挙する。
3. `Driving it with <harness>`：`Preconditions:`で始め、利用者の操作・正確なコマンド・観測できる結果を一つずつ組にしたラベル付き箇条書きを使う。
4. `Gotchas`：検証を無駄にしたり無効にしたりする落とし穴を列挙する。

機能一覧には実装の詳細を入れない。利用者からの経路、安定した識別子、必要な状態、コマンド、観測できる証拠だけを書く。
