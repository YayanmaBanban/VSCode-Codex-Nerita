# 検証Skillを作成する（Create a verification skill）

本格的なプロジェクトには、実際のアプリを操作して振る舞いを証明するスクリプトが必要である。起動し、ユーザーと同じ方法で機能を操作し、証拠を取得する。このSkillは、対象リポジトリに適したプロジェクト専用のSkill（`.cursor/skills/verify-<app>/`）を生成する。生成するSkillは人間ではなく次のエージェントのために書く。アプリを一度も見たことがないエージェントが作業途中で初めて読む前提とする。

## 1. ユーザーではなくリポジトリを調べる

次の質問にはコードベースから答え、観測できないことだけユーザーに尋ねる。

- **操作対象（Surface）：** 利用者が実際に触れるものは何か。Web UI、CLI/TUI、デスクトップアプリ、API、モバイルアプリ、ライブラリか。複数ある場合は主なものを選び、残りも記録する。
- **起動（Run）：** アプリはローカルでどう起動するか。リポジトリに記載された開発用コマンド（package scripts、Makefile、READMEのquickstart）を優先する。ポート、環境変数、初期データ、認証を記録する。
- **操作（Drive）：** エージェントがプログラムから操作するにはどうするか。既存のハーネスを最初に調べる。Playwright/Cypressテスト、expectスクリプト、PTY補助、curlで呼び出せるエンドポイント、デバッグポートなど。その後で一般的な方法を選ぶ。WebとElectronはブラウザー/CDP、CLI/TUIはtmux/PTYのハーネス、サービスは通常のHTTPを使う。
- **観測（Observe）：** どんな証拠を保存できるか。スクリーンショット、端末の記録、応答本文、ログ、終了コード、DB状態など。
- **隔離（Isolate）：** ポート・データディレクトリ・プロファイルを分けて2つのインスタンスを同時に実行できるか。できなければ生成するSkillに明記する。共有インスタンスを二重操作してユーザーのセッションを壊すより、二重操作を拒否する。

現在のチェックアウトをそのままビルド・起動できない場合は、生成前に修正する（または具体的に報告する）。壊れた基盤を前提に書いたSkillは誤った手順を教える。APIが提供しない静的ディレクトリやサンプル設定など、無関係な欠落物が起動を阻害するときは、検証の足場として明記し、後片付けで除去するのであれば、生成Skillがそれを作成してもよい。

## 2. Skillを生成する

`.cursor/skills/verify-<app>/SKILL.md`へ`name: verify-<app>`と、アプリ・操作対象・適用条件を示す`description`を含むYAML frontmatterを書き、次の節を用意する。frontmatterがなければSkillは登録されない。各節は実際に調べた内容を基に書き、プレースホルダーを残さない。

- **Launch：** 検証のためにアプリを起動する正確なコマンドと、準備完了を判断する方法（ログ行、プロンプトなど）。初期データのない状態から、移行とseedデータの準備を含めて利用可能な状態へ到達しなければならない。準備完了とは単にプロセスが応答することではなく、利用できることを指す。DBのhealth checkが通っても初期化スクリプトが動作中の場合がある。終了手順も含める。短命なCLI/TUIではサーバーを維持しない。Launchはバイナリをビルドするか依存関係を一度インストールし、個々の操作は隔離されたPTYまたはtmuxセッションで行うことを指す。
- **Doctor：** 「このインスタンスを操作する価値があるか」に答える読み取り専用の検査を1つ用意する。プロセスの稼働、正しいバージョン・ビルド、ポートの所有者が自分たちであること、認証の有効性など。異常に見えるときは最初にこれを実行する。
- **Drive：** このリポジトリの実際のセレクター・コマンドを用いた操作ハーネスの手順。例ではなく実物を使う。座標やTab移動の順序より、ARIAラベル、data属性、プロンプト文字列、ルートパスなど安定した識別子を優先する。
- **Evidence：** 何を証拠として取得し、どこに置くか。基準は、内部setterやテスト専用エンドポイントではなく実際のユーザー経路を操作すること、最終画面だけでなく操作とその結果の状態を取得すること、見えるものだけでなく副作用（ファイルの書き込み、行の追加、メッセージ送信）も検証すること、モックは製品の境界ですでに外部システムを隔離している場合だけ使用すること。安全な経路がdry-runやテストモードの場合は、名前を信用せず、実際に省略するものをファイル・ネットワーク・Git参照などの観測で確認する。一部のdry-runでもネットワークへアクセスし、ブラウザーを開くことがある。
- **Cleanup：** 実行中に作成したインスタンスを停止する方法。プロセス名で一括killせず、自分が起動したものだけを終了する。後片付けで消すのはインスタンスと一時状態であり、証拠ではない。証拠となる成果物は指定場所に残す。
- **Helpers：** 同梱するスクリプトは実行可能にし、呼び出し方法をSkill本文へ記載する。読み手が逆解析しないと使えない補助スクリプトは補助にならない。

## 3. 機能一覧を初期作成する

`.cursor/skills/verify-<app>/features/README.md`と、特定できる利用者向け機能ごとに1ファイルを作る。ルート・コマンド・メニュー・文書を基に、最初は主要な3～5機能を目安にする。[`references/feature-map-example/`](references/feature-map-example/)の形式に従い、READMEの目次と機能ごとのファイルを作る。各ファイルには利用者の視点から、機能の内容、到達方法、ハーネスによる操作方法、正しく動作したと証明できる観測状態を記述する。4つのH2見出しは`Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>`、`Gotchas`とする。初期データに操作の前提条件が不足している場合、その操作は失敗として報告し、理由を機能ファイルの`Gotchas`へ記す。通過させるために操作を弱めない。機能一覧はリポジトリが維持する検証の正本である。便利な入口を1つだけ操作した証明は、一覧にほかの経路が記載されているなら不完全である。

## 4. 引き渡す前に生成Skillを証明する

生成Skill自身の指示を最初から最後まで一度実行する。起動、Doctor、機能一覧のうち1機能の操作（1件で十分。ほかは後続の実行で扱う）、証拠の取得、後片付けを行う。後片付け後も指定場所に証拠があることを確認する。証拠を削除する後片付けではこの工程は失敗となる。失敗した点を修正し、失敗した試行ごとに生成された後片付けも実行して、失敗したプロセス・ポートを残さない。実行されていない生成Skillは成果物ではなく草案である。実際の対象の代用環境（新規VMの代わりのコンテナー、リモートの代わりのローカル構成など）で証明した場合は、代用環境が行い実際の対象が行わないすべての準備工程を列挙する。それらは実際の対象で検証するまでは未検証のままとなる。

## 5. 保守手順を提案する

アプリの変更後も機能一覧を正しく維持する方法として`/maintain-verification-skill`をユーザーに示す。定期実行を提案するのはユーザーから求められた場合だけ。
