# 形式検証Skillを保守する（Maintain a formal verification skill）

形式検査は、記述した対象について性質を証明する。コードが変わって検証が変わらない場合、すでに存在しないコードを説明しているのに検査が通り続けることがある。証明に見えるため、これが危険である。このSkillは`/create-formal-verification-skill`で作った検証Skill、または特定のコードに対してモデルチェッカー・証明器・コードレベルの検証器を使うプロジェクト専用Skillを維持する。通常のプロジェクト専用Skillは、それを使いながら行う変更を扱う。こちらはSkillを使わずに行われた変更、マージ、広い範囲のコミットによるずれを扱う。

## 結果（Outcomes）

検査ごとに以下の状態を一つ示す。

- **`in sync`：** 最後の同期から検査対象の内容を変える変更はなく、検査が合格する。
- **`updated`：** コードが変わり、検証は新しいコードを記述するよう更新され、検査が合格する。
- **`bug`：** 検証は現在のコードを記述しており、コードが性質を破る。これはコードについての発見であり、ずれではない。
- **`blocked`：** 検証を最新のコードへ合わせられないか、実行できない。理由を正確に示す。

一つの検査は`updated`と`bug`の両方になり得る。更新によって再び現在のコードを記述するようになり、その結果性質が失敗する場合である。

## 編集範囲

モデル、ハーネス、性質ファイル、検証Skill自身など**検証部分だけ**を編集する。ユーザーから依頼がない限り、実行中に製品コードを編集しない。現在のコードに対して性質が失敗する場合は、合格させるために性質やモデルを弱めない。失敗を報告する。

## 実行工程（Pass）

1. **検査を探す。** 検証Skillに固定名はないため、機能から探す。特定のコードに対してモデルチェッカー、証明器、その他の検証器を実行するプロジェクトSkillを見つける。見つかったすべて、またはユーザーが指定したものを読む。各検査について性質、対象コード、上限・仮定、実行コマンド、最後にコードを記述していると確認したコミットを集める。検証Skillがなければ停止して`/create-formal-verification-skill`を案内する。同期コミットが記録されていなければ、検証ファイルを最後に変更したコミットを使い、その旨を伝える。
2. **現在の状態で実行する。** 変更する前に各検査を一度実行し、結果を記録する。ここで合格してもコードの正しさは分からない。古い記述について性質が成り立つことを示しただけである。失敗は検証のずれか不具合かもしれない。工程5まで決めつけない。
3. **対象コードへのすべての変更を読む。** 同期コミットから現在のコミットまでの対象ファイルをdiffし、各コミットメッセージを読む。移動したコードも調べる。関数名が変わり、分割され、別ファイルへ移っても対象コードである。さらに、検査が守る状態へ影響する新しいコード、例えば同じフィールドへ書く新関数も探す。変更ごとに次の分類を行う。
   - **影響なし（No effect）。** 書式、コメント、検査対象外の経路など、検証が記述する内容を変えない。コミットメッセージではなくモデルやハーネスに照らして確認する。
   - **検証が現在のコードを記述していない。** 以前一つの不可分な操作だったものが二つになった、分岐が追加・削除された、チェックが移動した、新しい経路が保護する状態へ到達した、値の範囲が変わったなど。モデルまたはハーネスを修正する必要がある。
   - **約束が意図的に変わった。** コードが保証する振る舞いが変わり、文書コメント、テスト、変更履歴、コミットメッセージにそれが意図的だという根拠がある。性質も修正する必要があり、根拠を引用する。
   - **約束が壊れた可能性がある。** コードは変わったが保証を変更するという証拠がない。その後の失敗を不具合候補として扱う。
4. **実行結果からではなくコードから更新する。** モデルやハーネスを修正して、変わった各部分が再びレビュー担当の開けるコードを示し、コードの一つの不可分な工程が検証でも一つになるようにする。再実行前にコードを基に更新し、検査を通すために形を変えない。性質を変えるのは約束が意図的に変わった場合だけ。旧表現・新表現・根拠を書き出す。変更で不正になった場合を除き上限は維持する。上限を減らす必要があれば報告する。
5. **再実行して各結果を判断する。**
   - **合格（Pass）：** 新しい記述が失敗を検出できなくなったまま合格している可能性がある。新しいチェックを外す、新しい工程を入れ替えるなど、性質が守るべき内容を新しいコードで壊し、検査が検出することを確認する。その後、その破壊を取り消す。
   - **失敗（Fail）：** 反例を実際のコードで工程ごとに再現する。コードで発生しない工程が含まれていれば検証が間違っている。検証を修正して誤りを説明する。すべての工程が起こり得るならコードの不具合である。導入したコミットを特定し、コードの用語による手順列で反例を説明し、損害を一文で述べる。実コードに対する安価なテストや再現で示せるなら根拠として報告へ追加する。製品コードにはコミットしない。
6. **検証Skillを更新する。** 各検査が扱うコード、コマンド、上限、仮定、同期コミットを更新する。同期コミットは実際に確認したコミットに設定する。`blocked`の検査では同期コミットを進めず、報告で明示する。その後、次のエージェントが実行するのと同じように検証Skillを一度実施し、手順が動くことを確認する。

## 報告

検査ごとに以下をユーザーへ伝える。

- 結果と、読んだコミット。
- 検証で何をなぜ変更したか。各変更について、コードの構造が変わったのか、約束が意図的に変わったのか、その場合は証拠を含めて短く説明する。
- 再実行結果と、更新した検査がまだ失敗できることを確認するために使った意図的な破壊。
- 各不具合。コードの用語による反例の工程、損害、導入コミットを平易に述べる。
- 新しいコードを含む、検証すべきなのに対象外となっている部分。

各失敗が検証のずれかコードの不具合かを明示する。更新前に合格し、更新後に失敗した場合は、以前の合格が古い記述に対するものだったと説明する。

検証部分の修正は製品コードの修正と分け、独立した変更として扱う。
