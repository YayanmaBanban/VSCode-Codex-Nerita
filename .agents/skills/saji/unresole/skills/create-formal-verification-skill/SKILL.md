# 形式検証Skillを作成する（Create a formal verification skill）

テストが確認するのは誰かが書こうと考えたケースである。形式検証は、宣言した範囲のすべてのケースを調べる。モデル内で考えられる全実行順序、ある上限までのすべての入力、またはすべての入力である。このSkillはリポジトリ内で最も重要な箇所を探し、その性質を一つ検証し、次のエージェントが変更をその性質に照らして確認できるプロジェクト専用Skillを残す。作業途中で初めてそのSkillを読み、こちらの作業を見たことのないエージェント向けに書く。ユーザーは検証言語を学ばなくても結果を信用し、判断できる必要がある。

## コードから対象を選ぶ

コードベースから答え、観測できないことだけユーザーへ尋ねる。ユーザーが対象領域や不具合を指定していればそこから始める。

適切な対象は、コードが守ると約束している性質のうち、破れるとユーザーに損害があり、テストがその破綻ケースへ到達しにくいものである。リポジトリ内で最も重要なものを選び、最も検証しやすいものを選ばない。

## 問題に合わせて道具を選ぶ

最小のコストで問題に答えられるツールを選ぶ。モデルチェッカー、証明支援系、SMTを利用する検証器、その他のツールが候補になる。イベントが悪い順序で発生し得るかを調べる場合は、小さな設計モデルを使うモデルチェッカーが適していることが多く、言語を問わずTLA+を既定とする。メモリー安全性、オーバーフロー、データ構造の不変条件など、**コードそのもの**がすべての入力でどう振る舞うかを調べる場合は、コード上で実行する検証器が適していることが多い。その言語で動く検証器がないならそう伝え、関数の手書きモデルではなく生成入力で実コードをテストする。上限付きの確認では足りず、すべての大きさで成立しなければならない性質には証明が必要となることがある。リポジトリの開発者がインストール・実行できるツールを優先し、選択理由をユーザーに説明する。

## 良い検証に必要な条件

- **コードに忠実。** モデルや証明の各部分が、レビュー担当が開けるコードを指す。検証で一つの不可分な手順と扱うものは、コードでも一つの不可分な手順である。名前はこのリポジトリから取る。
- **失敗できる。** 一度も失敗したことがない検査は何も証明していない。検査対象のチェックを削除する、手順を入れ替えるなど、保護対象のコードを意図的に壊した版で各性質が失敗することを示す。
- **発見は発見として残す。** 現在のコードが性質を破る場合は、コードの用語による反例とともに報告する。合格させるために性質やモデルを弱めず、ユーザーに依頼されない限り製品コードも変更しない。
- **対象範囲を正直に示す。** どの範囲・上限・仮定で何を検証し、何を除いたかを示す。合格が保証するのはモデルや上限の範囲であり、システム全体ではない。
- **ツールを知らなくても読める。** 性質と、それが破れた際の損害を、それぞれ平易な一文で説明する。反例はコード上の用語を使った短い手順列として示す。
- **安価に再実行できる。** 一つのコマンド、再現可能なツールバージョン、後続のエージェントが関係する変更ごとに使える短い実行時間を確保する。
- **コードと同期して維持する。** 各検査が対象とするファイル・関数と、検証がそれらのコードを記述していると最後に確認したコミットを記録する。対象コードがそのコミット以後に変わったら、後続エージェントは再確認が必要だと判断できる。

## 検証Skillを生成する

対象領域を名前に含め、いつ使用するかを説明するfrontmatter付きのプロジェクト専用Skillを作る。frontmatterがなければSkillは登録されない。生成したSkillだけから次のエージェントが、変更が検証対象コードに触れるか、検査の実行方法、実際の不具合とモデル化の誤りの区別、意図した変更後の更新方法を判断できなければならない。検証の対象コード一覧と同期コミットをSkillに記載し、対象コミットを変更するのは新しいコミットのコードを検証が正しく記述していると確認した後だけにする。このリポジトリの実際のコマンド、パス、名称を使い、プレースホルダーを残さない。

検査がTLA+モデルなら、次のエージェントにすべての結果をpstackの[`/statechart`](../statechart/SKILL.md) Skillで読むよう指定する。statechartは、チェッカーが検出した各不変条件違反までの最短経路を平易な言葉で示す。検査に成功した場合、`/statechart`はシステムが状態間をどう遷移するかの図を描く。`/statechart`を名前で参照する。コマンド、選択肢、ファイルパスはリリースやマシンによって変わるため、生成したSkillやスクリプトにコピーしない。

## 引き渡し前に実証する

生成したSkillを、次のエージェントと同じ手順で一度実行する。実際のコードの性質を破る一時的な変更を作り、検査にそれを検出させる。その後、一時的な変更を取り除き、検査が元の状態へ戻ったことを確認する。元の状態は合格か、報告予定の発見だけが残る失敗状態である。実行したことがない検証Skillは草案である。違反を見逃したり工程が動かなかったりした場合は、一時変更ではなくSkillまたは検証を修正する。

## 引き渡し

何を検証し、どのツールをなぜ選び、どの上限を使い、平易な言葉で何が見つかり、どう実行し、何を検証していないかをユーザーに伝える。近接する別の重要な対象が見つかった場合だけ、2つ目を提案する。コード変更後に再検証していない部分を同期させるための`/maintain-formal-verification-skill`を案内する。
