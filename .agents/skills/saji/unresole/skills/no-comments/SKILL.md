# コメントをなくす（No comments）

Comment Sickoを起動する。採用した指摘に対処する。

Comment Sickoの新鮮な視点を尊重する。

## 対象範囲

呼び出し元が指定したファイルまたは差分を使う。指定がない場合は、作業ツリーを含めて、既定では`main`をベースブランチとした現在の差分を使う。

## 工程

1. `subagent_type: "comment-sicko"`の`Task`を起動し、対象範囲を渡す。各サブエージェントの推論レベルは**poteto-mode** SkillのSubagentsセクションに従って選ぶ。Comment Sickoの規則を再記述しない。
2. 報告と差分を確認する。アプリケーションコードの編集、対象外への逸脱、例外で保護されたコメントの削除、`MUST KILL`の理由の誤表示、意図的に残したコードを問題だと扱う指摘を拒否する。自分たちのコードに対する予期しない挙動を指摘する`Reshape`は引き続き対応対象とする。それらのコメントを復元しない。維持すべきコメントは、自分たちで変更できないものに関するものだと証明できる場合だけ残す。対象範囲内のLintやTypeScript抑制の見落としも監査する。正しさや安全性に関する抑制は引き続き対処対象の`MUST KILL`となる。削除したコメントの復元は、正確な例外と対象範囲内の証拠がある場合だけ認める。根拠の薄い`IMPORTANT`や`do not remove`の削除・維持を認める前に、関連シンボルを追跡するか`/why`を実行する。削除判断が曖昧なら復元しない。維持が反証された、またはなお曖昧なら削除する。拒否した報告は元に戻し、拒否理由を示して1度だけ再実行する。2度目も拒否する場合は未解決と報告し、`/no-comments`を失敗にする。
3. 採用した軽微な指摘は、不要な経路の削除、引数の除去、正規APIの使用によって直接修正する。修正に構造の判断が必要なら、採用した指摘と周辺コードについて`/architect`を一度だけ実行する。概略設計で停止する。Architectは構造を決め、工程4が実装する。
4. 対象範囲内で最小の根本原因修正を実施する。指定された回避策をすべて取り除く。根本原因が対象外なら、対象内の最小修正だけを反映し、残りは未解決として報告する。**principle-fix-root-causes**と**principle-redesign-from-first-principles**は方針の理解だけに使う。どちらも対象範囲の拡大や、対象外の個別例の修正を許可するものではない。症状を覆い隠すガードを後付けしない。
5. 制約を示すコメントには`do not remove`、`do not change wording`、`talk to X before changing`などがある。変更できないものに関するコメントは維持する。対象範囲で最小コストの型・実行時チェック・テスト・CI Lintを提案する。対話的な承認を待つ。無人実行やEvalには呼び出し元による事前承認が必要。承認された場合は制約を機械的に実装してコメントを削除する。そうでなければコメントを削除し、強制されていない制約を未解決として報告し、対象外の作業を概略設計として示す。
6. 削除したコメント数、復元したコメント、再実行、Architectの概略設計、修正、構造化の提案、実施した構造化、強制されていない制約、その他の未完了作業を報告する。
