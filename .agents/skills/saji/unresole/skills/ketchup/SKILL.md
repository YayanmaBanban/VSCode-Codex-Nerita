# Ketchup

`/ketchup`の前にユーザーが最後に書いたメッセージ以降、このチャットで何が変わったかを伝え、現在の状態だけでなく変化の内容も理解できるようにする。続いてユーザーの判断を待つ項目をすべて挙げ、回答だけで判断できるようにする。通知やサブエージェントの結果はユーザーのメッセージではない。ユーザーが覚えているのは最後の自身の発言までで、その後は何も知らないと仮定する。

[`/bro`](../../../skills/bro/SKILL.md)の**話し方**を使い、そのタスクは実行しない。難しい言葉を使わず、短い文で、一人の人が別の人に状況を伝えるように話す。どのように実施したかではなく、ユーザーにとって何が変わったかを述べる。「CIがgreen」ではなく「テストが通った」と書く。判断に必要な場合を除き、ハッシュ、ファイルパス、コマンド、ビルド番号、テスト件数は省く。PR・ブランチ・エージェントには、作ったラベルではなくユーザーが知る名称を使う。事実の理解に文脈が必要なら、その文脈を付けるか事実を省く。

## 何が変わったかを集める

このターンは読み取り専用とする。図や画像はすでにある情報からだけ作る。コード変更、アプリやジョブの起動、外部への投稿をしない。ユーザーの最後の発言以降の自分の作業、サブエージェントからの報告、このチャットに参加した他者の発言を集める。このチャットで扱ったPR・CI実行・エージェントの現在状態を確認する。表示する数値は根拠の事実に照らして検証し、訂正したらその旨を伝える。

対応事項は製品上の判断、承認、不可逆な操作、権限不足など、ユーザーだけが実施できる判断や工程である。最後の発言以前に提示されたものでも、依然としてユーザー待ちなら含める。自分でまだできる作業は対応事項ではない。項目数を増やすために判断を作り上げない。ユーザーが求めておらず作業上も不要な工程は、不可逆な操作でユーザー待ちになっている場合を除き対応事項ではない。その場合は1行で示し、図を付けない。

一つの判断がマージ待ちPR群など複数の項目をまとめる場合もある。各項目についてリンク、利用者に何が変わるか、自分の推奨の根拠、リスク、推奨を集める。判断に必要な事実が不明なら「不明」と記す。存在しないリンクは省く。

## 回答を書く

経緯より判断事項に言葉を割く。画像を除き、経緯は100語未満とし、変化が少なければもっと短くする。ユーザーに変化のない作業は省く。判断事項は各項目およそ30語とする。回答の長さは項目数に合わせる。2項目なら画像を除き全体で150語より十分短く、30項目なら大幅に長くなる。語数を満たすために項目を省いたり短縮したりしない。項目数だけで一覧を代用せず、リンクだけで説明を代用しない。リンクには詳細を補足できるが、回答だけで判断できなければならない。

最初は、ユーザーの判断待ちの内容を一文で示すか、判断待ちがないと述べる。詳細は対応事項で説明する。何も起きず判断待ちもない場合は、その旨を伝えて停止する。

次に、何が起きたかを示す。最初に画像を置く。作業で得たスクリーンショットと動画を埋め込み、その後に変化を説明する図を置く。次に、ユーザーが依頼した事柄を一つずつ短い箇条書きにまとめる。結果と、完了・実行中・失敗・未検証のどれかを記す。各行は口頭で説明するように書く。「検索が遅かったのはインデックスがなかったから」であり、「検索レビュー：完了」「遅い検索：インデックス欠落」といった形にはしない。各行だけを読んでも正しい文にする。ユーザーの判断待ちがあるものは完了としない。対応事項で説明する内容はここに入れない。概要の下に、ユーザーが知ることや行うことを変える短い行を最大3行置く。その後、自分でまだ行える作業を1行で示す。

最後に対応事項を列挙する。マージ・承認・選択など、ユーザーが行うべき判断を質問し、自分の推奨を示す。先に必要な作業も、実行前提や取り消せない内容も推奨へ含める。PR・課題・エージェントに関する判断には、それぞれの番号かリンクを付ける。複数案の選択でも同様にする。

判断内容に合った形式を使う。一つの対象についての判断なら箇条書き1件に、判断内容、推奨、利用者への変化、根拠、リスクを記載し、対象名は一度だけ示す。複数項目で判断を共有するなら、判断と推奨を一度書き、その下に各対象の項目をリスクの高い順で並べる。各項目にリンクと名前、利用者への変化、推奨の根拠、リスクを記載する。推奨が全体のものと異なる場合だけ個別の推奨を記す。低リスクでも「低リスク：色だけが変わる」などと示す。待つことで単なる遅延を超える損失（期限やデータ消失など）がある場合だけ、待つコストも述べる。

選択肢間の判断では、検討したすべての選択肢について、ユーザーが得るもの、コスト、存在する場合は現在の状態を示す。各選択肢のコストが判断のリスクに当たるので、別のリスク行を追加しない。上のスクリーンショットに選択肢が写っている場合は、各案の利点とコストをその画像の下へ記載する。

## 図と画像（Visuals）

Visualは写真や図である。スクリーンショット、動画、Mermaid図、`/visualize`によるチャート・図、生成画像などが該当する。Markdownの表は変更前後の列があってもVisualではない。

文で説明するより画像の方が分かりやすいものは図にする。設計・システムの仕組み、各PRの状態が付いたPRスタックや依存関係、修正前後の比較、選択肢の並列比較などが該当する。状態の一覧、対応事項の一覧、つながりのない箱の集まりは図にしない。同じ事実を文章と図、または複数の図で重複して示さない。

各図は一目で読めるよう小さくする。箱は最大6つ、箱ごとの文字数は最大8語とする。ラベルは「Tests: pass」のようなタグではなく、人が口にする平易な言葉にする。一文で説明すべき事実は文章へ置くか省く。

目に見える変更では、スクリーンショットや動画をリンクだけにせず文中に埋め込む。画像がない場合は概要行に「No screenshot yet」と記し、画面の何が変わったかを説明する。図とチャートは既存の事実から作る。接続関係にはMermaid図、数値には`/visualize`チャートを使う。数値を作り上げず、取得していない画面を描いたり生成したりしない。実在する成果物だけへリンクする。
