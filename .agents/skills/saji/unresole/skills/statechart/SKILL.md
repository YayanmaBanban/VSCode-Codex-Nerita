# Statechart

この図は、読む人の言葉でシステムが状態間をどう動くかを示す。振る舞いが正しいかは、その図を読む人が判断する。

## 実行（Run）

リポジトリ外の一時ディレクトリで作業する。TLA+の仕様と設定を記述してから、次を実行する。

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts`はTypeScriptなので、TypeScriptを実行できるランタイムを使う。`scripts/statechart`はランタイムを選ぶPOSIXシェルスクリプトである。ネイティブWindowsでは、Node 22.18～22.x、またはNode 23.6以降を使い、`node --disable-warning=ExperimentalWarning <skill dir>/scripts/statechart.ts`を実行する。

初回の実行ではmiseを使ってTLCとJavaをインストールし、ネットワークが必要となる。

## 仕様を書く（Write the spec）

- 読み手が合意する各規則を`INVARIANT`として記載する。画面、結果、保存値、メッセージに関する規則でもよい。規則を表す変数がモデルになければ追加する。成立させるために規則を弱めない。
- `Next`を、`YouPressPlay \/ YouPressStop`のような操作の選言として記述する。そうしなければTLCはすべての工程を`Next`と名付ける。
- 出口のない状態は、正しい終了状態であっても`NoDeadlock`に違反する。`INVARIANT`や`PROPERTY`にその名前がすでにある場合は、規則が`CHECK_DEADLOCK`となる。終了状態だけで成立し、状態を変えない操作、例えば`Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`を`Next`へ追加し、`step()`でラベルを付ける。

## 図を選ぶ（Pick the chart）

状態と矢印の言葉、フェーズとその色、タイトル、読者への報告など、判断が必要な部分を担当する。viewモジュールへ記述し、`--view`で渡す。

読む人の言葉で示すため、viewは`state(vars)`をexportする。`state()`が返す型によって図の形式が決まる。

- 文字列は平坦な図：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 配列は親状態：`export const state = (v) => v.main.split(".");`
- オブジェクトはキーごとに並列領域：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

各状態には「Paying」「Lease held, write pending」など、読む人が観測できること・関心のあることを付ける。変数名をラベルに入れない。`vars`に含まれるTLA+のsequenceは1から始まるキーを持つオブジェクトなので、`v.pc[1]`は`pc[1]`に対応する。setは配列になる。

viewは`step(action, from, to)`もexportできる。TLCの操作名とその前後の値を受け取り、矢印のラベルを返す。各ラベルは「you press play」「the connect fails」など、利用者が起きたと認識する言葉にする。コードやTLA+の操作名にしない。図の中で同じ結果になる2つの操作には同じラベルを付け、1本の矢印を共有させる。

工程が一部の条件でしか起きない場合は、`you press play [while the file loads]`のように、読む人の言葉で条件を角括弧に入れ、ラベルの末尾に付ける。並列領域の図では、コマンドがほかの領域の状態による条件を、`[when Offline]`などのように矢印上へ書く。自分で付けた角括弧がそれに優先するため、一つの状態から出る2本の矢印が同じに見えることがある。このため、並列領域の図では、ほかの領域による条件を自分で角括弧に書かない。ラベルに表示されない値が遷移先を決める場合は、「the roster read fails」のように結果をラベルに含める。

viewは次のものもexportできる。

- `group(vars)`はフェーズ名を返す。図の各状態は属するグループの色になる。一つの図の状態に対応する複数のモデル状態が異なるグループなら、その状態に色は付かない。
- `colors`はグループ名ごとに色のclassを指定する。
- `title`は図の上部に表示する文字列である。

コマンドはモデル状態ごとに`state()`と`group()`を最大1回、工程ごとに`step()`を最大1回呼ぶ。図と報告は同じ返答値を使う。そのため各関数は引数だけに依存するようにする。

同じラベルに留まる工程は図に描かれない。読み手がその工程を見る必要がある場合はラベルを分ける。

矢印は約20本以下を目安とする。それより多い図は読みにくい。最初に`state()`から粗いラベルを返す。同じように振る舞う値には一つのラベルを与え、結果に影響しない実行中の通信など、読者に不要な細部は省く。ただしバグに至る各状態と、各規則違反の印は保持する。統合によって`breaks`状態が`mayBreak`になった場合は、規則を破る場所が見えなくなる。異なる規則を破る2つの状態を統合してはならない。どの規則がどこで破られるか分からなくなるためである。それでも図が複雑すぎる場合は、全状態に存在するreset操作や、ほかの矢印と同じことを示す工程など、不要な工程について`step()`から`null`を返す。工程を非表示にする場合は、以下の規則を守る。

- 図のすべての状態に、開始状態から矢印をたどって到達できるようにする。
- モデル上で出口のある状態には、図でも最低1本の出る矢印を残す。
- 一つの矢印に対応する工程は、すべて非表示にするか、すべて表示する。一部だけ隠すと、その矢印の条件が狭くなる。
- 引き渡し時には、図で隠した工程を伝える。

## 報告を読む（Read the report）

- 図で規則に違反する状態のclassは`breaks`。その図の状態に対応するモデル状態の一部だけが違反するなら`mayBreak`。Legendには各印の規則名が書かれる。2規則を破る場合は一つの印に両方が記載されるため、どの状態がどの規則を破るか引き渡し時に説明する。並列領域の図では、ある領域の状態を含む状態の組み合わせのいずれもが規則に違反し得るとき、その状態に印を付ける。規則違反を起こし得る組み合わせに印付き状態が一つもなければ、組み合わせ中の各状態に印を付ける。
- TLCは規則に違反した状態の先も探索するため、図はバグの後の状態も示す。
- TLCがバグの後も探索するため、状態数が無制限のモデルは終了しないことがある。定数を小さくするか、`CONSTRAINT`を追加する。
- `VIEW`または`SYMMETRY`を使うと、TLCが同じだと扱う状態は1状態として数えられ、図にもその1状態だけが描かれる。矢印は実際の遷移先ではなく同一視した状態へ向く場合があり、報告にはその旨が記載される。
- TLCは`CONSTRAINT`または`ACTION_CONSTRAINT`の範囲外となった状態についても規則を検査するが、その状態から先を探索せずデッドロックも検査しない。規則違反までの最短経路がそのような状態で終わる場合、図はその状態を描き、報告に経路を示す。ただし境界の外側のその他の状態は描かず、そこにあるデッドロックも表示しない。`ACTION_CONSTRAINT`で除外する工程の後も規則を検査する。別経路で次の状態に到達する場合も同様である。最短経路がその工程で終わる場合は、図にその工程を描く。
- コマンドは設定ファイルを記載どおりに使用し、1ワーカーのTLCで規則を検査する。違反した規則がある場合、その規則を除いて再実行し、違反がなくなるまで繰り返す。最初の違反が見つかった後の各実行は、異なる状態数が100,000に到達した時点で停止する。大きなモデルが終了しなくなるのを防ぐためである。上限に達した、またはエラーで停止した場合は、未検査の規則を報告の`Rules not checked`へ列挙し、図には印を付けない。未検査の規則は成立するかもしれず、破れるかもしれない。調べるには設定から違反規則を除くかモデルを小さくする。上限処理はTLCの変数順を変えるモジュールを追加するため、PROPERTYでは制限なしの実行とは異なる反例になる場合がある。
- `tlc.out`は元の設定でTLCが出力した内容である。図に規則違反の経路が出ない場合、`tlc-RULE.out`はその規則の違反を見つけた実行のTLC出力である。TLCが初回の警告を繰り返した場合、素のTLCでは2回表示されるが、`tlc.out`には1回しかない。このコマンドが読む出力から2回目が省かれるためである。これはJavaで`-XX:+UseParallelGC`を使った場合だけ起きる。使わない場合、TLCの最初の警告はそのフラグを指定する勧告であり、1回しか表示されない。

## 図を提示する（Show the chart）

`chart.mmd`をMermaidコードブロックでユーザーに示す。図の状態数の上限は、元の設定をTLCで数えた500状態である。それを超える場合は規則違反までの経路だけを描き、規則違反がなければ`chart.mmd`を書き出さない。それでも各規則は検査され、報告に状態数と各バグ経路が示される。全状態の図が必要ならモデルを小さくする。

図の描画にはPeleを使う。ユーザーが画像を求めた場合、または図が大きすぎてテキストでは読めない場合は`references/render.md`に従う。ユーザーが別のレンダラーを指定した場合を除き、別のものを使わない。

## 引き渡し（Hand off）

図とMermaidの本文を判断担当者へ渡す。バグごとに、規則、読み手の言葉によるその規則の説明、報告にある番号付きの経路を1行で示す。モデルが省いた内容を説明する。同じファイルを再生成するコマンドは、新しい`--out`フォルダを指定して示す。

モデルが実際のコードを記述している場合は、各バグ経路を実コードに対して再実行する。各操作を1段階として、テストまたは動作中の再現で確認する。バグが再現しなければ、モデルが間違っている可能性を優先して考える。モデルが正しいと証明できるまでは、その考えを維持する。
