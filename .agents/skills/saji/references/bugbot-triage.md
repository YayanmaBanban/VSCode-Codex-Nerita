# Bugbotのレビュー指摘を分類する

Babysit Playbook（`../playbooks/babysit.md`）がBugbotや自動レビューツールのコメントを扱う際に参照する。目的はBugbotを最初から無視することではない。すべてのコメントを必須のコード修正として扱うのをやめることである。

## 判断基準

各Bugbotスレッドに対応する前に、次のいずれかへ分類する。

- `fix`：正しさ、セキュリティ、プライバシー、データ消失、認証、課金、移行、冪等性、競合、出荷後の振る舞いについて、もっともらしい問題が指摘されている。最も下位で責務を持つPRで修正し、コミットSHAを返信してスレッドを解決する。
- `dismiss`：文書化された低リスクの誤検出パターンに一致し、現在のコードと文脈により修正不要であると証明できる。短い理由を返信し、スレッドを解決する。
- `ask`：新規の指摘、重大な指摘、セキュリティ・プライバシー・データに関する指摘、または曖昧な指摘。推測で決めずユーザーに確認する。

迷ったら確認する。騒がしいコード品質指摘を飛ばすコストは小さいが、実際のデータ・セキュリティ上の問題を飛ばすコストは大きい。

## 学習したパターンの記録形式

新しいパターンは次の形式で追記する。

```markdown
### <short pattern name>

- Confidence: candidate | recurring | strong
- Skip when: <conditions that must be true>
- Do not skip when: <risk boundaries>
- Example signal: <phrases or code context that identify the pattern>
- Source: <PR/comment URL or short historical note>
```

`candidate`は1～2例の場合に使う。`recurring`は実際の指摘を複数回妥当に却下できた場合に使う。`strong`は、対象が狭く、何度も検証済みで、リスクが低い場合だけ使う。

## 繰り返し現れるスキップ候補

### 意図的なUI・デザインシステムの外観変更

- **確信度：** `candidate`
- **スキップできる条件：** PR説明、スクリーンショット、デザインレビュー、周辺コードから外観変更が意図的だと明らかで、Bugbotコメントが共有の外観既定値の変更を言い直しているだけの場合。
- **スキップしてはならない条件：** アクセシビリティ、フォーカス可視性、キーボード操作、色のコントラスト、PRが意図していないコンポーネントAPI契約に関する指摘。
- **指摘の例：** フォーカス枠、ボタンサイズ、余白、共通コンポーネントの外観既定値について、所有者が「意図どおり（intentional/intended）」と回答しているコメント。

### Bugbotから見えない上位スタック・スタック内の利用

- **確信度：** `candidate`
- **スキップできる条件：** Bugbotがexport、コンポーネント、補助関数、ファイルを未使用と指摘しているが、現在のForgeのPR一覧・差分、上位スタックの差分、PR文脈から後続PRで使われていることが確認できる場合。
- **スキップしてはならない条件：** 現在のPRがスタックの一部ではない、対象が公開API、または上位スタックでの使用を検証できない場合。
- **指摘の例：** 「エクスポートしたコンポーネントは一度も使われない」に対し、人間が「上位スタックで使用している（used upstack）」と回答。

### 並列実装中に生じる一時的な重複

- **確信度：** `candidate`
- **スキップできる条件：** 削除・置換・検証を進めている旧経路と新経路を並行して維持するため、PRが意図的に少量のコードを重複させている場合。
- **スキップしてはならない条件：** 重複したコードがセキュリティ、課金、データアクセス、APIの振る舞いを変更する、または長く維持する共有抽象化によって明確にリスクを下げられる場合。
- **指摘の例：** 「大きな重複」「検証ロジックの重複」に対し、旧経路を削除予定である、または意図的に局所的な重複を維持したと所有者が説明。

### 既存フレームワークや共有コンポーネントの不変条件で保証済み

- **確信度：** `candidate`
- **スキップできる条件：** 問題のないことが、共有コンポーネントの規則、フレームワーク契約、型の不変条件、単一の正本により、現在の差分や周辺コードで実際に保証されている場合。
- **スキップしてはならない条件：** 不変条件が仮定だけで強制されていない、タイミングに依存する、非同期・状態境界を越えて値が食い違う可能性がある場合。
- **指摘の例：** 共有popoverが画面の境界を強制しているのに内側のpopoverにmax-heightがないという指摘、またはnull許容値についてチェック済みの値と引数に渡した値が同じ正本に由来する場合。

### 所有者が宣言した後続対応・延期された整理

- **確信度：** `candidate`
- **スキップできる条件：** PR所有者が既知の後続対応であると明示し、現在のPRによって振る舞いが悪化せず、高リスク領域でもない場合。
- **スキップしてはならない条件：** エージェントが所有者の見解なしに判断している、製品の振る舞いに中～高程度の影響がある、または延期すると新しい回帰をマージしてしまう場合。
- **指摘の例：** 「これは後で対応する」「いずれ削除する」といったコメント。

### 指摘自身の取り下げ、明示された誤検出

- **確信度：** `recurring`
- **スキップできる条件：** 指摘本文または後続のBugbot返信で、問題が取り下げられた、規則に適合している、誤検出だったと明言されており、関連する規則をエージェント自身がローカルで検証できる場合。
- **スキップしてはならない条件：** 高リスク問題について、人間が説明なしに「誤検出」と言っていることだけが根拠の場合。
- **指摘の例：** ファイル名規則に関するコメント本文に、そのファイルがすでに規則に適合していると書かれている場合。

## 既定で確認を求める指摘

過去のPRで似た指摘を却下したことがあっても、次の分類を自動的にスキップしない。

- セキュリティ、プライバシー、認証、課金、データ保持、学習データ、権限境界に関する指摘。
- 重大度の高い指摘。
- 移行、スキーマ、冪等性、並行処理、システム間の振る舞いに関する指摘。
- 提案された修正が小さく、製品の意図を変えず、明確にリスクを下げる指摘。

過去の記録では、セキュリティやデータフローの指摘を人間が却下する場合もあった。これらは所有者自身の判断であり、チーム全体のスキップ規則にはしない。

## 最近のBabysitから得た候補

チームで共有する価値がありそうだが確立していない知見は、Babysitの最中または後にここへ追加する。複数のPRで確認できた候補は、上の繰り返しパターンへ昇格することを優先する。

### ブラウザー標準の動作を手作業で再実装した場合

- **確信度：** `candidate`
- **スキップできる条件：** 事実上ほとんどない。差分がブラウザーの標準動作を独自実装で置き換える場合（標準のsticky → JSで位置付けた複製、標準のスクロール位置への移動 → wheel/touchイベント転送、描画順による遮蔽 → mask/clip-path）、そのコードに関するBugbotのロジック不具合指摘は継続して正当だった。
- **スキップしてはならない条件：** wheelの`deltaMode`、タッチでの移動、端でのスクロール連鎖、タップの許容移動量（tap slop）などのイベント転送の欠落、mask/clipとhit-testingの不一致、observerとReact状態のタイミング競合を指摘された場合。既定では修正する。
- **指摘の例：** 「maskはhit-testingに影響しない」「overlayがwheelスクロールを阻害する」「deltaModeを無視する」「Reactが状態を適用する前にIntersectionObserver callback内で実行される」。
- **出典：** stickyによる遮蔽を扱った一つのPR。Bugbotが6回確認し、およそ18件の指摘があり、すべて却下ではなく修正された。

### 契約テストと文書のずれは安価に実証できる。まずテストを実行する

- **確信度：** `candidate`
- **スキップできる条件：** 検証そのものは絶対に飛ばさない。1コマンドで済むため。PRがプロトコルや文書の文章を固定する契約テスト（`SKILL.md`への正規表現、文言のスナップショットなど）を含み、Bugbotが「テストと文書が一致しない」（または逆）と主張したら、分類の前にPRのheadでテストを実行する。失敗すれば主張の実証になり、成功なら却下するための具体的な反証になる。
- **スキップしてはならない条件：** 該当なし（`n/a`）。これは却下パターンではなく、検証の近道。繰り返しの指摘を軽く却下する判断はここでは誤る。文章を固定するテストは、以前の修正で文章が編集された**からこそ**ずれるためである。
- **指摘の例：** 以前の修正コミットで対応する文章が書き換えられていたPRに対する「契約テストが修正前のwaitを省いている」。PRのheadでテストを実行すると、まさに指摘されたアサーションで失敗した。
- **出典：** 文章固定テストを含む一つのPR。Bugbotが8回確認し、以前の回はすべて修正・解決されたにもかかわらず、7回目の指摘は実際の問題だった。

### 同じPR内の後続コミットで修正済みの古いセキュリティ指摘

- **確信度：** `candidate`
- **スキップできる条件：** エージェントによるセキュリティレビューなどが認可・検証呼び出しの欠落を指摘したが、現在のPRのheadには、指摘された正確なゲートがテストとともに明確に存在する場合。通常はレビュー後に追加された堅牢化コミットによる。
- **スキップしてはならない条件：** 指摘対象のprincipalに対して補助関数が何もしない、守るべき副作用の後にチェックが実行される、または対象principalの検証が不足している場合。
- **指摘の例：** 重大度HIGHの「認可チェック欠落」指摘だが、現在のheadでは副作用より先に正確なガードがすでに呼ばれている。
- **出典：** レビュー実行後に堅牢化コミットが追加されたWebhookエンドポイントのPR一件。

### 意図的に限定したエラー条件を拡大すると本当のエラーが隠れる

- **確信度：** `candidate`
- **スキップできる条件：** 特定の`errno`、エラーコード、ステータス分類などに限った狭いエラー条件を、あらゆるエラーを捕捉する形へ拡張するよう求められ、元の限定に意味がある場合。典型例は`ENOENT`に限定した依存ツールのフォールバック。「バイナリがインストールされていない」と「コマンド自体は実行されたが失敗した」は別の状況である。すべての非ゼロ終了コードで再試行すると、正当な失敗（対象がない、認証期限切れ、ネットワーク障害など）に対してフォールバックを実行し、元の真のエラーを隠してフォールバック側のエラーだけを報告してしまう。
- **スキップしてはならない条件：** 狭い条件が**同じ分類**の失敗を取りこぼす場合（`EACCES`など別の「バイナリが使用できない」`errno`や別の通信層の障害）、未処理経路によってデータ消失や不完全な状態が生じる場合、または再試行が冪等であり元のエラーも報告される場合。
- **指摘の例：** 「XがENOENTで失敗したときだけ再試行し、動作可能なYが存在してもフォールバックを試さない」という指摘。ただしコードのフォールバックは操作失敗ではなく、依存バイナリの欠落に対応するために存在していた。
- **出典：** CLIの名前変更を扱うPR一件。フォールバックはコマンド実行失敗ではなく、バイナリ欠落に備えたものだった。
