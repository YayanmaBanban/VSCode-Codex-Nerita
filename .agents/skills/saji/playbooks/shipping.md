### 出荷（Shipping）

**マージされる内容に責任を持つ。各PRを独立に検証し、スタックの根元から検証済みの連続部分だけをマージする。処理中のスタックへ余計な変更を加えない。** マージ・ベース変更・リベース・Pushには、その操作についてユーザーの明示的な許可が必要。許可がなければ検証結果だけを報告し、Gitの状態を変更しない。

1. **GitHub上の各PRをマージ前に独立検証する。** `gh --version`と`gh auth status`でGitHub CLIを利用できることを確認する。利用できなければPRの出荷処理を止め、未実行と報告する。PRごとにコードを書いた担当とは**別の検証担当**を一人割り当てる。検証担当はPRのベースとheadを比較し、Web UIならPlaywrightなど実際の画面操作、CLIなら実コマンドと終了コードによって利用者と同じ操作で検証する。検証対象のSHAと実行ログ・スクリーンショットを根拠に、`PASS`、`PASS+NOTES`、`FAIL`のいずれかを報告する。レビューコメントの書き込みを許可されている場合のみPRへ投稿する。独立した担当者を起動できないなら、独立検証が未完了なので合格判定を作らない。CI成功やBotによる承認だけを独立判定の代わりにしない。
2. **根元から連続して検証済みの範囲だけをマージする。** 未マージPRの最下段から上へたどり、`PASS`または`PASS+NOTES`がない最初のPRで停止する。それより下がマージ可能な連続範囲で、停止したPRが上限となる。未検証PRより上の検証済みPRは待機する。下にあるコードなしではマージできないからである。ただし、そのコードを含まず、必要ともしないPRはtrunk上へ移し、単独でマージしてよい。その場合、以前の判定は下位コードが存在する状態での検証なので、まず新しい判定を得る。
3. **判定が現在のコードにも有効か再確認する。** 判定は一つのパッチに対応する。連鎖したリベースでは、チェックに失敗しなくても上位PRが新しいSHAになる。古い判定を信用する前に、判定対象SHAと現在のheadの`git patch-id`を比較する。差分がテスト・文書・Lint設定だけの場合、両SHAで実行されるビルドがノイズを除き同じなら、その検証系列（lane）の判定を引き継げる。ノイズとは、判定対象SHAを2回ビルドしても現れる差異、または埋め込まれたコミットSHAによる差異。ノイズの種類と対象ファイルをそれぞれ報告し、第三者が判断を確認できるようにする。**変更自体**には新しいチェックとレビューが必要。古い判定はその変更を見ていない。開発サーバーなどビルド成果物を出さない検証系列は同一性を示せないので再実行し、そのほか変化したものも再検証する。
4. **下から上へ、一度に一つずつマージする。** マージの明示的な許可がある場合だけ、検証済みの連続範囲の最下段のPRを`gh pr merge <pr> --squash`でマージする。PRのベースが親PRのブランチであれば、trunkではなくそのブランチへマージされるため、マージ前に`gh pr view <pr> --json baseRefName,headRefName,state`でベースを確認する。コマンドが成功と表示されても、キュー登録や自動マージ要求に過ぎない場合があるので、必ず`gh pr view <pr> --json state,mergedAt,baseRefName`で実際にマージ済みか確かめる。trunkをベースにしてmergedとなった場合にのみtrunkへの着地と判定する。`gh pr merge <pr> --auto`は現headに対する有効な独立判定があり、自動マージについても明示的に許可された場合だけ設定する。下位PRがマージされた後で上位PRのベースが下位ブランチになっていたなら、ベース変更とPushを明示的に許可されている場合だけ`gh pr edit <pr> --base <trunk>`でtrunkへ変更し、そのマージ結果へパッチを移し、現行remote SHAを確認した`git push --force-with-lease`で公開する。手順3のpatch-idで旧判定の有効性を確認し、チェックが通ったPRだけ順にマージする。権限がなければマージ後の追加変更を止めて状況を報告する。
5. **マージ処理中はスタックに触れない。** 手順4に記載した次PRの移動以外はブランチやベースを変更しない。実際にマージされるのはその瞬間のheadとベースの内容だからである。GitHubでは対象のPR番号を下から上へ保持し、`gh pr checks <pr> --watch`でチェック終了を待ち、終了後に`gh pr view <pr> --json state,mergedAt,baseRefName`で再確認する。連続範囲の上限がmergedになるまで、**実際に実行できるセッション内**でこれを繰り返す。継続して実行・監視する仕組みがなければ、最後に確認できた状態までを報告し、監視を続けているとは主張しない。親PRのマージに伴うベースのtrunkへの移動は正常であり、それだけを異常として修正しない。停滞したら原因を調べてから変更する。
6. **上限で停止する。** 連続範囲の拡張には新しい判定が必要なので、手順1から改めて実行する。

**回答：** 検証済みの連続範囲と上限、各PRの判定と判定者、実際にマージされたものとその確認方法、次の未解決箇所で必要な対応を示す。
