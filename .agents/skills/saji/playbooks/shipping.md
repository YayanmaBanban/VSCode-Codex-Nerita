### 出荷（Shipping）

**マージされる内容に責任を持つ。各PRを独立に検証し、スタックの根元から検証済みの連続部分だけをマージする。処理中のスタックへ余計な変更を加えない。**

1. **利用するForgeを決め、各PRをマージ前に独立検証する。** 既定はGitHub CLI（`gh`）。`command -v origin`が成功し、Originがリポジトリを解決できる場合は、すべてのPR操作に`origin pr`を使う。そうでなければ`gh`を維持し、代替したことを記録する。Graphite（`gt`）を必須にしない。PRごとに独立した検証担当を一人割り当てる。原文では各担当はCursorのクラウドエージェントであり、対象のcontrol Skill（例：`cursor-team-kit`の`control-ui`、`control-cli`）を用いて、親とheadを比較し、利用者と同じ手順で変更を実行する。そしてPRに`PASS`、`PASS+NOTES`、`FAIL`のいずれかを投稿する。コードを書いていないエージェントの判定だけを採用する。作者は「自分が作るつもりだったもの」を確認しがちだからである。CIが正常でもBotが承認していても、利用者と同じ操作で検証した判定の代わりにはならない。
2. **根元から連続して検証済みの範囲だけをマージする。** 未マージPRの最下段から上へたどり、`PASS`または`PASS+NOTES`がない最初のPRで停止する。それより下がマージ可能な連続範囲で、停止したPRが上限となる。未検証PRより上の検証済みPRは待機する。下にあるコードなしではマージできないからである。ただし、そのコードを含まず、必要ともしないPRはtrunk上へ移し、単独でマージしてよい。その場合、以前の判定は下位コードが存在する状態での検証なので、まず新しい判定を得る。
3. **判定が現在のコードにも有効か再確認する。** 判定は一つのパッチに対応する。連鎖したリベースでは、チェックに失敗しなくても上位PRが新しいSHAになる。古い判定を信用する前に、判定対象SHAと現在のheadの`git patch-id`を比較する。差分がテスト・文書・Lint設定だけの場合、両SHAで実行されるビルドがノイズを除き同じなら、その検証系列（lane）の判定を引き継げる。ノイズとは、判定対象SHAを2回ビルドしても現れる差異、または埋め込まれたコミットSHAによる差異。ノイズの種類と対象ファイルをそれぞれ報告し、第三者が判断を確認できるようにする。**変更自体**には新しいチェックとレビューが必要。古い判定はその変更を見ていない。開発サーバーなどビルド成果物を出さない検証系列は同一性を示せないので再実行し、そのほか変化したものも再検証する。
4. **下から上へ、一度に一つずつマージする。** 連続範囲の最下段の未マージPRを、`origin pr merge <pr>`または`gh pr merge <pr> --squash`でマージする。Originの単純なmergeコマンドは指定したPRより下のPRもすべてマージする。一方GitHubでは、PRのベースが親PRのブランチのままならtrunkではなくそのブランチへマージされる。コマンドの実行後は必ず`origin pr view <pr>`または`gh pr view <pr> --json state,mergedAt,baseRefName`で状態を再取得する。マージキューへ登録しただけでも成功と表示される場合があり、自動マージの要求もマージ済みとは限らない。実際にマージされたPRは、ベースが親ブランチではなくtrunkになった状態でmergedと表示される。`--auto`（Originのmerge-when-readyまたはGitHubのauto-merge）は、その時点のheadに対して有効な判定があるPRだけで設定する。条件成立時に何であれheadをマージするためである。マージ後、ベースがマージ済みブランチだった次のPRのベースをtrunkへ変更（`origin pr edit <pr> --base <trunk>`または`gh pr edit <pr> --base <trunk>`）し、パッチをそのマージ結果の上へ移動して`--force-with-lease`でPushする。判定の対象はコミットではなくパッチなので、手順3のpatch-id規則で以前の判定が有効か決める。チェックが通り判定が有効ならマージする。
5. **マージ処理中はスタックに触れない。** マージ時にはその瞬間のブランチとベースの内容がマージされるため、手順4で次のPRを移動する場合以外はブランチやベースを変更しない。判定の有無ではこの危険性は変わらない。GitHubでは`/loop`から`scripts/watch-pr/watch-pr --queued-stack`を使い、連続範囲の上限で`COMPLETE`が報告されるまで監視する。`--stack-prs`へ下から上のPR番号を渡し、監視ツールの再起動でも毎回同じ一覧を使う。Originでは`origin pr checks <pr> --watch`が終了するたび`origin pr view <pr> --checks`で状態を再取得し、上限のPRがmergedになるまで続ける。親PRのマージに伴ってベースがtrunkへ移るのは正常であり、修正するべき異常ではない。マージが停滞したら、変更に着手する前に理由を調べる。
6. **上限で停止する。** 連続範囲の拡張には新しい判定が必要なので、手順1から改めて実行する。

**回答：** 検証済みの連続範囲と上限、各PRの判定と判定者、実際にマージされたものとその確認方法、次の未解決箇所で必要な対応を示す。
