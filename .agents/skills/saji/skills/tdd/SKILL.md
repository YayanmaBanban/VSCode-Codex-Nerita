# TDDによるバグ修正

明確で安価なテスト手段があるバグ修正では、製品コードを変更する前に、壊れた振る舞いを実行できる形にする。目標は、修正前には失敗し、修正後には成功する、対象を絞った回帰テストである。

現実的でないテストを強制しない。利用できるテストのために広範な検証環境の構築、壊れやすいモック、遅いエンドツーエンド基盤、本番にしかない状態、曖昧な再現手順、大量の無関係なフィクスチャ変更が必要なら、新しいテストの追加を省き、代わりに最も近い有用な検証を使う。

## 作業手順

1. **バグを理解する。** 意図した振る舞い、現在の振る舞い、影響する経路、観測可能な最小の再現方法を特定する。
2. **実行できる最も狭い検査を選ぶ。** そのコード経路で既に使用されている単体・コンポーネント・結合・回帰テストのうち、最も近いものを優先する。実用的なテスト経路が明白でなければ、手順を満たすためだけにゼロから作らない。
3. **最初に失敗するテストを書く。** バグを検出できたはずの最小で対象を絞ったテストを追加する。現在の実装をなぞるのではなく、意図した振る舞いを表現する。
4. **修正前に新しいテストを実行する。** 意図した理由で失敗することを確認する。成功したり無関係な理由で失敗したりした場合は、実装を編集する前にテストまたは再現条件を修正する。
5. **バグを直す。** 周辺の契約を保ちながら、意図した振る舞いを満たす最小の製品コードの変更を行う。
6. **回帰テストを再実行する。** テストが成功することを確認する。

## 失敗テストが現実的でない場合

代わりに、実行できる最も近い回帰検査を使う。対象を絞ったスクリプト、手動の再現コマンド、ブラウザー自動化、スナップショット比較、ログのアサーション、対象を絞った結合検査などが該当する。

悪いテストを追加するより新しいテストを作らない方を優先する。悪いテストとは、ほぼモックだけを検証する、現在の実装詳細を固定する、タイミングや無関係なグローバル状態に依存する、小さな修正のために高価な基盤を必要とする、または修正の証明後すぐに削除するようなテストである。

## 守る条件

- 間違った実装に合わせるためだけにテストを変更しない。
- 期待する振る舞いが本当に変化し、その理由が明らかな場合を除き、既存のアサーションを弱めない。
- 回帰テストをバグに集中させる。フィクスチャを大幅に変更したり、無関係な範囲へ検証を広げたりしない。
- バグが不安定にしか発生しない場合は、可能な範囲でテストを決定的にし、固定したいシグナルを記録する。
- バグがより広い種類の故障を示す場合は、まず対象を絞った回帰経路を反映し、その後で関連ケースの追加を検討する。

## 最終報告

結果だけでなく証拠を報告する。

- 修正前に失敗したテストまたは実行検査の名前と、その失敗内容を示す。
- 修正後に成功したテスト実行と、周辺で行った検証を示す。
- 修正前の失敗を実証できなかった場合は、その理由と、代わりに使用した最も近い回帰検査を説明する。
