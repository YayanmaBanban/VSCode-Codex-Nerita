# コード構造

モジュール・パッケージ間の依存や公開境界の変更、ファイルの追加・移動・分割、共通化の判断時に参照する。具体的な配置と層の役割は、対象プロジェクトのディレクトリ構成・アーキテクチャの規約に従う。

## 依存方向

- 循環依存を作らない。循環が生じる場合は責務と依存方向を見直し、契約の分離、依存の受け渡し、共通処理の抽出などで解消する。
- 上位層を再利用するために下位層から逆向きにインポートしない。上下の関係は、対象プロジェクトで定めた依存方向に基づいて判断する。
- 共通処理の再利用は、既存の責務境界と依存方向に従う。直接参照が逆向きの依存や不要な結合を生む場合は、両方が参照でき、既存の責務境界と依存方向に沿う場所へ分離する。
- 製品コードからテスト・Storybook・検証データ・モック・一時検証コードをインポートしない。
- テスト支援コードは、検証対象の既存の型・契約を利用する。テストの都合だけで製品コードの公開範囲を広げない。配置も製品コードから参照されないようにする。

## モジュール境界

- UI・Host・バックエンドなど、対象プロジェクトで定められた責務境界を維持する。
- プラットフォーム固有 API は、そのプラットフォームを担当する層に閉じ込める。
- 型や定数を共有するためだけに、本来不要な上位モジュールへの依存を追加しない。
- 型・定数・契約の配置は、それを所有する責務に基づいて決める。利用回数や見た目だけで共通化を判断しない。役割と変更理由が共通かを確認する。共通の責務が明確でなければ機能側に置き、複数機能から使うという理由だけで共有層へ移さない。
- 複数モジュールのエクスポートを1つの入口にまとめる場合は、公開境界を簡潔にする目的で行い、循環依存を隠すためには使わない。

## ファイルの配置と分割

- 小規模な機能は同じフォルダにファイルを並べる構成から始め、責務やファイル数が増えたら責務別のフォルダを検討する。空の分類フォルダや、意味のない階層・再エクスポートファイルを増やさない。
- 1ファイルには1つの主要な責務を持たせる。異なる理由で変更される処理、独立して名前を付けられる責務、異なる外部依存を持つ処理は分離を検討する。
- 小さな型・定数・補助関数は、利用箇所が限定される場合は無理に別ファイルへ分離せず、利用側の近くに置く。
- 異なる機能に同名のファイルがあってもよい。ファイルの役割は、ファイル名と配置先のパスを合わせて判断する。
- 共有だけを目的とした細かなファイル分割によって、処理を追うための移動が増えないようにする。
- 1ファイル200〜300行程度を見直しの目安とし、超える場合は責務の混在と処理の追いやすさを確認する。この行数は上限ではない。行数だけを理由に分割しない。

## 変更時の確認

- ファイルを移動・分割する前に、そのファイルが参照するモジュールと、そのファイルを参照する利用側を確認する。
- 新しい共有モジュールを作る前に、その責務と依存方向に合う既存の配置がないか確認する。
- 構造変更後は、変更した範囲とその依存先・利用側を対象に、循環依存と禁止された層間のインポートがないことを確認する。調査範囲は変更の影響に合わせる。
