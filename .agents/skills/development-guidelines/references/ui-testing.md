# UI テストの実装

Storybook・Playwright・UI モック・UI テストの変更時に参照する。

共通の可読性・アサーション・モック方針は [テスト共通ルール](testing-common.md) を参照する。確認済みなら再読は不要。

## ストーリーで確認できる表示状態

UI の追加・変更時は、対象範囲の条件付き表示と表示条件を実装から確認し、既存ストーリーで確認できる状態と照合する。通常表示だけでなく、読み込み・保存の失敗、入力エラー、未保存、保存完了、復旧操作など、利用者が判断や操作に使う表示を対象にする。Host の応答でのみ表示される要素も含め、必要な状態を用意する。

自動操作テストで一度表示を検証していても、ストーリーを開いて目視確認できるとは限らない。確認対象のエラーを修正して保存まで進む `play` では、終了後にエラーや復旧ボタンが消える。こうした場合は、対象の状態で止まるストーリーや、その状態を選べる引数を用意し、ストーリー名や説明から表示条件を特定できるようにする。

一定時間で消える通知やアニメーションは、製品の表示時間を変えずに、表示中・退場中・消えた後を確認できる検証手段を用意する。時刻や外部応答の制御などを検証側で行い、目視確認のためだけに製品へ表示固定の分岐を追加しない。

ストーリーには実コンポーネントと製品の表示条件を使う。通知やエラーの見本をストーリー側に別途描画して代替しない。表示の削除・統合時は、対応するストーリーも削除・更新し、不要になった UI を検証のために残さない。

## 通信境界と実環境

対象プロジェクトのテスト設定と既存のモック API を確認する。製品の UI の操作、送信内容の確認、固定応答の注入、応答後の表示・操作可否の確認を分ける。モック内に承認・認証・保存などの製品処理を再実装せず、送信値を補正しない。応答前・成功後・失敗後の必要な状態を明示する。

実環境での受け入れ検証では画面操作や公開 API を使い、製品の状態を直接書き換えて操作を代替しない。外部応答を代替する範囲は、プロジェクトで定めた検証の条件に従う。表示だけでなく保存内容や副作用も観測する。

生成物・一時領域・プロセスは実行ごとに分離する。準備の失敗や結果が生成されていない状態を成功扱いにしない。終了時や期限切れ時は、検証用に起動したプロセスを終了する。要素の役割や名前で操作し、対象の状態になるまで待つ。
