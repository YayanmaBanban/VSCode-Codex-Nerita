# コーディング規約

ソースコードの追加・変更時に参照する。

## コメント

- コメントは日本語で、コードから読み取れない意図・理由・制約・外部仕様を説明する。コードを逐語的に言い換えるだけのコメントは避ける。外部仕様や回避策を理解するために根拠や適用条件が必要な場合は、それらも残す。
- ファイル先頭には、そのファイルの主要な役割を1〜3行で説明する。関数・型・クラスには、公開・非公開によらず、名前や型だけでは分からない役割や制約をコメントする。公開する関数・型・クラスでは、利用側が守る前提や注意点を明確にする。
- 関数内では、非自明な判断、互換性対応、回避策、処理順序に意味がある箇所をコメントする。

## 処理の流れと関数の分割

- 処理のまとまりごとに空行を入れ、上から下へ処理の流れを追えるようにする。
- ネストを増やすより、ガード節や早期 return を優先する。
- インラインのコールバックは、その場で流れを追える処理に留める。複数段階の処理やネストした非同期処理で見通しが悪くなる場合は、意味のある名前を持つ関数へ分離する。
- 関数は、独立した名前を付けられる責務が複数ある場合に分割する。行数を減らすためだけに数行の処理を別の関数へ切り出すことや、処理を追うための関数間の移動が増える分割は避ける。
- セットアップ・イベント処理・業務処理・クリーンアップなどを統括する関数では、「何をするか」が上から順に読める構造を優先する。「どう実現するか」の詳細で処理の流れが追いにくくなる場合は、補助関数へ分離する。
