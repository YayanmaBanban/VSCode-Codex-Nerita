# テスト方針

テストの追加・変更・整理に適用する。目的は、少ない変更コストで製品の振る舞い・契約・安全性の回帰を検出すること。件数やカバレッジの増減を成果としない。

共通の可読性・アサーション・モック方針は [テスト共通ルール](testing-common.md) を参照する。確認済みなら再読は不要。

## 追加・維持の判断

「このテストがなければ、どの具体的な不具合を見逃すか」で判断する。
対象仕様の既存テストを確認し、同じ回帰を検出できるなら既存の担当テストを使う。
担当テストは、その仕様を直接検証するテストまたはテスト群を指す。

- 追加する: 既存のテストで保護されていない重要なユーザー動作、外部契約、安全境界、複雑な状態遷移、実際に起きた不具合の再発防止。
- 既存の担当テストを拡張する: 同じ仕様の境界値や固有の失敗経路。代表値・境界値・過去の回帰を選ぶ。
- 削除・統合する: 固有の回帰を説明できない重複、外部から観測できる振る舞いを変えないリファクタリングだけで失敗するアサーション。

新しい実装やファイルに対応するという理由だけでは、テストを追加しない。
正式なテストは件数削減や実装完了だけを理由に削除しない。削除・統合時は、保護が不要になった理由、または保護を引き継ぐ担当テストを確認する。安全性・データ保持のテストでは、引き継ぐテストで同じ失敗経路を検出できることも確認する。配置先だけを理由に、テストを維持すべきか、削除してよいかを判断しない。
局所修正では関連するテストを調べればよく、全スイートの監査を毎回行う必要はない。

## ケースの独立性と選択実行

テストの作成・変更前に、事前条件・操作・期待結果・検出する具体的な不具合を明確にする。まず既存の担当テストと実行コマンドを調べ、ファイル・ケース名・タグなどで今回の対象を選択する。

各シナリオは、テストランナーから単独で選択・実行できるケースにする。関数に分けていても `main()` がすべて順番に呼び出す構成なら、単独で選択・実行できる単位に分離する。前のケースの操作状態・保存結果・実行順序には依存させず、必要な初期状態をケースごとに用意する。準備・後片付けはフィクスチャなどで共有してよい。

既存テストの必要なケースだけを実行できない場合は、今回必要なシナリオを独立して実行できるよう整理する。遅さを理由に同じ検証を別の使い捨てコードへ書き直さず、関連のないテストの一括移行も行わない。分離時は、元の前提条件と検出すべき失敗経路を維持する。

ケースを追加・分離したら、そのケースだけを選ぶコマンドで、対象が収集され、前のケースなしで実行できることを確認する。選択対象が0件だった実行を成功の証拠にしない。

## 一時検証と継続するテストの配置

一時検証は対象プロジェクトで定めた配置に置き、通常のテスト実行や CI の自動収集と分離する。目的と実行方法を残し、必要なものだけ明示して実行する。Git 管理の扱いはプロジェクトの規約に従う。用途を失った一時検証に恒久的な保守や代わりのテストの追加を求めない。

継続する回帰テストと共通の補助コードは既存の正式な配置に合わせる。追加時には、検出する具体的な不具合と実行タイミング・コマンドを明確にする。一時検証を作ったことだけを理由に正式な配置へ移さない。

## 仕様の担当テストとレイヤー

1仕様につき原則1つの担当テストを置く。上位層には、接続や実環境でしか検出できない失敗を担当させる。

| 種別 | 主な責任 |
| --- | --- |
| 単体テスト | ロジック、変換、状態遷移の入力と結果 |
| 契約テスト | スキーマ、プロトコル、公開 API、設定・保存形式の境界 |
| 結合テスト | コンポーネント間の接続、SDK 本体との連携、保存と独立した再起動後の復元 |
| スモークテスト | 起動・主要機能・配布物が実環境で動くこと |
| e2e / UI | 重要なユーザー操作と表示結果 |

正確な保存パスは保存先の契約テストで検証する。永続化やスモークテストでは保存・再起動・復元を検証し、パス文字列を重ねて固定しない。

## 安全性・データ保持

サンドボックス・承認・信頼・ワークスペース外アクセス・シェル・シンボリックリンク・外部コードの読み込みは、許可と拒否の両方を検証する。
破損したセッションの読み込み、復元失敗、会話の分岐では、既存データや現在の会話を失わないことを守る。
SDK との接続、OS の境界、人の承認操作など、異なる境界を検証する複数のテストレイヤーは維持する。
初期化失敗や前段の拒否を、目的の安全境界が機能した証拠にしない。

## 検証と完了

変更の影響に合うテストから実行し、今回の変更による失敗を修正して関連テストを再実行する。
ユーザーが依頼した範囲で、一時検証データだけを使うローカル検証は、その都度の確認を挟まず進める。
実際の認証・外部サービスの利用・インストールを伴う試験は、必要な環境と依頼の範囲を確認して選ぶ。
実行コマンドと前提環境は対象リポジトリの文書・パッケージ定義・テスト設定から確認する。
成功の判断は実際に検証した範囲に限定する。Storybook の描画成功を実際のバックエンドとの接続成功とみなさず、ローカル検証の成功を製品の UI・OS・外部サービスを使った受け入れ検証の成功とみなさない。

失敗は、製品の回帰、意図した仕様変更、実装への過剰な結合、環境不足に分けて判断する。
成功させるためだけにアサーションを削除・緩和したり、スキップへ変更したりしない。
重要な回帰テストを追加・変更した場合は、既知の不具合を再現した状態や、安全に元へ戻せる意図的な不具合を加えた状態で、目的のアサーションが失敗することを確認する。準備の失敗ではなく、検出対象の不具合で失敗したことを確かめる。既存テストの検出力を確認済みで、今回アサーションや検証経路を変えていなければ、毎回の再確認や全件のミューテーションテストは不要。確認できなかった場合は、検出力を未確認として報告する。
必要な検証が通ったら完了とし、新たな変更・失敗・未解決の懸念がなければ実行範囲を広げない。
全件実行は、全体整理や共通基盤の変更などで必要な場合、または明示的に依頼された場合に行う。
報告には変更理由、実行結果、残る失敗・未検証範囲を含める。
