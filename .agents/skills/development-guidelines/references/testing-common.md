# テスト共通ルール

テストコードの実装・変更・レビューで使う共通ルール。作業別リファレンスから参照される場合は、作業に該当する項目を読む。

## テストコードの可読性

- テストは、利用者や呼び出し側から観測できる振る舞い・シナリオを基準に構成する。実装の内部構造に合わせるためだけに分割しない。
- 1つのテストでは原則として1つのシナリオを検証する。同じシナリオの結果を確認する複数のアサーションは分割しなくてよい。
- テスト名には「どの条件・操作で、何が起きるか」を示し、失敗したアサーションと合わせて壊れた振る舞いを特定できるようにする。
- 準備・操作・検証のまとまりを空行で分け、上から順に原因と結果を追えるようにする。
- シナリオ固有の前提と結果に影響する入力値は、そのテストの近くに明示する。`beforeEach`・共有の検証データ・ビルダー・ファクトリーを使う場合も、結果の理解に必要な状態や値は、そのテストから読み取れるようにする。
- テストでは DRY より局所的な可読性を優先する。ヘルパーは準備・後片付けの詳細や、外部境界・ユーザー操作の手順を簡潔に表すために使い、重要な入力・操作・期待結果を隠さない。短い準備コードの重複を避けるためだけに抽出しない。
- パラメーター化テストは、同じ振る舞いを異なる代表値・境界値で確認する場合に使い、各ケースが失敗時に識別できる名前を持たせる。

## アサーションと検証データ

入力と観測可能な結果を優先する。内部クラス・インポート・ファイル分割・中間構造・DOM の入れ子・細かな呼び出し順や回数は、それ自体が契約の場合だけ固定する。
二重実行や承認の迂回を検出する呼び出し回数は、安全性を守るアサーションとして扱う。

アサーションでは、対象の振る舞いを検証するために必要な値を確認する。オブジェクト全体の一致やスナップショットは、その全体が検証したい契約である場合に使う。

期待結果は具体的な値で示し、本番と同等の分岐や計算で導出しない。繰り返し操作や共通アサーションにループを使う場合も、失敗したケースと期待結果を特定できるようにする。
テスト専用の不要なエクスポートや抽象化を本番コードに追加しない。

## モックの方針

高速に動作し、同じ条件で同じ結果を返す依存先は、可能な限り実装をそのまま使う。モックは、ネットワーク・OS・時刻・乱数・外部 SDK など、対象テストで制御が必要な境界に使う。実際の接続や互換性を検証するテストでは、その境界をモックで置き換えない。
